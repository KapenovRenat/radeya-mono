# API Reference

> Все эндпоинты `server/`. Формат записи задан в [AGENTS.md](../AGENTS.md),
> раздел «Фиксация изменений кода в docs/».
> Базовый префикс — `/api`. Локально: `http://localhost:4000/api`.

---

## Общее

**Формат ошибки** — одинаковый для всех эндпоинтов (тип `ApiErrorResponse` в `shared`):

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Не найдено",
    "details": { "email": ["Некорректный адрес"] }
  }
}
```

`details` присутствует только у `VALIDATION_ERROR`.

**Коды ошибок:** `VALIDATION_ERROR` (400), `UNAUTHORIZED` (401), `FORBIDDEN` (403),
`NOT_FOUND` (404), `CONFLICT` (409), `INTERNAL_ERROR` (500).

## Health

### GET /api/health

Проверка, что сервер жив и база отвечает. Используется при разработке и для мониторинга.

- Auth: не требуется
- Параметры: нет
- Ответ 200 — сервер и база в порядке:
  ```json
  {
    "status": "ok",
    "environment": "development",
    "uptimeSeconds": 42,
    "database": "ok",
    "timestamp": "2026-08-12T10:00:00.000Z"
  }
  ```
- Ответ 503 — сервер жив, база недоступна: то же тело с
  `"status": "degraded"` и `"database": "unavailable"`.
- Ошибки: если сервер не поднят — соединение не устанавливается.
- Файл: `server/src/modules/health/health.routes.ts`

> Разные коды ответа нужны мониторингу: 200 — всё хорошо, 503 — требуется вмешательство.

## Auth

Вход сотрудников в дашборд. **Регистрации через API нет:** первый администратор
создаётся командой `npm run create:admin --workspace=server`, остальных сотрудников
заводит админ из раздела «Сотрудники».

### Как устроена сессия

Токен наружу не отдаётся. После успешного входа сервер ставит **httpOnly-куку**
`radeya_sid` с идентификатором сессии; сама сессия — строка в таблице `Session`.

- `httpOnly` — кука недоступна из JavaScript, поэтому её нельзя украсть через XSS.
- `sameSite=lax` — не уходит на сторонние домены, это защита от CSRF.
- `secure` — только в продакшене: по http такая кука не поставится.
- Срок жизни — 7 дней.

Фронту достаточно отправлять запросы с `credentials: "include"` — браузер приложит куку сам.
Хранить что-либо в `localStorage` не нужно и нельзя.

Сессия проверяется **на каждом запросе**: истекла, удалена или сотрудник отключён —
доступ закрывается немедленно, без ожидания срока.

### POST /api/auth/login

Вход по логину и паролю.

- Auth: не требуется
- Тело: `{ "login": "ivan", "password": "..." }` (тип `LoginRequest` в `shared`)
- Ответ 200: `{ "user": { "id", "login", "name", "position", "role" } }` + кука `radeya_sid`
- Ошибки:
  - `401 UNAUTHORIZED` — неверная пара, отключённая учётная запись **или несуществующий логин**.
    Причина намеренно не уточняется: разделение подсказывает, какие логины существуют.
  - `400 VALIDATION_ERROR` — логин или пароль не проходят по формату, тем же текстом.
- Файл: `server/src/modules/auth/auth.routes.ts`

> Сравнение пароля выполняется и для несуществующего логина — по фиктивному хешу.
> Иначе по времени ответа можно перебрать список существующих учётных записей.

### POST /api/auth/logout

Завершение сессии.

- Auth: требуется
- Параметры: нет
- Ответ 204: тело пустое, кука удалена
- Ошибки: `401 UNAUTHORIZED` — сессии нет или она истекла
- Файл: `server/src/modules/auth/auth.routes.ts`

### GET /api/auth/me

Текущий пользователь. Фронт дёргает его при загрузке, чтобы понять, вошёл ли сотрудник.

- Auth: требуется
- Параметры: нет
- Ответ 200: `{ "user": { "id", "login", "name", "position", "role" } }`
- Ошибки: `401 UNAUTHORIZED` — не вошёл, сессия истекла или учётная запись отключена
- Файл: `server/src/modules/auth/auth.routes.ts`

## Users

Раздел «Аккаунты» — **целиком для роли `ADMIN`**. Иначе менеджер выпишет себе
роль `ADMIN` и обойдёт любые ограничения; список закрыт по тому же принципу —
состав команды с ролями рядовому сотруднику знать незачем.

### GET /api/users

Список сотрудников, свежие сверху.

- Auth: требуется, роль `ADMIN`
- Параметры: нет
- Ответ 200: `{ "items": [ { "id", "login", "name", "position", "role", "isActive", "createdAt" } ] }`
- Ошибки: `401 UNAUTHORIZED`, `403 FORBIDDEN`
- Файл: `server/src/modules/users/users.routes.ts`

### POST /api/users

Создание сотрудника. Пароль задаёт админ.

- Auth: требуется, роль `ADMIN`
- Тело: `{ "login", "password", "name", "position", "role" }` (тип `CreateUserRequest` в `shared`)
- Ответ 201: созданный сотрудник в форме `UserListItem`
- Ошибки:
  - `400 VALIDATION_ERROR` — с `details`: поле → список претензий, форма показывает их под полями
  - `409 CONFLICT` — логин занят
  - `403 FORBIDDEN` — роль ниже `ADMIN`
- Файл: `server/src/modules/users/users.routes.ts`

> Уникальность логина проверяет база, а не предварительный запрос: два одновременных
> запроса прошли бы такую проверку оба. Ошибка уникального индекса переводится в 409.

> Создание пишется в журнал действий. Пароль и его хеш в журнал не попадают.

## Audit

### GET /api/audit

Журнал действий, новые сверху. Постранично по 50 записей.

- Auth: требуется, роль `ADMIN`
- Параметры: `page` (query, число, по умолчанию 1)
- Ответ 200: `{ "items": [ { "id", "at", "userId", "userLogin", "userRole", "action", "entityType", "entityId" } ], "total", "page", "pageSize" }`
- Ошибки: `401 UNAUTHORIZED`, `403 FORBIDDEN`
- Файл: `server/src/modules/audit/audit.routes.ts`

> Эндпоинтов на изменение и удаление нет и не будет: журнал, который можно править,
> журналом не является. Пагинация обязательна — журнал растёт непрерывно.

> `userLogin` и `userRole` — снимок на момент действия, а не текущие значения.

## Kaspi Catalog

### POST /api/kaspi-catalog/preview

Разбор выгрузок каталога из кабинета Kaspi. **В базу ничего не пишет** — только
показывает, что получилось.

- Auth: требуется, роль `ADMIN`
- Тело: `{ "active": "<xml>", "archive": "<xml>" }` — содержимое файлов текстом,
  оба поля необязательные, но хотя бы одно должно быть (тип `KaspiCatalogPreviewRequest`)
- Ответ 200: `{ "offers": [...], "summary": {...}, "parsedAt": "..." }` (тип `KaspiCatalogPreview`)
- Ошибки:
  - `400 VALIDATION_ERROR` — файл не XML или в нём нет узла `kaspi_catalog → offers`
  - `409 CONFLICT` — не прислали ни одного файла
  - `403 FORBIDDEN` — роль ниже `ADMIN`
- Файл: `server/src/modules/kaspi-catalog/kaspi-catalog.routes.ts`

> Лимит тела на этом маршруте поднят до 20 МБ: две выгрузки весят около 650 КБ,
> а общий лимит приложения намеренно оставлен в 1 МБ.

> Файлы приходят текстом в JSON, а не multipart: ради двух текстовых файлов
> тащить разбор multipart на сервер незачем.

> Содержимое файлов в журнал действий не попадает — только итоги разбора.

### POST /api/kaspi-catalog/fetch

Обход каталога прямо в кабинете Kaspi (`mc.shop.kaspi.kz/bff/offer-view/list`):
товары в продаже и снятые с продажи за один вызов. Товары возвращаются сырыми,
как их отдал кабинет, — состав нашего DTO ещё не определён. **В базу не пишет.**

- Auth: требуется, роль `ADMIN`
- Тело: `{ "cookie": "...", "remember": false }` (тип `KaspiCabinetFetchRequest`),
  оба поля необязательные; пустая `cookie` — берётся запомненная
- Ответ 200: `{ "total", "onSale", "offSale", "expected", "withProblems", "pages", "stoppedAtPage", "stoppedReason", "hasStoredCookie", "warehouses", "sample", "offers" }`
  (тип `KaspiCabinetFetchResponse`). В `offers` — разобранные товары (`CabinetOffer`),
  не сырой ответ площадки; в `warehouses` — сводка складов за обход
  (`CabinetWarehouse`: `code`, `storeId`, `cityId`, `offersCount`, `totalStock`);
  в `sample` — три первых товара парами `{ raw, parsed }` (`CabinetSample`)
- Ошибки:
  - `400 VALIDATION_ERROR` — нет ни присланной, ни запомненной куки; не задан `KASPI_MERCHANT_ID`
  - `401 KASPI_UNAUTHORIZED` — Kaspi не принял куку: протухла или скопирована не целиком
  - `502 KASPI_UNAVAILABLE` — кабинет не ответил или вернул ошибку
  - `502 KASPI_BAD_RESPONSE` — пришёл не JSON или не список: формат изменился
  - `403 FORBIDDEN` — роль ниже `ADMIN`
- Файл: `server/src/modules/kaspi-catalog/kaspi-catalog.routes.ts`

> **Кука нигде не сохраняется на диск.** Только в памяти процесса и только при
> `remember: true`. В журнал действий, логи и ответ она не попадает: это по сути
> пароль от кабинета. Перезапустили сервер — вставляется заново.

> **Обрыв не теряет работу.** Кука протухла на середине — сервер возвращает то,
> что успел, и номер страницы в `stoppedAtPage`. Прогресс между вызовами не
> хранится: продолжение с места обрыва — задача синхронизации, её пока нет.

> **Защита от неверного ответа.** При протухшей сессии кабинет отвечает HTML
> страницы входа с кодом 200. Без проверки на массив это выглядело бы как пустой
> каталог, поэтому «не JSON» и «не список» — ошибки, а не ноль товаров.

> **Сырой ответ наружу не отдаётся — кроме образца.** В нём около трёхсот
> записей цен по городам на каждый товар, а нужна из них одна: ответ на 1335
> товаров весил бы мегабайты. Маппинг — `toCabinetOffer()` в `kaspi-cabinet.mapper.ts`.
> Исключение — поле `sample`: первые три товара сырыми и разобранными, чтобы
> сверять маппинг в консоли браузера (`SAMPLE_SIZE` в `kaspi-cabinet.service.ts`).
> Печатает их `logCabinetResponse()` в `use-kaspi-cabinet.ts` — свёрнутыми
> группами, рядом со списком всех разобранных товаров и таблицей складов.
> Это инструмент этапа 2: когда модели заведены, образец и вывод в консоль уходят.

> **Спорные места помечаются, а не разбираются наугад.** Цена различается по
> городам, в `familyId` несколько чисел, нет артикула — всё это попадает
> в `problems` у товара и в счётчик `withProblems`. Молча выбранное значение
> всплыло бы ошибкой в цене, и найти его было бы негде.

> **Склады собираются за весь обход.** Источник — `availabilities[].storeId`
> (`6871008_PP3`), код склада берётся из его хвоста; поле `points` для справочника
> не годится — там только `PP3`, без `storeId`. Сводка складывается
> в `collectCabinetWarehouses()` (`kaspi-cabinet.warehouses.ts`) и годится для
> `POST /api/warehouses/import-kaspi` как есть.

> **`cityId` в ответе кабинета всегда `null`.** Кода города (КАТО) у склада
> в JSON нет: `allCityPrices` — это города, где показывается цена покупателю,
> а не города складов. При импорте пустой город понимается как «неизвестно»:
> у складов, уже заведённых из выгрузки, он сохраняется, у новых остаётся пустым.

> **Два обхода за вызов:** `a=true` (в продаже) и `a=false` (архив). Статус
> товара определяется тем, в каком обходе он пришёл, — как и с файлами
> `ACTIVE.xml` / `ARCHIVE.xml`.

> **Полнота проверяется.** Кабинет присылает `total` на каждой странице; сумма
> по обоим режимам попадает в `expected`. Не сошлось с `total` — значит обход
> что-то потерял, и это видно на странице, а не только в логах.

> Страницы берутся по 100, между обращениями пауза 500 мс: частые запросы
> приводят к блокировке по IP. Обход останавливается, если страница не принесла
> ни одного нового `offerId` — значит кабинет перестал листать. Лишнее обращение
> за пустой страницей не делается: как только получено обещанное количество,
> режим закрывается.

## Warehouses

Справочник складов (точек выдачи). Целиком закрыт ролью `ADMIN`:
`warehousesRouter.use(requireAuth, requireRole(ADMIN))`.

### GET /api/warehouses

Справочник складов, отсортирован по коду.

- Auth: требуется, роль `ADMIN`
- Параметры: нет
- Ответ 200: `{ "items": WarehouseDto[] }` — `id`, `code`, `kaspiStoreId`,
  `kaspiCityId`, `name`, `isActive`, `kaspiOffersCount`, `kaspiTotalStock`,
  `kaspiStatsAt`
- Ошибки: `401 UNAUTHORIZED`, `403 FORBIDDEN`
- Файл: `server/src/modules/warehouses/warehouses.routes.ts`

### POST /api/warehouses/import-kaspi

Заводит склады из предпросмотра выгрузки Kaspi. Операция повторяемая:
сверка идёт по `code`, дубликаты не создаются.

- Auth: требуется, роль `ADMIN`
- Тело: `{ "warehouses": [{ "code": "PP3", "storeId": "6871008_PP3", "cityId": "710000000" | null }] }`
  (тип `SaveWarehousesRequest`), от 1 до 500 записей
- Ответ 200: `{ "created": 33, "updated": 0, "unchanged": 0 }` (тип `SaveWarehousesResponse`)
- Ошибки:
  - `400 VALIDATION_ERROR` — код не вида `PP3`, `storeId` не вида `6871008_PP3`,
    `cityId` не число, пустой список или больше 500 записей
  - `409 CONFLICT` — код склада в списке дважды, либо `storeId` уже занят другим кодом
  - `403 FORBIDDEN` — роль ниже `ADMIN`
- Файл: `server/src/modules/warehouses/warehouses.routes.ts`

> Приходит разобранный список, а не XML заново: сохраняется ровно то, что человек
> увидел на экране. Данные всё равно от клиента, поэтому каждое поле проверяется
> по шаблону — эндпоинт админский, но «свой пользователь» валидацию не заменяет.

> **Что выгрузка не перезаписывает:** `name` (наше название точки) и уже
> заполненный `kaspiCityId`. Пустой город в файле означает «неизвестно», а не
> «сотри». Иначе повторная загрузка стёрла бы всё, что вписали руками.

> **Счётчики сохраняются снимком.** `offersCount` и `totalStock` из запроса
> ложатся в `kaspiOffersCount`, `kaspiTotalStock` и датируются `kaspiStatsAt`.
> Они необязательны: в XML-выгрузке остатка по складу нет. Это состояние на
> момент загрузки, а не настройка склада, поэтому пишутся всегда — но
> изменением справочника не считаются и в счётчик `updated` не попадают.

> Склады, пропавшие из новой выгрузки, **не удаляются**: на них ссылаются прошлые
> заказы. Закрытую точку отключают флагом `isActive`.

> Вся запись идёт одной транзакцией — при сбое на середине справочник не остаётся
> заполненным наполовину.

## Products

Каталог. Целиком закрыт ролью `ADMIN`: заполнение каталога — настройка учёта,
а не рабочий экран.

### GET /api/products/skus

Артикулы, которые уже лежат в базе. По ним страница синхронизации прячет из
таблицы то, что сохранено ранее.

- Auth: требуется, роль `ADMIN`
- Параметры: нет
- Ответ 200: `{ "skus": string[] }` (тип `KnownSkusResponse`)
- Ошибки: `401 UNAUTHORIZED`, `403 FORBIDDEN`
- Файл: `server/src/modules/products/products.routes.ts`

> Отдаём только артикулы, а не товары целиком: полторы тысячи строк по 10 байт —
> это 13 КБ, и фронту для сверки больше ничего не нужно.

### POST /api/products/import-kaspi

Заводит в каталоге товары, загруженные из кабинета. Создаёт `Product`, `Variant`,
`Listing(KASPI)` и остатки по складам одной вложенной вставкой на товар.

- Auth: требуется, роль `ADMIN`
- Тело: `{ "offers": CabinetOffer[] }` (тип `ImportKaspiProductsRequest`),
  не больше 5000 позиций
- Ответ 200: `{ "created", "skipped", "failed": [{ "sku", "reason" }], "missingWarehouses": string[] }`
  (тип `ImportKaspiProductsResponse`)
- Ошибки:
  - `400 VALIDATION_ERROR` — пустой список, больше 5000 позиций, товар без
    артикула, код склада не вида `PP3`, отрицательная цена
  - `403 FORBIDDEN` — роль ниже `ADMIN`
- Файл: `server/src/modules/products/products.routes.ts`

> **Создаём только новое.** Товар, который уже есть по артикулу, пропускается
> целиком: у него может быть наша категория, ткань, закупочная цена и цена сайта.
> Обновление полей кабинета будет отдельной операцией с показом расхождений,
> а не молчаливой перезаписью.

> **Сохранение — отдельное нажатие.** Загрузка каталога в базу не пишет никогда:
> человек сначала смотрит таблицу, и только потом сохраняет то, что увидел.

> **Одна плохая запись не отменяет импорт.** Товар, который не сохранился,
> попадает в `failed` с причиной; остальные заводятся. Заливать полторы тысячи
> позиций заново из-за одной строки дороже, чем показать список.

> **Склад, которого нет в справочнике, не выдумывается.** Остатки по нему
> не записываются, код попадает в `missingWarehouses`: сначала «Сохранить
> склады», потом товары.

> **Дубли артикулов в запросе отбрасываются.** В кабинете один артикул бывает
> и в продаже, и в архиве — без этого вставка упала бы на уникальном индексе
> посреди импорта.

> **Каталог присылается пачками по 100 товаров.** Целиком это около пяти
> мегабайт — картинки и история изменений у каждой позиции, — а общий лимит
> тела запроса намеренно оставлен в 1 МБ. Свой лимит на маршруте не помог бы:
> `express.json` приложения разбирает тело раньше маршрутных мидлваров.
> Побочный выигрыш: виден прогресс, и сбой на середине не отменяет сохранённое.

## Права и роли

Две мидлвары в `server/src/middlewares/require-auth.ts`:

- `requireAuth` — проверяет сессию и кладёт пользователя в `req.user`.
- `requireRole(...roles)` — ограничение по ролям, ставится **после** `requireAuth`.

Проверка прав всегда на сервере. Скрытая кнопка в интерфейсе защитой не является:
запрос отправляется и без неё.

## Дерево категорий и серверный каталог (18.09.2026)

Все операции ниже доступны только авторизованному ADMIN; общие ошибки:
401 UNAUTHORIZED — нет сессии, 403 FORBIDDEN — нет роли. Контракты находятся в
`shared/src/types/catalog.ts`, настройки — в `shared/src/constants/catalog.ts`.

### GET /api/categories
Получить созданные вручную папки. Новые категории ограничены двумя уровнями:
корневая категория → подпапка. Ранее созданные более глубокие узлы не скрываются.
- Auth: ADMIN.
- Параметры: нет.
- Ответ 200: `{ allProducts: { id: null, name: "Все товары" }, items: CategoryTreeNode[] }`.
- Узел: `{ id, name, parentId, children }`. Корневые узлы находятся в items.
- Сортировка соседних папок: sortOrder, name, id по возрастанию.
- «Все товары» — отдельный первый служебный пункт интерфейса, не запись Category;
  доступен и в пустом каталоге. Показывает также товары без папки и снятые с продажи.
- Дерево не зависит от поиска и пагинации товаров. Возвращаются все папки, включая
  неактивные: это внутренний каталог, а не публичная витрина.
- Ошибки: общие 401/403.
- Файл: `server/src/modules/categories/categories.controller.ts` (getCategories).

### POST /api/categories
Создать папку верхнего уровня или подпапку (максимум два уровня).
- Auth: ADMIN.
- Body: `{ name: string, parentId?: string | null }`.
- name: 1–150 символов после trim; parentId — UUID существующей папки.
  Отсутствующий parentId или null создаёт корневую папку. Указанный родитель
  обязан быть корневым; создание внутри подпапки возвращает 400 VALIDATION_ERROR.
- Ответ 201: `{ id, name, parentId }` (CategoryDto).
- Ошибки: 400 VALIDATION_ERROR — неверное тело либо зарезервированное имя
  «Все товары» без учёта регистра; 404 NOT_FOUND — родителя нет;
  409 CONFLICT — имя уже занято у этого родителя без учёта регистра либо
  исчерпаны повторные попытки после конкурентного изменения; общие 401/403.
- Одинаковые имена в разных родителях разрешены. Проверка корневых дубликатов
  защищена Serializable-транзакцией (обычный unique допускает NULL-родителей).
- path заполняется от родителя; slug служебный, category-UUID. Само создание
  папки не создаёт Product, не объединяет товары и не переносит их по названию.
- Аудит: CATEGORY_CREATED, новая папка в after.
- Файл: `server/src/modules/categories/categories.controller.ts` (postCategory).

### GET /api/products/variants
Страница артикулов из нашей БД, с серверным поиском и фильтром по папке.
- Auth: ADMIN.
- Query (все необязательные): page — целое 1–1000000, по умолчанию 1;
  pageSize — только 10/20/50, по умолчанию 20; search — строка до 200 символов
  после trim; categoryId — UUID папки. Пустой categoryId не передавать.
- Ответ 200: `{ items: CatalogRowDto[], total, page, pageSize, totalPages }`.
  Используется существующая форма PaginatedResponse с дополнительным totalPages.
- Одна строка — Variant, поэтому total считает артикулы. Поиск по части строки,
  без учёта регистра: sku, Product.name, kaspiMasterTitle, kaspiTitle (ИЛИ).
  %, _ и обратная косая черта ищутся буквально. Пустой поиск не ограничивает выборку.
- categoryId включает саму папку и все её подпапки; без него — весь каталог.
  Поиск работает внутри выбранной области, а не только внутри полученной страницы.
- Порядок: Variant.createdAt по убыванию, затем id по возрастанию.
- Страница вне диапазона приводится к последней существующей; пустой результат:
  items=[], total=0, page=1, totalPages=0. Фронт использует возвращённый page.
- Счётчик и страница читаются в одном снимке RepeatableRead. Между отдельными
  запросами страниц каталог может измениться из-за импорта или переноса.
- Ошибки: 400 VALIDATION_ERROR — неверные параметры (включая неизвестные);
  404 NOT_FOUND — выбранная папка отсутствует; общие 401/403.
- Файл: `server/src/modules/products/catalog.controller.ts` (getCatalog).

Состав CatalogRowDto — всё, что хранится на артикуле. Тип:
`shared/src/types/catalog.ts`, выборка и маппинг: `catalog.mapper.ts`.

| Поле | Смысл |
|---|---|
| variantId, productId | Идентификатор строки и общей карточки товара |
| name, sku, barcode, brand | Наше название, артикул, штрихкод и бренд |
| category | { id, name } либо null |
| imageUrl | Первая пригодная миниатюра по HTTP(S) либо null |
| images | Вся галерея: массив { small, medium, large }, каждое поле может быть null |
| status, productIsActive | Наш статус продажи модификации и активность Product |
| sortOrder, createdAt, updatedAt | Порядок и даты самой модификации |
| fabric | { id, name, code, type } либо null |
| fabricShade | { id, name, code, hex, imageUrl } либо null |
| listings | Массив размещений: id, channel, status, price, discountPrice, discountPercent, externalId, externalSku, externalUrl, publishedAt, lastSyncedAt, syncError |
| stocks | Массив { warehouse: { id, code, name, kaspiStoreId, kaspiCityId, isActive }, quantity, preOrderDays } |
| totalStock, preOrderDays | Сумма остатков и максимальный срок предзаказа по складам |
| purchasePrice | Закупочная цена. Только дашборд — см. предупреждение ниже |
| minChannelPrice, maxChannelPrice | Денормализованные минимум и максимум по каналам |
| kaspi | Поля кабинета: masterTitle, title, model, masterSku, offerId, fileId, merchantUid, shopLink, updatedAt, updates |
| delivery | Пять флагов: any, express, local, merchant (кабинет) и site (наш) |
| product | Общее для всех модификаций: slug, description, kaspiFamilyId, createdAt, updatedAt |

**Закупочная цена отдаётся в этом DTO.** Эндпоинт закрыт ролью ADMIN целиком,
и в дашборде закупка нужна. Два следствия: на страницы магазина этот DTO
не отдавать ни в каком виде, и при открытии каталога ролям MANAGER и SELLER
`purchasePrice` срезать по роли, а не оставлять всем.

Цены — строки с двумя десятичными знаками в тенге либо null: number на цене
теряет тиын. Даты — ISO-строки. Неизвестный остаток quantity=null не заменяется
нулём, но в totalStock считается нулём — сложить «неизвестно» нечем. Нет Listing
для канала — нет элемента в массиве; это не нулевая цена. `kaspi.updates` —
сырой снимок истории кабинета, формат недокументированный, не разбирается;
пустой массив, если снимка нет. В ответ не входит только история `VariantChange` —
её отдаст будущий API подробной карточки, которого пока нет.

### PATCH /api/products/category
Перенести выбранные товары в папку либо снять привязку к папке.
- Auth: ADMIN.
- Body: `{ productIds: string[], categoryId: string | null }`.
  От 1 до 100 UUID товаров; повторные ID сворачиваются. categoryId обязателен;
  null снимает категорию. «Все товары» — обзор, а не место хранения.
- Ответ 200: `{ updated: number }` — число фактически изменённых Product.
- Переносятся все модификации каждого Product, включая не отображённые на странице.
  Частичный перенос при неверном ID исключён: вся операция в транзакции.
- Ошибки: 400 VALIDATION_ERROR — неверное тело; 404 NOT_FOUND — папка либо
  хотя бы один товар не найдены; 409 CONFLICT — товары изменены параллельно,
  повторить запрос; общие 401/403.
- Аудит: PRODUCTS_CATEGORY_CHANGED; before — старые категории изменённых товаров,
  after — целевая категория и их ID. Повторный перенос в ту же папку не пишет аудит.
- Файл: `server/src/modules/products/catalog.controller.ts` (patchProductsCategory).

### PATCH /api/categories/:id
Переименовать папку без изменения родителя и привязки товаров.
- Auth: ADMIN.
- Path: id — UUID существующей Category.
- Body: { name: string }, 1–150 символов после trim. Другие поля запрещены.
- Ответ 200: CategoryDto { id, name, parentId }.
- Ошибки: 400 VALIDATION_ERROR — неверный UUID/название, включая «Все товары»;
  404 NOT_FOUND — папки нет; 409 CONFLICT — дубликат имени внутри родителя
  без учёта регистра либо конфликт параллельного изменения; общие 401/403.
- Уникальность проверяется в Serializable-транзакции, включая корневые папки.
  path и slug при переименовании сохраняются. Повтор того же имени не пишет аудит.
- Аудит: CATEGORY_RENAMED, before/after с прежним и новым названием.
- Файл: server/src/modules/categories/categories.controller.ts (patchCategory).

### DELETE /api/categories/:id
Удалить пустую папку, не удаляя товары и подпапки.
- Auth: ADMIN.
- Path: id — UUID существующей Category. Body не требуется.
- Ответ 200: DeleteCategoryResponse { id }.
- Ошибки: 400 VALIDATION_ERROR — неверный UUID; 404 NOT_FOUND — папки нет;
  409 CONFLICT — есть хотя бы один товар (в том числе неактивный) или подпапка;
  общие 401/403. «Все товары» — служебный пункт без UUID, удалить его нельзя.
- В транзакции ReadCommitted запись Category блокируется FOR UPDATE перед
  проверкой товаров и подпапок. Новые FK-ссылки ждут блокировку; удаление не
  должно неявно отвязать конкурентно добавленный товар через onDelete: SetNull.
- Аудит: CATEGORY_DELETED, удалённая папка в before.
- Файл: server/src/modules/categories/categories.controller.ts (removeCategory).
