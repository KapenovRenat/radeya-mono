# API Reference

> Все эндпоинты `server/`. Формат записи задан в [AGENTS.md](../AGENTS.md),
> раздел «Фиксация изменений кода в docs/».
> Базовый префикс — `/api`. Локально: `http://localhost:4000/api`.

---

## Общее

**Формат ошибки** — одинаковый для всех эндпоинтов (тип `ApiErrorResponse` в `shared`):

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Не найдено",
    "details": { "email": ["Некорректный адрес"] }
  }
}
```

`details` присутствует только у `VALIDATION_ERROR`.

**Коды ошибок:** `VALIDATION_ERROR` (400), `UNAUTHORIZED` (401), `FORBIDDEN` (403),
`NOT_FOUND` (404), `CONFLICT` (409), `INTERNAL_ERROR` (500).

## Health

### GET /api/health

Проверка, что сервер жив и база отвечает. Используется при разработке и для мониторинга.

- Auth: не требуется
- Параметры: нет
- Ответ 200 — сервер и база в порядке:
  ```json
  {
    "status": "ok",
    "environment": "development",
    "uptimeSeconds": 42,
    "database": "ok",
    "timestamp": "2026-08-12T10:00:00.000Z"
  }
  ```
- Ответ 503 — сервер жив, база недоступна: то же тело с
  `"status": "degraded"` и `"database": "unavailable"`.
- Ошибки: если сервер не поднят — соединение не устанавливается.
- Файл: `server/src/modules/health/health.routes.ts`

> Разные коды ответа нужны мониторингу: 200 — всё хорошо, 503 — требуется вмешательство.

## Auth

Вход сотрудников в дашборд. **Регистрации через API нет:** первый администратор
создаётся командой `npm run create:admin --workspace=server`, остальных сотрудников
заводит админ из раздела «Сотрудники».

### Как устроена сессия

Токен наружу не отдаётся. После успешного входа сервер ставит **httpOnly-куку**
`radeya_sid` с идентификатором сессии; сама сессия — строка в таблице `Session`.

- `httpOnly` — кука недоступна из JavaScript, поэтому её нельзя украсть через XSS.
- `sameSite=lax` — не уходит на сторонние домены, это защита от CSRF.
- `secure` — только в продакшене: по http такая кука не поставится.
- Срок жизни — 7 дней.

Фронту достаточно отправлять запросы с `credentials: "include"` — браузер приложит куку сам.
Хранить что-либо в `localStorage` не нужно и нельзя.

Сессия проверяется **на каждом запросе**: истекла, удалена или сотрудник отключён —
доступ закрывается немедленно, без ожидания срока.

### POST /api/auth/login

Вход по логину и паролю.

- Auth: не требуется
- Тело: `{ "login": "ivan", "password": "..." }` (тип `LoginRequest` в `shared`)
- Ответ 200: `{ "user": { "id", "login", "name", "position", "role" } }` + кука `radeya_sid`
- Ошибки:
  - `401 UNAUTHORIZED` — неверная пара, отключённая учётная запись **или несуществующий логин**.
    Причина намеренно не уточняется: разделение подсказывает, какие логины существуют.
  - `400 VALIDATION_ERROR` — логин или пароль не проходят по формату, тем же текстом.
- Файл: `server/src/modules/auth/auth.routes.ts`

> Сравнение пароля выполняется и для несуществующего логина — по фиктивному хешу.
> Иначе по времени ответа можно перебрать список существующих учётных записей.

### POST /api/auth/logout

Завершение сессии.

- Auth: требуется
- Параметры: нет
- Ответ 204: тело пустое, кука удалена
- Ошибки: `401 UNAUTHORIZED` — сессии нет или она истекла
- Файл: `server/src/modules/auth/auth.routes.ts`

### GET /api/auth/me

Текущий пользователь. Фронт дёргает его при загрузке, чтобы понять, вошёл ли сотрудник.

- Auth: требуется
- Параметры: нет
- Ответ 200: `{ "user": { "id", "login", "name", "position", "role" } }`
- Ошибки: `401 UNAUTHORIZED` — не вошёл, сессия истекла или учётная запись отключена
- Файл: `server/src/modules/auth/auth.routes.ts`

## Users

Раздел «Аккаунты» — **целиком для роли `ADMIN`**. Иначе менеджер выпишет себе
роль `ADMIN` и обойдёт любые ограничения; список закрыт по тому же принципу —
состав команды с ролями рядовому сотруднику знать незачем.

### GET /api/users

Список сотрудников, свежие сверху.

- Auth: требуется, роль `ADMIN`
- Параметры: нет
- Ответ 200: `{ "items": [ { "id", "login", "name", "position", "role", "isActive", "createdAt" } ] }`
- Ошибки: `401 UNAUTHORIZED`, `403 FORBIDDEN`
- Файл: `server/src/modules/users/users.routes.ts`

### POST /api/users

Создание сотрудника. Пароль задаёт админ.

- Auth: требуется, роль `ADMIN`
- Тело: `{ "login", "password", "name", "position", "role" }` (тип `CreateUserRequest` в `shared`)
- Ответ 201: созданный сотрудник в форме `UserListItem`
- Ошибки:
  - `400 VALIDATION_ERROR` — с `details`: поле → список претензий, форма показывает их под полями
  - `409 CONFLICT` — логин занят
  - `403 FORBIDDEN` — роль ниже `ADMIN`
- Файл: `server/src/modules/users/users.routes.ts`

> Уникальность логина проверяет база, а не предварительный запрос: два одновременных
> запроса прошли бы такую проверку оба. Ошибка уникального индекса переводится в 409.

> Создание пишется в журнал действий. Пароль и его хеш в журнал не попадают.

## Audit

### GET /api/audit

Журнал действий, новые сверху. Постранично по 50 записей.

- Auth: требуется, роль `ADMIN`
- Параметры: `page` (query, число, по умолчанию 1)
- Ответ 200: `{ "items": [ { "id", "at", "userId", "userLogin", "userRole", "action", "entityType", "entityId" } ], "total", "page", "pageSize" }`
- Ошибки: `401 UNAUTHORIZED`, `403 FORBIDDEN`
- Файл: `server/src/modules/audit/audit.routes.ts`

> Эндпоинтов на изменение и удаление нет и не будет: журнал, который можно править,
> журналом не является. Пагинация обязательна — журнал растёт непрерывно.

> `userLogin` и `userRole` — снимок на момент действия, а не текущие значения.

## Kaspi Catalog

### POST /api/kaspi-catalog/preview

Разбор выгрузок каталога из кабинета Kaspi. **В базу ничего не пишет** — только
показывает, что получилось.

- Auth: требуется, роль `ADMIN`
- Тело: `{ "active": "<xml>", "archive": "<xml>" }` — содержимое файлов текстом,
  оба поля необязательные, но хотя бы одно должно быть (тип `KaspiCatalogPreviewRequest`)
- Ответ 200: `{ "offers": [...], "summary": {...}, "parsedAt": "..." }` (тип `KaspiCatalogPreview`)
- Ошибки:
  - `400 VALIDATION_ERROR` — файл не XML или в нём нет узла `kaspi_catalog → offers`
  - `409 CONFLICT` — не прислали ни одного файла
  - `403 FORBIDDEN` — роль ниже `ADMIN`
- Файл: `server/src/modules/kaspi-catalog/kaspi-catalog.routes.ts`

> Лимит тела на этом маршруте поднят до 20 МБ: две выгрузки весят около 650 КБ,
> а общий лимит приложения намеренно оставлен в 1 МБ.

> Файлы приходят текстом в JSON, а не multipart: ради двух текстовых файлов
> тащить разбор multipart на сервер незачем.

> Содержимое файлов в журнал действий не попадает — только итоги разбора.

## Warehouses

Справочник складов (точек выдачи). Целиком закрыт ролью `ADMIN`:
`warehousesRouter.use(requireAuth, requireRole(ADMIN))`.

### GET /api/warehouses

Справочник складов, отсортирован по коду.

- Auth: требуется, роль `ADMIN`
- Параметры: нет
- Ответ 200: `{ "items": WarehouseDto[] }` — `id`, `code`, `kaspiStoreId`,
  `kaspiCityId`, `name`, `isActive`
- Ошибки: `401 UNAUTHORIZED`, `403 FORBIDDEN`
- Файл: `server/src/modules/warehouses/warehouses.routes.ts`

### POST /api/warehouses/import-kaspi

Заводит склады из предпросмотра выгрузки Kaspi. Операция повторяемая:
сверка идёт по `code`, дубликаты не создаются.

- Auth: требуется, роль `ADMIN`
- Тело: `{ "warehouses": [{ "code": "PP3", "storeId": "6871008_PP3", "cityId": "710000000" | null }] }`
  (тип `SaveWarehousesRequest`), от 1 до 500 записей
- Ответ 200: `{ "created": 33, "updated": 0, "unchanged": 0 }` (тип `SaveWarehousesResponse`)
- Ошибки:
  - `400 VALIDATION_ERROR` — код не вида `PP3`, `storeId` не вида `6871008_PP3`,
    `cityId` не число, пустой список или больше 500 записей
  - `409 CONFLICT` — код склада в списке дважды, либо `storeId` уже занят другим кодом
  - `403 FORBIDDEN` — роль ниже `ADMIN`
- Файл: `server/src/modules/warehouses/warehouses.routes.ts`

> Приходит разобранный список, а не XML заново: сохраняется ровно то, что человек
> увидел на экране. Данные всё равно от клиента, поэтому каждое поле проверяется
> по шаблону — эндпоинт админский, но «свой пользователь» валидацию не заменяет.

> **Что выгрузка не перезаписывает:** `name` (наше название точки) и уже
> заполненный `kaspiCityId`. Пустой город в файле означает «неизвестно», а не
> «сотри». Иначе повторная загрузка стёрла бы всё, что вписали руками.

> Склады, пропавшие из новой выгрузки, **не удаляются**: на них ссылаются прошлые
> заказы. Закрытую точку отключают флагом `isActive`.

> Вся запись идёт одной транзакцией — при сбое на середине справочник не остаётся
> заполненным наполовину.

## Права и роли

Две мидлвары в `server/src/middlewares/require-auth.ts`:

- `requireAuth` — проверяет сессию и кладёт пользователя в `req.user`.
- `requireRole(...roles)` — ограничение по ролям, ставится **после** `requireAuth`.

Проверка прав всегда на сервере. Скрытая кнопка в интерфейсе защитой не является:
запрос отправляется и без неё.
