# API Reference

> Все эндпоинты `server/`. Формат записи задан в [AGENTS.md](../AGENTS.md),
> раздел «Фиксация изменений кода в docs/».
> Базовый префикс — `/api`. Локально: `http://localhost:4000/api`.

## Общее

**Формат ошибки** — одинаковый для всех эндпоинтов (тип `ApiErrorResponse` в `shared`):

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Не найдено",
    "details": { "email": ["Некорректный адрес"] }
  }
}
```

`details` присутствует только у `VALIDATION_ERROR`.

**Коды ошибок:** `VALIDATION_ERROR` (400), `UNAUTHORIZED` (401), `FORBIDDEN` (403),
`NOT_FOUND` (404), `CONFLICT` (409), `INTERNAL_ERROR` (500).

## Health

### GET /api/health

Проверка, что сервер жив и база отвечает. Используется при разработке и для мониторинга.

- Auth: не требуется
- Параметры: нет
- Ответ 200 — сервер и база в порядке:
  ```json
  {
    "status": "ok",
    "environment": "development",
    "uptimeSeconds": 42,
    "database": "ok",
    "timestamp": "2026-08-12T10:00:00.000Z"
  }
  ```
- Ответ 503 — сервер жив, база недоступна: то же тело с
  `"status": "degraded"` и `"database": "unavailable"`.
- Ошибки: если сервер не поднят — соединение не устанавливается.
- Файл: `server/src/modules/health/health.routes.ts`

> Разные коды ответа нужны мониторингу: 200 — всё хорошо, 503 — требуется вмешательство.

## Auth

Вход сотрудников в дашборд. **Регистрации через API нет:** первый администратор
создаётся командой `npm run create:admin --workspace=server`, остальных сотрудников
заводит админ из раздела «Сотрудники».

### Как устроена сессия

Токен наружу не отдаётся. После успешного входа сервер ставит **httpOnly-куку**
`radeya_sid` с идентификатором сессии; сама сессия — строка в таблице `Session`.

- `httpOnly` — кука недоступна из JavaScript, поэтому её нельзя украсть через XSS.
- `sameSite=lax` — не уходит на сторонние домены, это защита от CSRF.
- `secure` — только в продакшене: по http такая кука не поставится.
- Срок жизни — 7 дней.

Фронту достаточно отправлять запросы с `credentials: "include"` — браузер приложит куку сам.
Хранить что-либо в `localStorage` не нужно и нельзя.

Сессия проверяется **на каждом запросе**: истекла, удалена или сотрудник отключён —
доступ закрывается немедленно, без ожидания срока.

### POST /api/auth/login

Вход по логину и паролю.

- Auth: не требуется
- Тело: `{ "login": "ivan", "password": "..." }` (тип `LoginRequest` в `shared`)
- Ответ 200: `{ "user": { "id", "login", "name", "position", "role" } }` + кука `radeya_sid`
- Ошибки:
  - `401 UNAUTHORIZED` — неверная пара, отключённая учётная запись **или несуществующий логин**.
    Причина намеренно не уточняется: разделение подсказывает, какие логины существуют.
  - `400 VALIDATION_ERROR` — логин или пароль не проходят по формату, тем же текстом.
- Файл: `server/src/modules/auth/auth.routes.ts`

> Сравнение пароля выполняется и для несуществующего логина — по фиктивному хешу.
> Иначе по времени ответа можно перебрать список существующих учётных записей.

### POST /api/auth/logout

Завершение сессии.

- Auth: требуется
- Параметры: нет
- Ответ 204: тело пустое, кука удалена
- Ошибки: `401 UNAUTHORIZED` — сессии нет или она истекла
- Файл: `server/src/modules/auth/auth.routes.ts`

### GET /api/auth/me

Текущий пользователь. Фронт дёргает его при загрузке, чтобы понять, вошёл ли сотрудник.

- Auth: требуется
- Параметры: нет
- Ответ 200: `{ "user": { "id", "login", "name", "position", "role" } }`
- Ошибки: `401 UNAUTHORIZED` — не вошёл, сессия истекла или учётная запись отключена
- Файл: `server/src/modules/auth/auth.routes.ts`

## Users

Раздел «Аккаунты» — **целиком для роли `ADMIN`**. Иначе менеджер выпишет себе
роль `ADMIN` и обойдёт любые ограничения; список закрыт по тому же принципу —
состав команды с ролями рядовому сотруднику знать незачем.

### GET /api/users

Список сотрудников, свежие сверху.

- Auth: требуется, роль `ADMIN`
- Параметры: нет
- Ответ 200: `{ "items": [ { "id", "login", "name", "position", "role", "isActive", "createdAt" } ] }`
- Ошибки: `401 UNAUTHORIZED`, `403 FORBIDDEN`
- Файл: `server/src/modules/users/users.routes.ts`

### POST /api/users

Создание сотрудника. Пароль задаёт админ.

- Auth: требуется, роль `ADMIN`
- Тело: `{ "login", "password", "name", "position", "role" }` (тип `CreateUserRequest` в `shared`)
- Ответ 201: созданный сотрудник в форме `UserListItem`
- Ошибки:
  - `400 VALIDATION_ERROR` — с `details`: поле → список претензий, форма показывает их под полями
  - `409 CONFLICT` — логин занят
  - `403 FORBIDDEN` — роль ниже `ADMIN`
- Файл: `server/src/modules/users/users.routes.ts`

> Уникальность логина проверяет база, а не предварительный запрос: два одновременных
> запроса прошли бы такую проверку оба. Ошибка уникального индекса переводится в 409.

> Создание пишется в журнал действий. Пароль и его хеш в журнал не попадают.

## Audit

### GET /api/audit

Журнал действий и история изменений, новые сверху. Постранично по 50 записей.
С фильтром по сущности — история одного товара для его карточки.

- Auth: требуется, роль `ADMIN`
- Параметры (query, все необязательные): `page` — целое ≥ 1, по умолчанию 1;
  `entityType` + `entityId` — только парой: имя модели (`Variant`, `Product`,
  `Supplier`) и UUID; `action` — значение из `AUDIT_ACTIONS`. Неизвестный
  параметр — 400.
- Ответ 200: `{ "items": [ { "id", "at", "userId", "userLogin", "userRole", "action", "entityType", "entityId", "source", "changes", "context" } ], "total", "page", "pageSize" }`
- `source` — `MANUAL` | `IMPORT` | `KASPI_SYNC`, null у записей журнала действий.
- `changes` — `[{ field, from, to }]`, значения строками или null. `field` — ключ
  из `HISTORY_FIELD_LABELS`, подпись — `historyFieldLabel()`. Пустой массив
  у записей журнала действий.
- `context` — `{ warehouse?, document?, sheet?, note? }` либо null.
- Порядок: `at desc`, затем `id` — у записей одного импорта время одно.
- Ошибки: `400 VALIDATION_ERROR`, `401 UNAUTHORIZED`, `403 FORBIDDEN`
- Файл: `server/src/modules/audit/audit.controller.ts`

> Журнал и история — одна таблица, пишут их по-разному. `logAction()` — действие
> (вход, импорт целиком), после операции, сбой проглатывается. `recordHistory()`
> (`server/src/lib/history.ts`) — изменённые поля сущности, **в транзакции
> самого изменения**: не легла история — не применилось и изменение.
> Сейчас историю пишут: импорт товаров и остатков МойСклада, импорт поставщиков,
> правка поставщика, перенос товаров в папку, скрипт `rename-products`.

> Эндпоинтов на изменение и удаление нет и не будет: журнал, который можно править,
> журналом не является. Пагинация обязательна — журнал растёт непрерывно.

> `userLogin` и `userRole` — снимок на момент действия, а не текущие значения.

## Orders

### GET /api/orders
Страница заказов из нашей базы. Свежие сверху.
- Auth: `can()` — любой вошедший.
- Query (все необязательные): `page` — целое 1–1000000, по умолчанию 1;
  `pageSize` — только 10/20/50, по умолчанию 20; `search` — поиск по номеру
  заказа, до 200 символов после trim; `from` и `to` — период по дате оформления
  (`placedAt`), ISO-**время** включительно; `salesPointId`, `sellerId`,
  `deliveryStatusId`, `paymentMethodId`, `shipmentOriginId`, `customerSourceId` —
  списки uuid, до 50 значений каждый. Другие поля запрещены.
- Фильтры по справочникам заказы площадки не показывают: у них эти поля пустые.
  Так и задумано — «Наличка» не должна находить заказ Kaspi.
- `salesPointId` и `sellerId` передаются повторением параметра
  (`?salesPointId=a&salesPointId=b`). Пустой список в запрос не уходит вовсе:
  пусто означает «все», а не «ни одного» — сняв последнюю галку в фильтре,
  человек ждёт полный реестр, а не пустую таблицу.
- `from`/`to` принимаются временем, а не датой `YYYY-MM-DD`, намеренно:
  границы суток зависят от часового пояса, и «за 21 сентября» в Алматы и в UTC —
  разные наборы заказов. Переводит выбранные даты в моменты клиент: только он
  знает пояс пользователя. `from > to` отклоняется валидацией.
- Ответ 200: `{ items: OrderRowDto[], total, page, pageSize, totalPages }`
  (тип `OrderListResponse`).
- Поиск по части номера, без учёта регистра; `%`, `_` и обратная косая черта
  ищутся буквально.
- В строке едут `salesPoint` (`id`, `name`, `type`) и `seller` (`id`, `name`,
  `role`). `seller = null` у заказов площадки — их никто не заводил руками;
  интерфейс в этом случае показывает название точки. `commentsCount` — счётчик
  ленты, сами тексты отдаёт `/orders/:id/comments`.
- Поля офлайн-продажи (`externalNumber`, `paidAmount`, `balanceDue`,
  `discountPercent`, `discountComment`, `customerSource`, `deliveryStatus`,
  `shipmentOrigin`, `paymentMethod`) отдаются всегда, но у заказов площадки
  они пустые: Kaspi платит целиком и сразу, скидку считает сам, а наших
  справочников не знает. Из справочников едет только название — фильтруют
  по ним отдельными параметрами.
- Порядок: `placedAt` по убыванию, затем `code`. Второй ключ обязателен:
  у заказов одной миллисекунды порядок между запросами иначе не определён,
  и один мог бы попасть на две страницы, а другой ни на одну.
- Страница вне диапазона приводится к последней существующей.
- Счётчик и страница читаются в одном снимке RepeatableRead: иначе
  параллельная синхронизация сдвинет строки между `count` и `findMany`.
- **Наружу идёт узкий набор полей.** Адрес, координаты, накладная и прочее
  в списке не нужны, а телефон и имя покупателя — персональные данные:
  отдаём только то, что видно в таблице. Остальное отдаст карточка заказа.
- Ошибки: 400 VALIDATION_ERROR — неверные параметры; общие 401/403.
- Файл: `server/src/modules/orders/orders.controller.ts` (getOrders).

### GET /api/orders/kaspi
Одна страница заказов Kaspi, разобранная в нашу модель. **В базу не пишет.**
- Auth: `can([ADMIN])` — отладка сверки статусов, не рабочий экран. Фронт
  вызывает его только у админа.
- Query (все необязательные): `days` — за сколько дней назад от текущего
  момента, 1–730, по умолчанию 14; `page` — страница Kaspi с нуля, по умолчанию 0;
  `pageSize` — 1–100, по умолчанию 100 (больше Kaspi не отдаёт); `raw` — `1`
  добавляет к ответу `rawOrders` с заказами целиком, как прислал Kaspi.
- `raw` не включён по умолчанию: он удваивает вес ответа, а нужен только при
  разборе расхождений со складом.
- Ответ 200: `{ meta, count, orders: KaspiOrderDraft[], sample, withProblems }`
  (тип `KaspiOrdersPreview`). `meta` — блок Kaspi как есть (`totalCount`,
  `pageCount`, `pageNumber`, `pageSize`). `sample` — первый заказ сырым
  и разобранным рядом: сверка маппинга глазами, без открытия Kaspi.
- **Имена полей `KaspiOrderDraft` совпадают с моделью `Order`**: когда дойдём
  до записи, сохранение станет прямым переносом, без второго словаря имён.
  Деньги — строки с двумя знаками, даты — ISO.
- Поля, которых нет в Shop API (`cancelReason`, зоны доставки, суммы рассрочки,
  сроки этапов), всегда null: они приходят только из кабинета. Их заполнит
  отдельный проход.
- Спорное не угадывается: чего нет или что пришло не в том виде, попадает
  в `problems` у записи и остаётся пустым. `withProblems` — сколько таких.
- `seen` — сколько раз встретилось каждое значение `status`, `state`,
  `deliveryMode` и наших вычисленных. `unknownValues` — значения Kaspi, которых
  нет в нашем списке известных. Полного перечня статусов Kaspi не публикует,
  и это единственный способ узнать о новом: незнакомый статус помечается
  проблемой, а не падает молча в «Новый».
- Заказ без номера пропускается целиком: сопоставить его не с чем.
- Позиций в ответе нет — Kaspi отдаёт их отдельным запросом на каждый заказ.
  В `entriesCount` только их количество из `relationships`.
- Авторизация в Kaspi — заголовок `X-Auth-Token` со значением `KASPI_API_TOKEN`.
  Токен в ответ и в логи не попадает.
- Ошибки: 400 VALIDATION_ERROR — неверные параметры; 401 KASPI_UNAUTHORIZED —
  Kaspi не принял токен; 502 KASPI_UNAVAILABLE / KASPI_BAD_RESPONSE — Kaspi
  недоступен или ответил не тем; 503 KASPI_TOKEN_MISSING — токен не задан
  в `.env`; общие 401/403.
- Файл: `server/src/modules/orders/orders.controller.ts` (getKaspiOrders).

> Период задаётся днями назад, а не датами: это просмотр. Для записи в базу
> есть `POST /api/orders/sync` с отрезками и курсором.

### POST /api/orders/sync
Шаг синхронизации заказов: читает из Kaspi и **пишет в базу**.
- Auth: `can([ADMIN, MANAGER])`.
- Блокировка: та же, что у воркера заказов (`LOCKS.KASPI_ORDERS_SYNC`). Воркер
  в цикле — сразу 409 CONFLICT «повторите через минуту», без ожидания.
- Body: `{ period: '3m' | '2y', to?: string, cursor?: string, maxChunks?: number }`.
  `to` — правый край всего периода (ISO), задаёт первый вызов и повторяют
  остальные; `cursor` — граница, с которой продолжать, пусто на первом шаге;
  `maxChunks` — 1–100, по умолчанию 20. Другие поля запрещены.
- Ответ 200: `{ period, from, to, done, nextCursor, chunksTotal, chunksDone,
  pages, ordersSeen, created, updated, skipped, withProblems, unknownValues,
  unknownWarehouses, tookMs }` (тип `SyncKaspiOrdersResponse`).
- **Синхронизация возобновляемая.** Два года — это 244 трёхдневных отрезка,
  то есть минуты в одном запросе: оборвётся браузер или прокси. Поэтому вызов
  обрабатывает пачку отрезков и возвращает `nextCursor`; клиент повторяет, пока
  не придёт `done`. Готовый цикл — хук `useKaspiOrdersSync`.
- **`to` обязателен со второго шага.** Без якоря «два года назад» на каждом
  вызове означало бы чуть другую дату, окно ползло бы за временем, и последний
  отрезок не сходился.
- Отрезки идут от свежих к старым: оборвалась синхронизация — в базе уже лежат
  последние заказы, а не позапрошлогодние.
- Счётчики в ответе — **только этого вызова**. Итог за весь период складывает
  клиент: сервер не хранит состояние прогона.
- **Обновляются только поля Shop API.** Поля кабинета (`cancelReason`,
  `deliveryZone`, `loanAmount`, сроки этапов) в набор не входят намеренно:
  синхронизация по токену не должна затирать их пустотой.
- Заказ без номера или без даты создания пропускается и попадает в `skipped`:
  по номеру его ищут и обновляют, по дате считают выручку, подставлять «сейчас»
  нельзя.
- Склад ищется по `kaspiPickupPointId` в `Warehouse.kaspiStoreId`. Не нашёлся —
  заказ сохраняется без связи, код остаётся строкой, а сам склад попадает
  в `unknownWarehouses`. Сначала «Сохранить склады», потом заказы.
- Повторный прогон безопасен: запись идёт по номеру заказа, существующие
  обновляются. Пачками по 100 в транзакции.
- Ошибки: 400 VALIDATION_ERROR — неверное тело или границы; 401 KASPI_UNAUTHORIZED;
  502 KASPI_UNAVAILABLE / KASPI_BAD_RESPONSE; 503 KASPI_TOKEN_MISSING; общие 401/403.
- Аудит: KASPI_ORDERS_SYNCED на **каждый шаг** — только счётчики, без самих
  заказов: это персональные данные покупателей, а журнал не хранилище.
  У полного прогона таких записей около десятка, и по ним видно, где оборвалось.
- Файл: `server/src/modules/orders/orders.controller.ts` (postSyncKaspiOrders).

> Позиции заказов (`/orders/{id}/entries`) этим эндпоинтом не тянутся: Kaspi
> отдаёт их отдельным запросом на каждый заказ, и это отдельный проход.
> `OrderEntry` пока остаётся пустой.

Заказы, привязанные не к точке Kaspi, синхронизация не трогает: они попадают
в счётчик `skipped`. Номера офлайн-заказов начинаются с букв и с цифровыми
номерами площадки совпасть не могут, но затёртый офлайн-заказ восстанавливать
нечем — поэтому проверка стоит и здесь.

### GET /api/orders/:id
Заказ целиком — для окна заказа.
- Auth: `can()` — любой вошедший.
- Параметры: `id` (path, UUID).
- Ответ 200: `OrderDetailsDto` — все поля строки списка (`OrderRowDto`) плюс
  `kaspiState`, `cancellationReason`, даты (`approvedByBankAt`, `completedAt`,
  `courierTransmissionPlannedAt`, `courierTransmissionAt`), `deliveryCost`,
  `paymentMode`, `creditTerm`, `deliveryMode`, `isKaspiDelivery`, `isExpress`,
  `waybillNumber`, `deliveryAddress` (адрес одной строкой от Kaspi),
  `deliveryComment`, `originCityName`, `kaspiPickupPointId`, `entries`,
  `entriesLoaded`, `canLoadEntries`.
- `entries[]` — `{ id, entryNumber, sku, offerName, quantity, basePrice, totalPrice,
  categoryTitle, note, variant: { id, sku, name, imageUrl } | null }`. `variant` —
  наш товар по артикулу; null — в каталоге его нет. `variant.name` — по тому же
  правилу, что в каталоге (`variantDisplayName`): название карточки Kaspi, иначе
  название модели. Заглушка `entryNumber = -1`
  в список не входит.
- `entriesLoaded` — состав уже загружали (есть позиции или заглушка «пусто»).
  `canLoadEntries` — заказ Kaspi с `kaspiId`: состав можно забрать с площадки.
- `plannedPointDeliveryAt` — «Планируемая дата прибытия» из кабинета Kaspi
  (показывать датой без времени). `cabinetRefreshDue` — активный заказ Kaspi,
  дату не спрашивали или больше часа назад: окно само вызывает
  `POST …/cabinet/sync`.
- Телефон и адрес здесь полные: окно заказа — рабочий экран всех сотрудников.
  Скрывать их от кого-то — срезать поля по роли на сервере, как закупку в каталоге.
- Чтение на площадку не ходит и в базу не пишет — это `POST …/entries/sync`.
- Ошибки: 400 VALIDATION_ERROR — не UUID; 404 NOT_FOUND; общие 401/403.
- Файл: `server/src/modules/orders/orders.controller.ts` (getOrder),
  сервис `order-details.service.ts`.

### POST /api/orders/:id/entries/sync
Состав заказа Kaspi — забирается с площадки при первом открытии окна и остаётся в базе.
- Auth: `can()` — любой вошедший: вызывается сам при открытии заказа.
- Параметры: `id` (path, UUID). Тела нет.
- Ответ 200: `{ created, order: OrderDetailsDto }` — сколько позиций записано
  этим вызовом и заказ целиком, уже с составом.
- **Состав уже есть — Kaspi не трогается**, `created: 0`, заказ отдаётся как есть.
- Иначе `GET /orders/{kaspiId}/entries` (раздел 2.2 интеграции): `offer.code` —
  артикул, товар ищется в каталоге без учёта регистра, как в импортах МойСклада.
  Не нашёлся — позиция сохраняется без `variantId`, с названием с площадки.
- Kaspi вернул пусто — пишется заглушка `entryNumber = -1`: иначе «пусто»
  и «ещё не загружали» неотличимы, и заказ тянули бы при каждом открытии.
- Повтор и два открытия разом безопасны: `createMany` с `skipDuplicates`
  по `@@unique([orderId, entryNumber])`.
- POST, а не часть GET: чтение не должно ходить на площадку и писать в базу —
  иначе повторы браузера и кэш клиента дёргали бы Kaspi сами. В журнал не пишется.
- Ошибки: 400 ENTRIES_NOT_AVAILABLE — заказ не из Kaspi или без `kaspiId`;
  404 NOT_FOUND; 503 KASPI_TOKEN_MISSING; 401 KASPI_UNAUTHORIZED;
  502 KASPI_UNAVAILABLE / KASPI_BAD_RESPONSE; общие 401/403.
- Файл: `server/src/modules/orders/orders.controller.ts` (postSyncOrderEntries).

### POST /api/orders/:id/cabinet/sync
«Планируемая дата прибытия» одного заказа из кабинета Kaspi — окно заказа,

### POST /api/orders/cabinet/sync

- Тела нет. Под общей с воркером блокировкой: занято — 409.

## Stats

### GET /api/stats/orders
Сводка по заказам за период, в разрезе точек продаж.
- Auth: `can()` — любой вошедший. Закрыть выручку — перечислить роли в `stats.routes.ts`.
- Query: `from`, `to` — ISO-время включительно, оба необязательны. Период
  считает клиент: он же вычисляет «текущий месяц» и «прошлый месяц».
- Ответ 200: `{ from, to, total, points: OrderStatsCard[] }`.
- Считается двумя группировками, а не перебором заказов: их десятки тысяч.
- **Привязанные заказы в суммы не входят.** Офлайн-продажа, уехавшая
  Kaspi-доставкой, лежит в двух записях; считается заказ площадки, а офлайновый
  идёт справочно в `linkedCount` и `linkedAmount`.
- Точки без заказов за период не возвращаются: карточка из одних нулей занимает
  место и ничего не сообщает.

Как считаются деньги (правило одно на все точки):

| Показатель | Что входит |
|---|---|
| `netRevenue` | заказы в стадии «Доставлен» |
| `inTransit` | всё незавершённое: от «Новый» до «Своя доставка» |
| `totalRevenue` | `netRevenue` + `inTransit` |
| — | отменённые и возвраты **не входят никуда**: это не выручка |

`returnsCount` — «Возврат» и «Ожидают решения по возврату»; `cancelledCount` —
«Отменён» и «Ожидают возврата/отмены», сюда же попадает «Ошибочный ввод».
`returnsShare` — доля от числа заказов, один знак после запятой.

Самовывоз и своя доставка остаются в пути, пока их не перевели в доставленные:
иначе чистая выручка считала бы заказы, которые ещё лежат на складе.

- Ошибки: 400 VALIDATION_ERROR — `from > to`; общие 401/403.
- Файл: `server/src/modules/stats/stats.controller.ts` (getOrdersStats).

## Imports

Импорт продаж офлайн-точки из книги Excel. Только ADMIN: это запись в заказы
пачкой, и ошибка здесь стоит дороже, чем в любой форме.

Два шага: **предпросмотр разбирает файл и ничего не пишет**, запись принимает
именно те строки, которые человек увидел. Импорт, который пишет сразу, однажды
зальёт в заказы чужую таблицу, а откатывать это нечем.

### POST /api/imports/offline-orders/preview
Разбор книги. **В базу не пишет.**
- Auth: ADMIN.
- Тело: файл `.xlsx` двоичным потоком (не multipart). Лимит 25 МБ — рабочая
  книга продаж весит около четырёх; выше лимита запрос отклоняется, не доходя
  до распаковки.
- Query: `sheet` — название листа. Без него отдаётся **только список листов**:
  в рабочей книге их сотня, разбирать наугад нечего.
- Ответ 200: `OfflineImportPreview` — `sheets`, `sheet`, `rows`, `skipped`,
  `invalid`, `unknownValues`, `ignoredColumns`.
- Колонки ищутся **по заголовку**, а не по букве: порядок колонок на листах
  книги совпадает не везде. Строка заголовков — первая из пяти верхних, где есть
  и «Дата», и «Продажи».
- Строка без даты, но с признаками продажи (товар, оплата, продавец, адрес)
  попадает в ответ с замечанием. Строка, где кроме суммы нет ничего, считается
  служебным итогом и пропускается.
- Значение, которого нет в справочнике, **не отклоняет строку**: списки
  пополняемые, и новый способ оплаты не повод терять продажу. Такие значения
  собираются в `unknownValues` со счётчиком.
- Дата в ячейке — **календарный день в Астане**, а не в UTC: приводится
  к местной полуночи по постоянному смещению UTC+5 (Казахстан живёт на нём
  круглый год). Без этого заказ сохранялся бы на полночь UTC и показывался
  как «23.09.2026, 05:00» — время, которого в таблице нет. Смещение задано
  константой, а не часовым поясом сервера: в проде он почти наверняка UTC.
- Строка = заказ, даже когда у двух строк один покупатель и адрес: два товара
  в одну дату считаются двумя продажами. Решение пользователя, 24.09.2026.
- Скидка: до единицы — процентный формат Excel, умножается на сто; до ста —
  проценты как есть; больше ста — не процент, уходит в причину с замечанием.
  Текст целиком уходит в причину, тоже с замечанием.
- Остаток «оплачено» читается как `0.00`. Любой другой текст не выдумывается:
  замечание, поле пустое.
- Ошибки: 400 VALIDATION_ERROR — нет файла; 400 BAD_FILE — файл не книга Excel;
  400 HEADER_NOT_FOUND — на листе нет строки заголовков; 404 SHEET_NOT_FOUND;
  общие 401/403.
- Файл: `server/src/modules/imports/imports.controller.ts` (previewOfflineOrders).

### POST /api/imports/offline-orders/commit
Запись разобранных строк в заказы точки.
- Auth: ADMIN.
- Body: `{ salesPointId, sheet, rows }` — до 2000 строк. Строки проверяются
  целиком, хотя их же собрал сервер: между предпросмотром и записью лежит сеть.
- Точка обязана быть **офлайновой и открытой**: импортировать продажи в Kaspi
  нельзя.
- Ответ 201: `{ created, failed }`.
- Номера заказов — `OFF-1-000001` и дальше по счётчику точки. Буквы в начале
  не дают совпасть с цифровым номером Kaspi.
- Стадия заказа выводится из рабочего статуса доставки только для однозначных
  значений («Доставлен Клиенту» → DELIVERED, «Отмена заказа» → CANCELLED,
  «Ошибочный ввод» → CANCELLED). Остальное получает NEW: подставить
  правдоподобную стадию значит записать догадку.
- Продавец **не проставляется**: в листе стоит «чей рабочий день», а это
  не всегда тот, кто оформил. Имя сохраняется в комментарии заказа вместе
  с названием листа и номером строки.
- Всё в одной транзакции: половина импортированного месяца хуже, чем ничего —
  при повторе получились бы дубли, а найти место обрыва не по чему.
- Ошибки: 400 VALIDATION_ERROR; 404 NOT_FOUND — нет точки продаж; общие 401/403.
- Аудит: OFFLINE_ORDERS_IMPORTED — счётчики и название листа, без самих строк.
- Файл: `server/src/modules/imports/imports.controller.ts` (commitOfflineOrders).

## Suppliers

Справочник поставщиков и импорт его из выгрузки контрагентов МойСклада.
Список — любому вошедшему (нужен фильтру каталога); импорт и правка — только ADMIN:
это закупочная сторона дела.

Выгрузка МойСклада содержит **весь** справочник контрагентов — покупатели
Kaspi, банки, площадки, услуги и поставщики в одной книге. Поставщиками
считаются только строки группы `поставщики` (колонка «Группы»). Отбор
по группе, а не по «Тип контрагента»: там и покупатели помечены
«Юридическое лицо», по типу они неотличимы. Группу проставляет человек
в МойСкладе — это и есть его решение, кто поставщик.

Повторная заливка того же файла дублей не создаёт: сверка идёт по `externalId`
(UUID контрагента). На проверенной выгрузке он уникален на все 5751 строку,
тогда как наименования дают 630 групп дублей — по имени сверять нельзя.

### GET /api/suppliers
Справочник целиком, без пагинации: поставщиков десятки.
- Auth: `can()` — любой вошедший.
- Ответ 200: `SuppliersResponse` — `{ items: SupplierDto[] }`, отсортировано
  по названию. Закрытые тоже отдаются: на них ссылаются прошлые закупки.
- Файл: `server/src/modules/suppliers/suppliers.controller.ts` (getSuppliers).

### POST /api/suppliers/import/preview
Разбор выгрузки контрагентов. **В базу не пишет** — только читает, чтобы
показать, что новое, а что уже есть.
- Auth: ADMIN.
- Тело: файл `.xlsx` двоичным потоком (не multipart). Лимит 25 МБ.
- Query: `sheet` — название листа. Без него отдаётся только список листов.
- Ответ 200: `SupplierImportPreview` — `sheets`, `sheet`, `rows`, `total`,
  `filtered`, `invalid`, `known`.
- Колонки ищутся **по заголовку**: `UUID`, `Группы`, `Наименование`,
  `Фактический адрес`, `Телефон`. Строка заголовков — первая из пяти верхних,
  где есть и «Наименование», и «Группы».
- Группа сравнивается по каждому куску пути (`поставщики/Казахстан` подходит):
  контрагент может лежать во вложенной группе.
- Отброшенные строки не пропадают: их количество едет в `filtered`, чтобы было
  видно, что файл разобран целиком, а не обрезан.
- Строка без `UUID` **не записывается**: повторный импорт не отличит её
  от новой и заведёт второго такого же поставщика.
- Телефон-заглушка МойСклада `+7+0(000)-000-00-00` (в проверенной выгрузке
  таких 3606) телефоном не считается и до базы не доезжает. Замечания на неё
  нет: это не спорное значение, а известное значение по умолчанию. Формат
  остальных не приводится — в ячейке бывает два номера сразу.
- Поле, заполненное у нас и расходящееся с файлом, едет в `diffs` строки.
  Импорт его **не перезапишет** — показывает, чтобы человек решил сам.
- Наименование совпало, а UUID другой — замечание «будет заведён второй»:
  одинаковое имя у двух разных поставщиков возможно, склеивать их молча нельзя.
- Ошибки: 400 VALIDATION_ERROR — нет файла; 400 BAD_FILE — файл не книга Excel;
  400 HEADER_NOT_FOUND; 404 SHEET_NOT_FOUND; общие 401/403.
- Файл: `server/src/modules/suppliers/suppliers.controller.ts` (previewSuppliers).

### POST /api/suppliers/import/commit
Запись разобранных строк в справочник.
- Auth: ADMIN.
- Body: `{ sheet, rows }` — до 1000 строк. Строки проверяются целиком, хотя их же
  собрал сервер: между предпросмотром и записью лежит сеть.
- Ответ 201: `{ created, updated, skipped, failed }`.
- Новые заводятся; существующим **дозаполняются только пустые поля**.
  Заполненное не перезаписывается, иначе каждая выгрузка откатывала бы правки,
  сделанные руками, и понять, почему адрес «сам» вернулся к старому, было бы нечем.
- `telegramId` импорт не трогает никогда: в файле его нет.
- Один UUID дважды в одном файле — вторая строка уходит в `failed`.
- Всё одной транзакцией: половина импортированного справочника хуже, чем ничего.
- Ошибки: 400 VALIDATION_ERROR — ни одна строка не готова к записи; общие 401/403.
- Аудит: SUPPLIERS_IMPORTED — счётчики и название листа, без самих строк.
- Файл: `server/src/modules/suppliers/suppliers.controller.ts` (commitSuppliers).

### PATCH /api/suppliers/:id
Правка карточки руками — прежде всего Telegram ID, которого в выгрузке нет.
- Auth: ADMIN.
- Body: любое подмножество `{ name, address, phone, telegramId, isActive }`.
  Пустое тело отклоняется. `telegramId` — только цифры, у группы с минусом
  (`TELEGRAM_CHAT_ID_PATTERN`), `null` — снять. Ник `@name` не принимается:
  бот по нему не отправит. Правится из «Настройки» → «Поставщики в Telegram».
- `externalId` сменить нельзя: это ключ сверки с МойСкладом, и подмена склеила бы
  двух поставщиков при следующем импорте.
- Удаления нет, только `isActive: false`: на поставщика будут ссылаться закупки.
- Ответ 200: `SupplierDto`.
- Ошибки: 400 VALIDATION_ERROR; 404 NOT_FOUND; общие 401/403.
- Аудит: SUPPLIER_UPDATED — before/after карточки.
- Файл: `server/src/modules/suppliers/suppliers.controller.ts` (patchSupplier).

## Импорт товаров из МойСклада

Заполняет то, чего нет в Kaspi: закупочную цену с валютой, поставщика и сроки
предзаказа по складам. **Новых товаров не заводит** — каталог наполняется
из кабинета Kaspi, здесь только дополняются уже сохранённые артикулы.

Артикул ищется по колонке **«Код»**, а не «Артикул»: в проверенной выгрузке
«Артикул» заполнен у 40 строк из 1799, а «Код» — у всех 1785 товаров, и формат
совпадает с нашими артикулами (`zkz090`, `KN100`, `XRW112`). Сравнение без учёта
регистра: в файле `zkz090`, у нас `ZKZ090`.

### POST /api/products/moysklad/preview
Разбор выгрузки номенклатуры. **В базу не пишет.**
- Auth: ADMIN.
- Тело: файл `.xlsx` двоичным потоком. Лимит 25 МБ.
- Query: `sheet` — название листа. Без него только список листов.
- Ответ 200: `MoyskladImportPreview` — `sheets`, `sheet`, `rows`, `total`,
  `filtered`, `duplicated`, `notFound`, `ready`, `unknownSuppliers`, `ignoredColumns`.
- Колонки по заголовкам: `Тип`, `Код`, `Наименование`, `Закупочная цена`,
  `Валюта (Закупочная цена)`, `Поставщик`, плюс пять колонок «Доп. поле: Склад N».
- Строки типов «Услуга», «Комплект», «Товар.Карточка контента» отбрасываются
  в `filtered`: у них нет ни закупки, ни склада.
- **Код, встречающийся в файле дважды, не записывается.** В проверенной выгрузке
  таких 23 пары — картина и постер с одним кодом, у одной строки цена
  и поставщик, у второй нули. Записать обе — вторая затрёт первую. Правило
  «берём ту, где цена не ноль» работало бы на сегодняшнем файле и сломалось бы
  на первом дубле с двумя ценами.
- Цены лежат **строками с запятой** (`"4645,38"`). Ноль означает «цена
  не указана»: товара, который достаётся даром, не бывает, а записанный ноль
  в отчёте по марже выглядел бы настоящей закупкой.
- Валюта сопоставляется по списку (`тенге` → `KZT`, `руб` → `RUB`). Незнакомое
  название — замечание, а не молчаливое превращение в тенге.
- Склады: колонка → код склада задан явно в `MOYSKLAD_WAREHOUSE_COLUMNS`
  (`PP3`, `PP6`, `PP27`, `PP4`). Подбор по подстроке однажды связал бы не тот
  склад. «Склад Алматы» в раскладке нет: такого склада у нас нет, а колонка
  пуста во всей выгрузке — она уходит в `ignoredColumns`.
- **Пустая ячейка склада означает «этот склад товар не возит»** — строка остатка
  для него не создаётся. Ноль означал бы «есть в наличии», это другое.
- Срок предзаказа больше `MOYSKLAD_MAX_PREORDER_DAYS` (180) не записывается:
  срок уходит на площадку, и трёхзначное число там означало бы год доставки.
- Поставщик ищется по названию в справочнике. Не нашёлся — замечание, строка
  всё равно поедет, поле останется пустым. Сводка по таким — в `unknownSuppliers`
  со счётчиком товаров.
- Ошибки: 400 VALIDATION_ERROR; 400 BAD_FILE; 400 HEADER_NOT_FOUND;
  404 SHEET_NOT_FOUND; общие 401/403.
- Файл: `server/src/modules/products/moysklad.controller.ts` (previewMoysklad).

### POST /api/products/moysklad/commit
Запись закупки, поставщика и сроков предзаказа в найденные артикулы.
- Auth: ADMIN.
- Body: `{ sheet, rows }` — до 5000 строк.
- Ответ 201: `{ updated, pricesSet, suppliersSet, stocksSet, failed }`.
- **Пустое в файле ничего не затирает:** нет цены — остаётся наша, нет
  поставщика — остаётся наш. Иначе каждая выгрузка откатывала бы правки руками.
- Строки складов **дозаписываются, а не пересобираются**: склад, которого
  в файле нет, у нас мог появиться руками. Трогается только `preOrderDays` —
  `quantity` ведётся отдельно и файлом МойСклада не описывается.
- Заодно проставляет `Warehouse.name` тем складам, у которых название пустое:
  выгрузка Kaspi названий не содержит, а в заголовках колонок МойСклада они
  написаны словами. Заполненное руками название не трогается.
- Пишется пачками по 100 в отдельных транзакциях, а не всё одной: полторы тысячи
  артикулов с четырьмя складами — это тысячи операторов. Обрыв на середине
  не страшен: импорт обновляет записи, а не создаёт, поэтому повтор просто
  дозапишет остальное и дублей не создаст.
- Ошибки: 400 VALIDATION_ERROR — ни одна строка не готова; общие 401/403.
- Аудит: MOYSKLAD_PRODUCTS_IMPORTED — счётчики и название листа одной записью
  журнала. Плюс история каждого товара в транзакции пачки: закупка, валюта,
  поставщик (названием) — одной записью, срок предзаказа — отдельной записью
  на склад, код склада в `context.warehouse`. Источник `IMPORT`.
- Файл: `server/src/modules/products/moysklad.controller.ts` (commitMoysklad).

### POST /api/products/moysklad/stock/preview
Разбор отчёта «Остатки» МойСклада для одного склада. **В базу не пишет.**
- Auth: ADMIN.
- Query: `warehouseId` (UUID, обязателен) — склад, в который пойдёт запись;
  `sheet` (необязателен) — без него в ответе только список листов.
- Body: файл `.xlsx` двоичным телом, до 25 МБ.
- Ответ 200: `StockImportPreview` — `{ sheets, sheet, warehouse: { id, code, name },
  stockAt, rows, total, groups, duplicated, invalid, notFound, ready, toZero }`.
- **Склада в отчёте нет** — ни колонкой, ни строкой: МойСклад строит отчёт на один
  склад. Поэтому склад выбирает человек, название файла роли не играет.
- Заголовок ищется в первых 20 строках (в проверенном файле — восьмая): над ним
  шапка отчёта. Колонки по заголовкам: `Код`, `Наименование`, `Остаток` —
  обязательны; `Резерв`, `Ожидание`, `Доступно`, `Себестоимость`, `Дней на складе`.
- `stockAt` — из шапки «на момент:», читается как время Астаны (UTC+5).
  Не нашёлся — null, при записи возьмётся время записи.
- Строки-папки (заполнен только «Код»: «Диваны/Мадрид 310») пропускаются
  в `groups`. Строка «Итого:» закрывает таблицу.
- **Пустая ячейка количества — 0, отрицательное — как есть** (решение пользователя):
  отрицательный остаток — это продажа без посадки. Дробное или не число — строка
  `invalid`, не записывается.
- «Доступно» не записывается, но сверяется с Остаток − Резерв + Ожидание;
  расхождение — замечание, строку не блокирует.
- Себестоимость: ноль и пусто — `null`, прежняя не затирается. МойСклад пишет
  ноль, когда на складе пусто.
- `toZero` — товары, у которых на этом складе остаток, резерв или ожидание
  не ноль, а в отчёте их кода нет. Пустой остаток (`null`) сюда не попадает:
  «не указан» — не то же самое, что «есть».
- Задвоенный код — как в выгрузке товаров, строка пропускается; такой товар
  в `toZero` не попадает: в отчёте он есть.
- Старый `.xls` → 400 `XLS_NOT_SUPPORTED` с подсказкой пересохранить.
- Ошибки: 400 VALIDATION_ERROR; 400 BAD_FILE; 400 XLS_NOT_SUPPORTED;
  400 HEADER_NOT_FOUND; 404 NOT_FOUND — склад; 404 SHEET_NOT_FOUND; общие 401/403.
- Файл: `server/src/modules/products/moysklad.controller.ts` (previewStock).

### POST /api/products/moysklad/stock/commit
Запись остатков в выбранный склад и обнуление того, чего в отчёте нет.
- Auth: ADMIN.
- Body: `{ sheet, warehouseId, stockAt, rows, zeroVariantIds }` — строки и список
  на обнуление ровно из предпросмотра; до 5000 каждого.
- Ответ 201: `{ updated, zeroed, costsSet, failed }`.
- Остаток, резерв и ожидание **перезаписываются** — отчёт это снимок склада.
  `stockAt` пишется в строку склада, `receivedAt` = момент отчёта − дней на складе
  (у пустого склада — null). Срок предзаказа не трогается.
- Себестоимость пишется в `Variant.costPrice` только непустая.
- **Обнуление:** список приходит от клиента — ровно то, что человек видел. Сервер
  его не вычисляет заново, но отбрасывает товары, чей код в отчёте есть: обнулить
  товар с остатком в файле — худшая ошибка импорта. Обнуляются остаток, резерв
  и ожидание, `receivedAt` сбрасывается. Строка, которую успели обнулить после
  предпросмотра, пропускается.
- Пачки по 100 в отдельных транзакциях, как у импорта товаров. Повтор безопасен:
  снимок перезаписывается тем же снимком.
- Аудит: MOYSKLAD_STOCK_IMPORTED — счётчики, лист и момент отчёта одной записью
  журнала (`entityType: Warehouse`). Плюс история каждого товара в транзакции:
  остаток, резерв, ожидание, себестоимость; склад в `context.warehouse`,
  у обнулённых — `context.note`. Источник `IMPORT`.
- Ошибки: 400 VALIDATION_ERROR — неверное тело или записывать нечего;
  404 NOT_FOUND — склад; общие 401/403.
- Файл: `server/src/modules/products/moysklad.controller.ts` (commitStock).

## Dictionaries

Четыре пополняемых списка офлайн-точки в одной таблице: «Откуда пришёл клиент»,
«Статус доставки», «Откуда поехал товар», «Способ оплаты». Различаются полем
`kind` из закрытого перечисления — произвольный вид списка завести нельзя.

Чтение — любому вошедшему: значения нужны в форме заказа и в фильтрах. Запись —
ADMIN и MANAGER: список пополняется по ходу работы, гонять админа ради нового
способа оплаты незачем, но и продавцу плодить строки в общем справочнике не стоит.

**Удаления нет.** На значении висят заказы; «закрыть» — `PATCH` с `isActive: false`.

### GET /api/dictionaries
Значения списков.
- Auth: любой вошедший.
- Query: `kind` — необязательный. Без него отдаются все четыре списка разом:
  в форме заказа нужны сразу все, а строк там несколько десятков.
- Ответ 200: `{ items: DictionaryItemDto[] }` — `id`, `kind`, `name`, `isActive`,
  `sortOrder`, `ordersCount`.
- Порядок: вид, затем `sortOrder`, затем название.
- Закрытые значения тоже отдаются — они нужны в фильтрах и в отчётах
  за прошлые периоды, где на них ещё висят заказы.
- Ошибки: 400 VALIDATION_ERROR — неизвестный `kind`; общие 401/403.
- Файл: `server/src/modules/dictionaries/dictionaries.controller.ts` (getDictionaries).

### POST /api/dictionaries
Новое значение списка.
- Auth: ADMIN или MANAGER.
- Body: `{ kind, name }` — название 1–120 символов после trim. Другие поля запрещены.
- Ответ 201: `DictionaryItemDto`.
- Порядок (`sortOrder`) ставится следующим в своём списке, под Serializable
  с повтором: без изоляции два одновременных добавления встали бы на одно место.
- Ошибки: 400 VALIDATION_ERROR; 409 CONFLICT — название занято внутри этого
  списка (без учёта регистра, включая закрытые значения); общие 401/403.
- Аудит: DICTIONARY_ITEM_CREATED.
- Файл: `server/src/modules/dictionaries/dictionaries.controller.ts` (postDictionaryItem).

### PATCH /api/dictionaries/:id
Переименование и закрытие/открытие.
- Auth: ADMIN или MANAGER.
- Body: `{ name?, isActive? }`, хотя бы одно поле.
- **Вид списка не меняется:** это был бы перенос значения в другой справочник
  вместе со всеми заказами, которые на нём висят.
- Ответ 200: `DictionaryItemDto` после изменения.
- Ошибки: 400 VALIDATION_ERROR; 404 NOT_FOUND; 409 CONFLICT; общие 401/403.
- Аудит: DICTIONARY_ITEM_RENAMED и/или DICTIONARY_ITEM_CLOSED / _REOPENED
  отдельными записями.
- Файл: `server/src/modules/dictionaries/dictionaries.controller.ts` (patchDictionaryItem).

> «Ошибочный ввод» в списке статусов доставки — особое значение: удалять заказы
> может только админ, поэтому ошибка продавца помечается им и выпадает
> из статистики. Переименуете его в базе — правило перестанет срабатывать.

## Sales Points

Справочник происхождения заказов: и площадки, и офлайн-точки в одной таблице.
Чтение открыто любому вошедшему — список нужен в фильтре реестра и в выпадашке
ввода заказа, секрета в названиях нет. Запись только ADMIN: точка продаж —
разрез всей статистики.

**Удаления нет.** На точке висят заказы; «закрыть» — это `PATCH` с
`isActive: false`. Закрытая точка исчезает из выпадашки ввода, но остаётся
в фильтрах и отчётах за прошлые периоды.

### GET /api/sales-points
Справочник целиком, без пагинации.
- Auth: любой вошедший.
- Ответ 200: `{ items: SalesPointDto[] }` — `id`, `code`, `name`, `type`,
  `isActive`, `sortOrder`, `ordersCount`.
- Порядок: `sortOrder`, затем название. Не алфавит: «Абая» встала бы выше Kaspi,
  хотя открывают чаще Kaspi.
- Закрытые точки тоже отдаются — они нужны в фильтрах.
- `ordersCount` объясняет, почему точку нельзя удалить.
- Файл: `server/src/modules/sales-points/sales-points.controller.ts` (getSalesPoints).

### POST /api/sales-points
Создание офлайн-точки.
- Auth: ADMIN.
- Body: `{ name }` — 1–80 символов после trim. Другие поля запрещены.
- **Ни тип, ни код не принимаются.** Тип через API всегда `OFFLINE`, код генерит
  сервер (`OFF-1`, `OFF-2`). Если позволить прислать код, однажды придёт `KASPI` —
  и синхронизация начнёт писать заказы площадки в чужую строку.
- Ответ 201: `SalesPointDto`.
- Запись идёт под Serializable с повтором: номер кода вычисляется чтением
  максимума, и без изоляции два одновременных создания взяли бы один `OFF-3`.
- Ошибки: 400 VALIDATION_ERROR; 409 CONFLICT — название занято (без учёта
  регистра, включая закрытые точки); общие 401/403.
- Аудит: SALES_POINT_CREATED.
- Файл: `server/src/modules/sales-points/sales-points.controller.ts` (postSalesPoint).

### PATCH /api/sales-points/:id
Переименование и закрытие/открытие.
- Auth: ADMIN.
- Параметры: `id` — uuid точки.
- Body: `{ name?, isActive? }`, хотя бы одно поле. Другие запрещены.
- **Кода и типа здесь нет вовсе:** сменить их значит превратить точку в другую,
  утащив за собой все её заказы. Название менять можно у любой точки, включая
  системные: синхронизация ищет Kaspi по коду.
- Ответ 200: `SalesPointDto` после изменения.
- Ошибки: 400 VALIDATION_ERROR; 404 NOT_FOUND; 409 CONFLICT — название занято;
  общие 401/403.
- Аудит: SALES_POINT_RENAMED и/или SALES_POINT_CLOSED / SALES_POINT_REOPENED —
  разные действия пишутся отдельными записями, их и искать будут по отдельности.
- Файл: `server/src/modules/sales-points/sales-points.controller.ts` (patchSalesPoint).

## Kaspi Catalog

### POST /api/kaspi-catalog/preview

Разбор выгрузок каталога из кабинета Kaspi. **В базу ничего не пишет** — только
показывает, что получилось.

- Auth: требуется, роль `ADMIN`
- Тело: `{ "active": "<xml>", "archive": "<xml>" }` — содержимое файлов текстом,
  оба поля необязательные, но хотя бы одно должно быть (тип `KaspiCatalogPreviewRequest`)
- Ответ 200: `{ "offers": [...], "summary": {...}, "parsedAt": "..." }` (тип `KaspiCatalogPreview`)
- Ошибки:
  - `400 VALIDATION_ERROR` — файл не XML или в нём нет узла `kaspi_catalog → offers`
  - `409 CONFLICT` — не прислали ни одного файла
  - `403 FORBIDDEN` — роль ниже `ADMIN`
- Файл: `server/src/modules/kaspi-catalog/kaspi-catalog.routes.ts`

> Лимит тела на этом маршруте поднят до 20 МБ: две выгрузки весят около 650 КБ,
> а общий лимит приложения намеренно оставлен в 1 МБ.

> Файлы приходят текстом в JSON, а не multipart: ради двух текстовых файлов
> тащить разбор multipart на сервер незачем.

> Содержимое файлов в журнал действий не попадает — только итоги разбора.

### POST /api/kaspi-catalog/fetch

Обход каталога прямо в кабинете Kaspi (`mc.shop.kaspi.kz/bff/offer-view/list`):
товары в продаже и снятые с продажи за один вызов. Товары возвращаются сырыми,
как их отдал кабинет, — состав нашего DTO ещё не определён. **В базу не пишет.**

- Auth: требуется, роль `ADMIN`
- Тело: `{ "cookie": "...", "remember": false }` либо `{ "useSession": true }`
  (тип `KaspiCabinetFetchRequest`), все поля необязательные; пустая `cookie` —
  берётся запомненная. `useSession: true` — сессия входа по email и паролю через
  `withCabinetSession()`: жива — сразу, нет — вход и обход заново, один раз.
  Вместе с `cookie` или `remember` — 400
- Кабинет не пустил на первой странице — ошибка 401, а не пустой результат:
  по ней `withCabinetSession()` входит заново. Обрыв дальше первой страницы —
  частичный результат со `stoppedAtPage`, как раньше
- Редиректы не проходятся (`cabinetGetJson`): редирект на вход — это 401
- Ответ 200: `{ "total", "onSale", "offSale", "expected", "withProblems", "pages", "stoppedAtPage", "stoppedReason", "hasStoredCookie", "warehouses", "sample", "offers" }`
  (тип `KaspiCabinetFetchResponse`). В `offers` — разобранные товары (`CabinetOffer`),
  не сырой ответ площадки; в `warehouses` — сводка складов за обход
  (`CabinetWarehouse`: `code`, `storeId`, `cityId`, `offersCount`, `totalStock`);
  в `sample` — три первых товара парами `{ raw, parsed }` (`CabinetSample`)
- Ошибки:
  - `400 VALIDATION_ERROR` — нет ни присланной, ни запомненной куки; не задан `KASPI_MERCHANT_ID`;
    `useSession` вместе с кукой
  - `401 KASPI_UNAUTHORIZED` — кабинет не пустил: кука протухла или скопирована не целиком
    (в режиме сессии — не пустил и после повторного входа)
  - режим сессии: `409 KASPI_CABINET_NOT_CONFIGURED`, `409 KASPI_LOGIN_*`,
    `429 KASPI_LOGIN_BLOCKED`, `502 KASPI_LOGIN_ERROR` — см. раздел Kaspi Cabinet
- Журнал: KASPI_CABINET_FETCH, в `after.source` — `cookie` или `session`
  - `502 KASPI_UNAVAILABLE` — кабинет не ответил или вернул ошибку
  - `502 KASPI_BAD_RESPONSE` — пришёл не JSON или не список: формат изменился
  - `403 FORBIDDEN` — роль ниже `ADMIN`
- Файл: `server/src/modules/kaspi-catalog/kaspi-catalog.routes.ts`

> **Кука нигде не сохраняется на диск.** Только в памяти процесса и только при
> `remember: true`. В журнал действий, логи и ответ она не попадает: это по сути
> пароль от кабинета. Перезапустили сервер — вставляется заново.

> **Обрыв не теряет работу.** Кука протухла на середине — сервер возвращает то,
> что успел, и номер страницы в `stoppedAtPage`. Прогресс между вызовами не
> хранится: продолжение с места обрыва — задача синхронизации, её пока нет.

> **Защита от неверного ответа.** При протухшей сессии кабинет отвечает HTML
> страницы входа с кодом 200. Без проверки на массив это выглядело бы как пустой
> каталог, поэтому «не JSON» и «не список» — ошибки, а не ноль товаров.

> **Сырой ответ наружу не отдаётся — кроме образца.** В нём около трёхсот
> записей цен по городам на каждый товар, а нужна из них одна: ответ на 1335
> товаров весил бы мегабайты. Маппинг — `toCabinetOffer()` в `kaspi-cabinet.mapper.ts`.
> Исключение — поле `sample`: первые три товара сырыми и разобранными, чтобы
> сверять маппинг в консоли браузера (`SAMPLE_SIZE` в `kaspi-cabinet.service.ts`).
> Печатает их `logCabinetResponse()` в `use-kaspi-cabinet.ts` — свёрнутыми
> группами, рядом со списком всех разобранных товаров и таблицей складов.
> Это инструмент этапа 2: когда модели заведены, образец и вывод в консоль уходят.

> **Спорные места помечаются, а не разбираются наугад.** Цена различается по
> городам, в `familyId` несколько чисел, нет артикула — всё это попадает
> в `problems` у товара и в счётчик `withProblems`. Молча выбранное значение
> всплыло бы ошибкой в цене, и найти его было бы негде.

> **Склады собираются за весь обход.** Источник — `availabilities[].storeId`
> (`6871008_PP3`), код склада берётся из его хвоста; поле `points` для справочника
> не годится — там только `PP3`, без `storeId`. Сводка складывается
> в `collectCabinetWarehouses()` (`kaspi-cabinet.warehouses.ts`) и годится для
> `POST /api/warehouses/import-kaspi` как есть.

> **`cityId` в ответе кабинета всегда `null`.** Кода города (КАТО) у склада
> в JSON нет: `allCityPrices` — это города, где показывается цена покупателю,
> а не города складов. При импорте пустой город понимается как «неизвестно»:
> у складов, уже заведённых из выгрузки, он сохраняется, у новых остаётся пустым.

> **Два обхода за вызов:** `a=true` (в продаже) и `a=false` (архив). Статус
> товара определяется тем, в каком обходе он пришёл, — как и с файлами
> `ACTIVE.xml` / `ARCHIVE.xml`.

> **Полнота проверяется.** Кабинет присылает `total` на каждой странице; сумма
> по обоим режимам попадает в `expected`. Не сошлось с `total` — значит обход
> что-то потерял, и это видно на странице, а не только в логах.

> Страницы берутся по 100, между обращениями пауза 500 мс: частые запросы
> приводят к блокировке по IP. Обход останавливается, если страница не принесла
> ни одного нового `offerId` — значит кабинет перестал листать. Лишнее обращение
> за пустой страницей не делается: как только получено обещанное количество,
> режим закрывается.

## Kaspi Cabinet — доступ в кабинет по email и паролю (30.09.2026)

Настройка и проверка входа. Самого входа как эндпоинта нет: входит сервер,
когда кабинет кому-то понадобился, через `withCabinetSession()`
(`server/src/modules/kaspi-cabinet/cabinet-session.service.ts`). Жива
сохранённая сессия — запрос идёт без входа; кабинет ответил
`KASPI_UNAUTHORIZED` — один вход и один повтор. Схема — «Как заходим»
в [kaspi-api-integration.md](kaspi-api-integration.md).

Все три — только ADMIN. Файл: `server/src/modules/kaspi-cabinet/kaspi-cabinet.controller.ts`.

### GET /api/kaspi-cabinet/account
Email и состояние входа. Пароля в ответе нет ни в каком виде.
- Auth: ADMIN
- Ответ 200: `KaspiCabinetAccountDto` — `configured`, `email`, `hasSession`,
  `status` (`KASPI_LOGIN_STATUSES` или null — входа не было), `lastError`,
  `lastAttemptAt`, `blockedUntil` (только если пауза ещё идёт), `updatedAt`.
  Данных нет — `configured: false`, остальное пусто.
- Ошибки: общие 401/403.

### PUT /api/kaspi-cabinet/account
Сохранить email и пароль. **Входа здесь нет** — только хранение.
- Auth: ADMIN
- Тело: `{ email: string (email, ≤254), password: string (1–128, не обрезается) }`
- Ответ 200: `KaspiCabinetAccountDto`.
- Что происходит: пароль шифруется AES-256-GCM (`KASPI_SECRETS_KEY`); сохранённая
  сессия и итог прошлого входа стираются — следующая проверка войдёт заново
  и проверит именно новый пароль. Сменили email — снимается и пауза Kaspi.
- Ошибки: 400 VALIDATION_ERROR; 503 SECRETS_KEY_MISSING — нет ключа в `.env`,
  ничего не записано; общие 401/403.
- Журнал: KASPI_CABINET_ACCOUNT_SAVED — email до и после, без пароля.

### POST /api/kaspi-cabinet/check
Проверка подключения — тот же путь, что у любого потребителя кабинета.
- Auth: ADMIN
- Тело: нет.
- Порядок: есть сессия — одна страница товаров (`offer-view/list`, `l=1`);
  ответил JSON — готово, входа нет. Иначе вход: `oauth2/authorization/1` →
  `POST idmc…/api/p/login` → `redirectUrl` → снова страница товаров.
- Ответ 200: `KaspiCabinetCheckResponse` — `ok`, `status`, `message`, `loggedIn`
  (false — сессия была жива), `trace` (шаги: адрес, код, переход, **имена** кук,
  JSON-тело, заметка о HTML), `account`. Неудачный вход — тоже 200 с `ok: false`:
  трасса нужна именно тогда.
- Маскировка трассы: `code`, `state`, токены в адресах и `_p`, `password`,
  токены в телах — `***`; значения кук не отдаются. Тело запроса входа в трассу
  не пишется вовсе.
- Ограничения: один вход на процесс (параллельные ждут тот же); пауза Kaspi
  (`breakTimeSeconds`) соблюдается — до её конца вход не пытается.
- Ошибки: 400 VALIDATION_ERROR — не задан `KASPI_MERCHANT_ID`;
  409 KASPI_CABINET_NOT_CONFIGURED — данных для входа нет; 500 SECRET_UNREADABLE —
  сменился `KASPI_SECRETS_KEY`; 503 SECRETS_KEY_MISSING; общие 401/403.
- Журнал: KASPI_CABINET_CHECKED — итог и `loggedIn`, без трассы.

**Ошибки `withCabinetSession()` для будущих потребителей:** 409
`KASPI_LOGIN_CODE_REQUIRED` / `KASPI_LOGIN_CREDENTIALS_INVALID` /
`KASPI_LOGIN_MERCHANT_CHOICE_REQUIRED` — после таких итогов сервер сам больше
не входит, пока не сохранят данные или не нажмут «Проверить подключение»;
429 `KASPI_LOGIN_BLOCKED`; 502 `KASPI_LOGIN_ERROR`. Сама функция входа наружу
не выставлена — её вызывают сервисы.

- Ответ 200: обновлённый `WorkerDto`.
- Ошибки: 400 VALIDATION_ERROR — значение не из списка; оповещения без Telegram ID;

- Журнал: WORKER_SETTINGS_UPDATED (before/after) и событие воркера
  SETTINGS_CHANGED «кто: что было → что стало».

## Warehouses

Справочник складов (точек выдачи). Список — любому вошедшему (фильтр и колонки
каталога), импорт — только `ADMIN`.

### GET /api/warehouses

Справочник складов, отсортирован по коду.

- Auth: `can()` — любой вошедший
- Параметры: нет
- Ответ 200: `{ "items": WarehouseDto[] }` — `id`, `code`, `kaspiStoreId`,
  `kaspiCityId`, `name`, `isActive`, `kaspiOffersCount`, `kaspiTotalStock`,
  `kaspiStatsAt`, `telegramChatId`
- Ошибки: `401 UNAUTHORIZED`, `403 FORBIDDEN`
- Файл: `server/src/modules/warehouses/warehouses.routes.ts`

### POST /api/warehouses/import-kaspi

Заводит склады из предпросмотра выгрузки Kaspi. Операция повторяемая:
сверка идёт по `code`, дубликаты не создаются.

- Auth: требуется, роль `ADMIN`
- Тело: `{ "warehouses": [{ "code": "PP3", "storeId": "6871008_PP3", "cityId": "710000000" | null }] }`
  (тип `SaveWarehousesRequest`), от 1 до 500 записей
- Ответ 200: `{ "created": 33, "updated": 0, "unchanged": 0 }` (тип `SaveWarehousesResponse`)
- Ошибки:
  - `400 VALIDATION_ERROR` — код не вида `PP3`, `storeId` не вида `6871008_PP3`,
    `cityId` не число, пустой список или больше 500 записей
  - `409 CONFLICT` — код склада в списке дважды, либо `storeId` уже занят другим кодом
  - `403 FORBIDDEN` — роль ниже `ADMIN`
- Файл: `server/src/modules/warehouses/warehouses.routes.ts`

### PATCH /api/warehouses/:id

Telegram-группа кладовщика склада — «Из наличия в Астане» в настройках.
Туда воркер шлёт заказы в наличии с этого склада ([workers.md](workers.md)).

- Auth: `can([ADMIN])`
- Тело: `{ "telegramChatId": "-100…" | null }` (`UpdateWarehouseRequest`) — цифры,
  у группы с минусом; `null` — снять. Другие поля запрещены
- Ответ 200: `WarehouseDto` (с `telegramChatId`)
- Ошибки: `400 VALIDATION_ERROR`, `404 NOT_FOUND`, общие 401/403
- Журнал: WAREHOUSE_UPDATED — Telegram ID до и после
- Файл: `server/src/modules/warehouses/warehouses.controller.ts` (patchWarehouse)

> Приходит разобранный список, а не XML заново: сохраняется ровно то, что человек
> увидел на экране. Данные всё равно от клиента, поэтому каждое поле проверяется
> по шаблону — эндпоинт админский, но «свой пользователь» валидацию не заменяет.

> **Что выгрузка не перезаписывает:** `name` (наше название точки) и уже
> заполненный `kaspiCityId`. Пустой город в файле означает «неизвестно», а не
> «сотри». Иначе повторная загрузка стёрла бы всё, что вписали руками.

> **Счётчики сохраняются снимком.** `offersCount` и `totalStock` из запроса
> ложатся в `kaspiOffersCount`, `kaspiTotalStock` и датируются `kaspiStatsAt`.
> Они необязательны: в XML-выгрузке остатка по складу нет. Это состояние на
> момент загрузки, а не настройка склада, поэтому пишутся всегда — но
> изменением справочника не считаются и в счётчик `updated` не попадают.

> Склады, пропавшие из новой выгрузки, **не удаляются**: на них ссылаются прошлые
> заказы. Закрытую точку отключают флагом `isActive`.

> Вся запись идёт одной транзакцией — при сбое на середине справочник не остаётся
> заполненным наполовину.

и себестоимость в нём срезаются по ролям. Перенос в папку — `ADMIN`, `MANAGER`.

Артикулы, которые уже лежат в базе. По ним страница синхронизации прячет из

### POST /api/products/import-kaspi

Заводит в каталоге товары, загруженные из кабинета. Создаёт `Product`, `Variant`,
`Listing(KASPI)` и остатки по складам одной вложенной вставкой на товар.

- Auth: требуется, роль `ADMIN`
- Тело: `{ "offers": CabinetOffer[] }` (тип `ImportKaspiProductsRequest`),
  не больше 5000 позиций
- Ответ 200: `{ "created", "skipped", "failed": [{ "sku", "reason" }], "missingWarehouses": string[] }`
  (тип `ImportKaspiProductsResponse`)
- Ошибки:
  - `400 VALIDATION_ERROR` — пустой список, больше 5000 позиций, товар без
    артикула, код склада не вида `PP3`, отрицательная цена
  - `403 FORBIDDEN` — роль ниже `ADMIN`
- Файл: `server/src/modules/products/products.routes.ts`

> **Создаём только новое.** Товар, который уже есть по артикулу, пропускается
> целиком: у него может быть наша категория, ткань, закупочная цена и цена сайта.
> Обновление полей кабинета будет отдельной операцией с показом расхождений,
> а не молчаливой перезаписью.

> **Сохранение — отдельное нажатие.** Загрузка каталога в базу не пишет никогда:
> человек сначала смотрит таблицу, и только потом сохраняет то, что увидел.

> **Одна плохая запись не отменяет импорт.** Товар, который не сохранился,
> попадает в `failed` с причиной; остальные заводятся. Заливать полторы тысячи
> позиций заново из-за одной строки дороже, чем показать список.

> **Склад, которого нет в справочнике, не выдумывается.** Остатки по нему
> не записываются, код попадает в `missingWarehouses`: сначала «Сохранить
> склады», потом товары.

> **Дубли артикулов в запросе отбрасываются.** В кабинете один артикул бывает
> и в продаже, и в архиве — без этого вставка упала бы на уникальном индексе
> посреди импорта.

> **Каталог присылается пачками по 100 товаров.** Целиком это около пяти
> мегабайт — картинки и история изменений у каждой позиции, — а общий лимит
> тела запроса намеренно оставлен в 1 МБ. Свой лимит на маршруте не помог бы:
> `express.json` приложения разбирает тело раньше маршрутных мидлваров.
> Побочный выигрыш: виден прогресс, и сбой на середине не отменяет сохранённое.

## Права и роли (30.09.2026)

Роли — `USER_ROLES` в `shared/src/constants/roles.ts`, общие для сервера
и фронта: `ADMIN`, `MANAGER`, `SELLER`, `VIEWER`. Должность сотрудника
(«Дизайнер») — просто подпись, доступ решает только роль.

**Сервер** — `can(roles?)` в `server/src/middlewares/require-auth.ts`,
у **каждого маршрута явно**:

```ts
const { ADMIN, MANAGER } = USER_ROLES;

router.use(can());                                   // весь модуль — только вошедшим
router.get('/', can(), getList);                     // любой вошедший
router.post('/', can([ADMIN, MANAGER]), create);     // только эти роли
```

- `can()` без ролей — любой вошедший; со списком — только эти роли.
- `can()` сам проверяет вход. `router.use(can())` в начале модуля — страховка:
  маршрут, у которого забыли `can()`, всё равно не станет публичным. Повторный
  поход в базу за сессией при этом не делается.
- Проверка — функция `hasRole(role, roles)` из shared, та же, что на фронте.
- Нет сессии — 401 UNAUTHORIZED, нет роли — 403 FORBIDDEN.

**Поля по ролям.** Закупка (`purchasePrice`, `purchaseCurrency`) и себестоимость
(`costPrice`) в `GET /api/products/variants` приходят `null`, если роли нет
в `CATALOG_PURCHASE_ROLES` / `CATALOG_COST_ROLES` (`shared/src/constants/catalog.ts`).
Сортировка по закупке без доступа — 403: порядок строк выдал бы её саму.
Фронт прячет эти столбцы по тем же константам.

**Фронт** — `useCan()` и `RoleGuard`, та же проверка. Это удобство, а не защита:
спрятанная кнопка ничего не закрывает, закрывает `can()` на сервере. Поэтому
роли у кнопки и у маршрута должны совпадать.

**Новая роль:** `USER_ROLES` и `USER_ROLE_LABELS` в shared + значение в
`enum UserRole` в `schema.prisma` + миграция. Проверка роли при создании
сотрудника берёт весь `USER_ROLES` и правки не требует.

| Импорты, МойСклад, `kaspi-catalog`, `products/skus`, `products/import-kaspi`, `warehouses/import-kaspi` | ADMIN |
| Аккаунты (`/api/users`), журнал (`/api/audit`), кабинет Kaspi (`/api/kaspi-cabinet`), воркеры (`/api/workers`) | ADMIN |

## Дерево категорий и серверный каталог (18.09.2026)

Дерево — любому вошедшему, создание и правка папок — `ADMIN`, `MANAGER`. Общие
ошибки: 401 UNAUTHORIZED — нет сессии, 403 FORBIDDEN — нет роли. Контракты
находятся в `shared/src/types/catalog.ts`, настройки — в `shared/src/constants/catalog.ts`.

### GET /api/categories
Получить созданные вручную папки. Новые категории ограничены двумя уровнями:
корневая категория → подпапка. Ранее созданные более глубокие узлы не скрываются.
- Auth: `can()` — любой вошедший.
- Параметры: нет.
- Ответ 200: `{ allProducts: { id: null, name: "Все товары" }, items: CategoryTreeNode[] }`.
- Узел: `{ id, name, parentId, children }`. Корневые узлы находятся в items.
- Сортировка соседних папок: sortOrder, name, id по возрастанию.
- «Все товары» — отдельный первый служебный пункт интерфейса, не запись Category;
  доступен и в пустом каталоге. Показывает также товары без папки и снятые с продажи.
- Дерево не зависит от поиска и пагинации товаров. Возвращаются все папки, включая
  неактивные: это внутренний каталог, а не публичная витрина.
- Ошибки: общие 401/403.
- Файл: `server/src/modules/categories/categories.controller.ts` (getCategories).

### POST /api/categories
Создать папку верхнего уровня или подпапку (максимум два уровня).
- Auth: `can([ADMIN, MANAGER])`.
- Body: `{ name: string, parentId?: string | null }`.
- name: 1–150 символов после trim; parentId — UUID существующей папки.
  Отсутствующий parentId или null создаёт корневую папку. Указанный родитель
  обязан быть корневым; создание внутри подпапки возвращает 400 VALIDATION_ERROR.
- Ответ 201: `{ id, name, parentId }` (CategoryDto).
- Ошибки: 400 VALIDATION_ERROR — неверное тело либо зарезервированное имя
  «Все товары» без учёта регистра; 404 NOT_FOUND — родителя нет;
  409 CONFLICT — имя уже занято у этого родителя без учёта регистра либо
  исчерпаны повторные попытки после конкурентного изменения; общие 401/403.
- Одинаковые имена в разных родителях разрешены. Проверка корневых дубликатов
  защищена Serializable-транзакцией (обычный unique допускает NULL-родителей).
- path заполняется от родителя; slug служебный, category-UUID. Само создание
  папки не создаёт Product, не объединяет товары и не переносит их по названию.
- Аудит: CATEGORY_CREATED, новая папка в after.
- Файл: `server/src/modules/categories/categories.controller.ts` (postCategory).

### GET /api/products/variants
Страница артикулов из нашей БД: серверный поиск, папка, фильтры по складам
и поставщикам, сортировка по колонке.
- Auth: `can()` — любой вошедший. Закупка и себестоимость — только ролям из
  `CATALOG_PURCHASE_ROLES` / `CATALOG_COST_ROLES`, остальным `null`
  (`hideCatalogMoney()` в `catalog.mapper.ts`). `sort=purchasePrice` без доступа —
  403 FORBIDDEN.
- Query (все необязательные): page — целое 1–1000000, по умолчанию 1;
  pageSize — только 10/20/50, по умолчанию 20; search — строка до 200 символов
  после trim; categoryId — UUID папки. Пустой categoryId не передавать.
- `warehouseIds` — UUID складов через запятую, до 100. Товары, **назначенные**
  хотя бы на один из них: есть строка `VariantStock`, даже с нулевым остатком.
  В ответе у строки остаются только выбранные склады (`stocks`, а с ними
  `totalStock` и `preOrderDays`).
- `supplierIds` — UUID поставщиков через запятую, до 100; значение `none` —
  «без поставщика». Несколько — ИЛИ.
- `sort` — одна колонка из `CATALOG_SORT_KEYS`: `price` (цена Kaspi со скидкой,
  если есть), `purchasePrice` (по числу, без учёта валюты — решение пользователя),
  `quantity`, `reserved`, `expected` (сумма по складам), `available`
  (Остаток − Резерв + Ожидание по тем же складам), `preOrderDays` (максимум),
  `daysOnStock` (среднее, взвешенное по остатку). При фильтре по складам цифры
  считаются только по выбранным. `order` — `desc` (по умолчанию) или `asc`.
  Пустые значения — в конце в обе стороны; дальше порядок по умолчанию.
- Порядок и id страницы считает параметризованный SQL
  (`server/src/modules/products/catalog.query.ts`): Prisma не сортирует по сумме
  дочерних строк. Колонка и направление — из закрытых словарей по ключу,
  текст запроса в SQL не попадает.
- Ответ 200: `{ items: CatalogRowDto[], total, page, pageSize, totalPages }`.
  Используется существующая форма PaginatedResponse с дополнительным totalPages.
- Одна строка — Variant, поэтому total считает артикулы. Поиск по части строки,
  без учёта регистра: sku, Product.name, kaspiMasterTitle, kaspiTitle (ИЛИ).
  %, _ и обратная косая черта ищутся буквально. Пустой поиск не ограничивает выборку.
- categoryId включает саму папку и все её подпапки; без него — весь каталог.
  Поиск работает внутри выбранной области, а не только внутри полученной страницы.
- Порядок: сначала status (ON_SALE выше OFF_SALE), затем Product.name по алфавиту,
  затем sku. `status: 'asc'` ставит ON_SALE первым потому, что Postgres сортирует
  enum по порядку объявления в схеме — переставите значения в enum, и сортировка
  поедет молча. sku третьим ключом обязателен: у товаров с одинаковым названием
  без него порядок между запросами не определён, и один артикул мог бы попасть
  на две страницы, а другой ни на одну. Сортировка названий зависит от коллации
  базы: при `C` кириллица сортируется по кодам символов, а не по алфавиту.
- Страница вне диапазона приводится к последней существующей; пустой результат:
  items=[], total=0, page=1, totalPages=0. Фронт использует возвращённый page.
- Счётчик и страница читаются в одном снимке RepeatableRead. Между отдельными
  запросами страниц каталог может измениться из-за импорта или переноса.
- Ошибки: 400 VALIDATION_ERROR — неверные параметры (включая неизвестные);
  404 NOT_FOUND — выбранная папка отсутствует; общие 401/403.
- Файл: `server/src/modules/products/catalog.controller.ts` (getCatalog).

Состав CatalogRowDto — всё, что хранится на артикуле. Тип:
`shared/src/types/catalog.ts`, выборка и маппинг: `catalog.mapper.ts`.

| Поле | Смысл |
|---|---|
| variantId, productId | Идентификатор строки и общей карточки товара |
| name, sku, barcode, brand | Наше название, артикул, штрихкод и бренд |
| category | { id, name } либо null |
| imageUrl | Первая пригодная миниатюра по HTTP(S) либо null |
| images | Вся галерея: массив { small, medium, large }, каждое поле может быть null |
| status, productIsActive | Наш статус продажи модификации и активность Product |
| sortOrder, createdAt, updatedAt | Порядок и даты самой модификации |
| fabric | { id, name, code, type } либо null |
| fabricShade | { id, name, code, hex, imageUrl } либо null |
| listings | Массив размещений: id, channel, status, price, discountPrice, discountPercent, externalId, externalSku, externalUrl, publishedAt, lastSyncedAt, syncError |
| stocks | Массив { warehouse: { id, code, name, kaspiStoreId, kaspiCityId, isActive }, quantity, reserved, expected, available, daysOnStock, stockAt, preOrderDays } |
| stocks[].available | Доступно = Остаток − Резерв + Ожидание. Считает сервер, в базе не хранится; null — все три не указаны |
| stocks[].daysOnStock | Дней на складе, два знака. Считается при выдаче от `VariantStock.receivedAt`, поэтому растёт каждый день сам; null — склад пуст или срок неизвестен |
| totalStock, preOrderDays | Сумма остатков и максимальный срок предзаказа по складам |
| purchasePrice, purchaseCurrency | Закупочная цена и её валюта. `null` без роли из `CATALOG_PURCHASE_ROLES` |
| costPrice | Себестоимость единицы, всегда в тенге. `null` без роли из `CATALOG_COST_ROLES` |
| minChannelPrice, maxChannelPrice | Денормализованные минимум и максимум по каналам |
| kaspi | Поля кабинета: masterTitle, title, model, masterSku, offerId, fileId, merchantUid, shopLink, updatedAt, updates |
| delivery | Пять флагов: any, express, local, merchant (кабинет) и site (наш) |
| product | Общее для всех модификаций: slug, description, kaspiFamilyId, createdAt, updatedAt |

**Закупочная цена отдаётся в этом DTO** — тем, кому положено по ролям, остальным
`null`. На страницы магазина этот DTO не отдавать ни в каком виде.

Цены — строки с двумя десятичными знаками в тенге либо null: number на цене
теряет тиын. Даты — ISO-строки. Неизвестный остаток quantity=null не заменяется
нулём, но в totalStock считается нулём — сложить «неизвестно» нечем. Нет Listing
для канала — нет элемента в массиве; это не нулевая цена. `kaspi.updates` —
сырой снимок истории кабинета, формат недокументированный, не разбирается;
пустой массив, если снимка нет. В ответ не входит история изменений — её отдаёт
`GET /api/audit?entityType=Variant&entityId=…`.

### PATCH /api/products/category
Перенести выбранные товары в папку либо снять привязку к папке.
- Auth: `can([ADMIN, MANAGER])`.
- Body: `{ productIds: string[], categoryId: string | null }`.
  От 1 до 100 UUID товаров; повторные ID сворачиваются. categoryId обязателен;
  null снимает категорию. «Все товары» — обзор, а не место хранения.
- Ответ 200: `{ updated: number }` — число фактически изменённых Product.
- Переносятся все модификации каждого Product, включая не отображённые на странице.
  Частичный перенос при неверном ID исключён: вся операция в транзакции.
- Ошибки: 400 VALIDATION_ERROR — неверное тело; 404 NOT_FOUND — папка либо
  хотя бы один товар не найдены; 409 CONFLICT — товары изменены параллельно,
  повторить запрос; общие 401/403.
- Аудит: PRODUCTS_CATEGORY_CHANGED; before — старые категории изменённых товаров,
  after — целевая категория и их ID. Повторный перенос в ту же папку не пишет аудит.
- Файл: `server/src/modules/products/catalog.controller.ts` (patchProductsCategory).

### PATCH /api/categories/order
Задать порядок папок одного уровня.
- Auth: `can([ADMIN, MANAGER])`.
- Body: `{ parentId: string | null, ids: string[] }`. parentId — UUID родителя
  либо null для корневого уровня. ids — **полный** упорядоченный список детей
  этого уровня, 1–200 UUID без повторов. Другие поля запрещены.
- Ответ 200: `{ updated: number }` — сколько папок реально сменило позицию.
- Присылается весь уровень, а не «подними одну вверх»: операция идемпотентна
  и не накапливает расхождений, а при одновременной правке двумя админами
  уровень перезаписывается целиком, а не съезжает на позицию дважды.
- Неполный или посторонний список — 409, а не частичная запись: иначе половина
  уровня получит новый порядок, половина старый, и по данным уже не восстановить,
  что человек имел в виду.
- Пишутся только позиции, которые действительно изменились.
- Порядок хранится в `Category.sortOrder`, дерево читается
  по `sortOrder → name → id`. Поле существовало до этого эндпоинта,
  миграция не нужна. У всех папок по умолчанию 0, то есть до первой
  перестановки уровень идёт по алфавиту.
- Маршрут объявлен строго до `/:id`, иначе «order» попадёт в параметр
  и уедет в переименование.
- Ошибки: 400 VALIDATION_ERROR — неверное тело; 409 CONFLICT — список не совпал
  с фактическим составом уровня либо конфликт параллельного изменения;
  общие 401/403.
- Аудит: CATEGORIES_REORDERED, before/after — порядок id. entityId — родитель
  (пусто для корня). Порядок не изменился — записи нет.
- Файл: `server/src/modules/categories/categories.controller.ts` (patchCategoriesOrder).

### PATCH /api/categories/:id
Переименовать папку без изменения родителя и привязки товаров.
- Auth: `can([ADMIN, MANAGER])`.
- Path: id — UUID существующей Category.
- Body: { name: string }, 1–150 символов после trim. Другие поля запрещены.
- Ответ 200: CategoryDto { id, name, parentId }.
- Ошибки: 400 VALIDATION_ERROR — неверный UUID/название, включая «Все товары»;
  404 NOT_FOUND — папки нет; 409 CONFLICT — дубликат имени внутри родителя
  без учёта регистра либо конфликт параллельного изменения; общие 401/403.
- Уникальность проверяется в Serializable-транзакции, включая корневые папки.
  path и slug при переименовании сохраняются. Повтор того же имени не пишет аудит.
- Аудит: CATEGORY_RENAMED, before/after с прежним и новым названием.
- Файл: server/src/modules/categories/categories.controller.ts (patchCategory).

### DELETE /api/categories/:id
Удалить пустую папку, не удаляя товары и подпапки.
- Auth: `can([ADMIN, MANAGER])`.
- Path: id — UUID существующей Category. Body не требуется.
- Ответ 200: DeleteCategoryResponse { id }.
- Ошибки: 400 VALIDATION_ERROR — неверный UUID; 404 NOT_FOUND — папки нет;
  409 CONFLICT — есть хотя бы один товар (в том числе неактивный) или подпапка;
  общие 401/403. «Все товары» — служебный пункт без UUID, удалить его нельзя.
- В транзакции ReadCommitted запись Category блокируется FOR UPDATE перед
  проверкой товаров и подпапок. Новые FK-ссылки ждут блокировку; удаление не
  должно неявно отвязать конкурентно добавленный товар через onDelete: SetNull.
- Аудит: CATEGORY_DELETED, удалённая папка в before.
- Файл: server/src/modules/categories/categories.controller.ts (removeCategory).
