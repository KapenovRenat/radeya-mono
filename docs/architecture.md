# Архитектура проекта

> Структура папок, слои и решения по стеку. Обновляется при появлении нового модуля,
> слоя или изменении структуры (п.10 в [AGENTS.md](../AGENTS.md)).

---

## 1. Монорепозиторий

Три пакета в одном репозитории, связаны через **npm workspaces** (корневой `package.json`):

```
radeya-mono/
├── server/    # Express + Prisma + PostgreSQL — API
├── front/     # Next.js (App Router) — магазин + dashboard
├── shared/    # Общий код server и front
└── node_modules/   # один на все пакеты (хостинг зависимостей)
```

У каждого пакета свой `package.json` — свой список зависимостей и свои команды.
Физически библиотеки лежат в корневом `node_modules`: одна копия, одинаковые версии.

Внутри `server/` или `front/` папки `node_modules` быть не должно — если появилась,
значит workspaces не отработали.

## 2. server — слои

```
server/
├── prisma/
│   ├── schema.prisma          # модели БД
│   └── migrations/            # SQL-миграции, обязательно в git
├── prisma.config.ts           # конфиг Prisma 7: путь к схеме и DATABASE_URL
├── src/
│   ├── index.ts               # запуск сервера, graceful shutdown, наблюдатель воркеров
│   ├── worker.ts              # отдельный процесс воркеров (docs/workers.md)
│   ├── app.ts                 # сборка Express: мидлвары + маршруты
│   ├── routes.ts              # подключение модулей к /api
│   ├── config/
│   │   └── env.ts             # валидация переменных окружения (zod)
│   ├── db/
│   │   └── client.ts          # единственный экземпляр Prisma Client
│   ├── generated/prisma/      # сгенерированный клиент, в git не попадает
│   ├── lib/                   # переиспользуемое, без привязки к домену
│   │   ├── advisory-lock.ts   # блокировки PostgreSQL между процессами
│   │   ├── errors.ts          # AppError и наследники
│   │   ├── excel.ts           # чтение книги .xlsx и её ячеек
│   │   ├── secret-box.ts      # AES-256-GCM для секретов в базе
│   │   ├── telegram.ts        # отправка в Telegram Bot API
│   │   └── logger.ts
│   ├── middlewares/
│   │   ├── error-handler.ts   # ставится последним
│   │   ├── not-found.ts
│   │   └── request-log.ts
│   └── modules/               # фича = папка
│       └── health/
│           ├── health.routes.ts
│           ├── health.controller.ts
│           └── health.service.ts
├── .env                       # локальные значения, в git не попадает
└── .env.example               # список переменных без значений, в git
```

### Разделение ответственности

| Слой | Что знает | Чего не знает |
|---|---|---|
| `*.routes.ts` | путь, мидлвары, какой контроллер вызвать | всё остальное |
| `*.controller.ts` | `req` и `res` | SQL, бизнес-правила |
| `*.service.ts` | бизнес-правила | HTTP, `req`/`res` |
| `*.repository.ts` | запросы в БД через Prisma | бизнес-правила |

Смысл разделения: сервис можно вызвать из воркера (у которого нет `req`) и протестировать
без поднятия сервера. `repository` заводится, когда запросов становится много —
на мелком модуле сервис ходит в Prisma сам.

**Два процесса.** `index.ts` — API, `worker.ts` — фоновые задачи
(модуль `modules/workers/`). Код общий: воркер вызывает те же сервисы, что
и контроллеры, например `syncKaspiOrdersPeriod()` из модуля заказов. Общую
работу двух процессов разводит блокировка PostgreSQL (`lib/advisory-lock.ts`),
а не память процесса. Подробности — [workers.md](workers.md).

### Как добавить модуль

1. Папка `src/modules/<имя>/` с файлами `<имя>.routes.ts`, `.controller.ts`, `.service.ts`.
2. Схема валидации входа — `<имя>.schema.ts` (zod).
3. Одна строка в `src/routes.ts`: `apiRouter.use('/<путь>', <имя>Router)`.
4. Запись в `docs/api-reference.md` и в карту `index.md` — в той же задаче.

### База данных

Prisma 7 подключается к PostgreSQL **через драйвер-адаптер** (`@prisma/adapter-pg`) —
в 6-й версии этого не требовалось. Клиент создаётся один раз на процесс в `src/db/client.ts`:
каждый экземпляр держит собственный пул соединений, поэтому создавать их по месту вызова нельзя.

Сгенерированный клиент лежит в `src/generated/prisma` — внутри `src`, иначе он оказывается
вне `rootDir` и ломает проверку типов. Папка в git не попадает, восстанавливается командой
`npm exec --workspace server -- prisma generate`. Её нужно повторять после каждого
изменения `schema.prisma`.

### Ошибки

Сервисы бросают классы из `lib/errors.ts` (`NotFoundError`, `ForbiddenError` и т.д.),
а не возвращают `res.status(...)`. HTTP-код проставляет `error-handler`.
Наружу уходит единая форма `ApiErrorResponse` из `shared` — стек и внутренние детали
в ответ не попадают никогда.

## 3. front — структура

Маршруты в Next.js App Router лежат только в `src/app/`, имя папки задано фреймворком.
Разделение магазина и админки — через **группы маршрутов**: папка в скобках не попадает
в URL, но даёт разделу свой `layout` и свои стили.

```
front/
├── src/
│   ├── app/                   # ТОЛЬКО маршруты
│   │   ├── layout.tsx         # корневой layout: шрифты, Providers
│   │   ├── providers.tsx      # Redux-провайдер (клиентский компонент)
│   │   ├── globals.css        # Tailwind + базовые токены
│   │   ├── (shop)/            # магазин: свой layout, класс theme-shop
│   │   └── dashboard/         # админка: (main) с сайдбаром и (auth) со входом
│   ├── components/
│   │   └── price-tag/         # наш компонент: tree-list.tsx + style.module.scss
│   ├── features/              # логика по доменам: эндпоинты RTK Query, хуки
│   ├── shared/                # переиспользуемое внутри front
│   │   └── api/base-api.ts    # единая точка RTK Query
│   ├── store/                 # Redux Toolkit: makeStore, типизированные хуки
│   └── lib/utils.ts           # cn() — склейка Tailwind-классов
└── public/
```

Правило по компонентам: набор один на всё приложение, деления по разделам нет.
Всё, что нужно одной странице, — рядом с ней в `_components/`.

### Состояние

Серверные данные — **только** через RTK Query: `baseApi` один на всё приложение, модули
дописывают эндпоинты через `injectEndpoints`. Кэш и повторные запросы берёт на себя он же,
руками их дублировать не нужно.

Клиентское состояние (корзина, фильтры, UI) — слайсы Redux Toolkit, добавляются
в `reducer` внутри `makeStore()`.

Стор создаётся фабрикой на каждого клиента, а не на уровне модуля: иначе при серверном
рендере состояние одного пользователя утекло бы к другому.

### Стили: две системы, один слой токенов

| Что | Чем стилизуется | Почему |
|---|---|---|
| `components/<имя>/` — наши компоненты | SCSS-модули | Папка + `tree-list.tsx` + `style.module.scss` |
| Разметка страниц и layout | Tailwind | Быстрее для сеток и отступов |

**Готовых UI-китов в проекте нет.** Все компоненты пишутся сами: shadcn/ui, его CLI,
`tw-animate-css` и `class-variance-authority` удалены. Остались Tailwind как система утилит
и Sass для своих компонентов.

Base UI оставлен намеренно — он не приносит ни одного стиля, только поведение
и доступность там, где их дорого писать руками: фокус-ловушка в модальном окне, работа
клавиатуры в списках, ARIA. Разметка и внешний вид полностью свои.

**Компоненты не делятся по разделам.** Набор один на всё приложение: и витрина, и админка
используют одни и те же компоненты. Компонент не знает, где он стоит.
Разный вид получается из двух источников: тема раздела подставляет свои токены,
а вызывающая сторона передаёт `className` для точечных правок.

Отсюда контракт любого компонента:
- принимает `className` и склеивает его через `cn()` — внешние отступы и ширину задаёт вызывающий;
- пробрасывает остальные пропсы через `...props` — `onClick`, `disabled`, `aria-*` работают без переписывания;
- не задаёт себе внешние отступы и ширину — это ответственность страницы.

Разметка, нужная одной странице, живёт рядом с ней в `_components/`, а не в общей папке.

Связывает их **единственный слой токенов** — CSS-переменные. Классы Tailwind (`bg-primary`)
и SCSS (`var(--primary)`) читают одни и те же значения, поэтому тема меняется в одном месте.

**Правила для `style.module.scss`:**
- суффикс `.module` обязателен — иначе классы глобальные и конфликтуют между разделами;
- цвета, скругления и акценты — только через `var(--токен)`, без хардкода;
- `@apply` внутри SCSS не используем: две системы стилей в одном файле труднее отлаживать.

Правка `components/ui/` допустима, только если изменение нужно **обоим** разделам.
Иначе — новый компонент в своей папке.

### Темы

Четыре темы — это два измерения: раздел × цветовая схема. Файл `src/styles/themes.css`,
подключён из `globals.css`:

```
.theme-shop             магазин, светлая
.dark .theme-shop       магазин, тёмная
.theme-dashboard        админка, светлая
.dark .theme-dashboard  админка, тёмная
```

Класс раздела вешается на layout группы маршрутов, класс `dark` — на `<html>`.
Базовые значения токенов лежат в `globals.css` (`:root` и `.dark`), в `themes.css`
переопределяется только то, что отличается.

Собственные токены раздела (например `--shop-price`) объявляются там же и используются
в SCSS-модулях этого раздела.

### Шрифт

`Inter` с подмножествами `latin` и `cyrillic` — интерфейс русскоязычный, шрифт обязан
поддерживать кириллицу. Geist из стартового шаблона Next не взят — с кириллицей у него неясно.

Добавил файл — реэкспортируй его в `shared/src/index.ts`, иначе снаружи он не виден.

## 5. Решения по стеку

| Решение | Почему |
|---|---|
| **npm workspaces** | Один `node_modules`, общие версии, раздельные списки зависимостей для деплоя |
| **App Router** | Группы маршрутов дают магазину и админке раздельные layout и стили из коробки |
| **Redux Toolkit + RTK Query** | Слайсы для клиентского состояния, RTK Query — кэш и инвалидация серверных данных |
| **Tailwind + свои компоненты** | Готовый UI-кит не подключаем: компоненты пишутся сами, раскладка на Tailwind, внутренности на SCSS-модулях |
| **Prisma** | Типизированный клиент и нормальные миграции; схема пишется с нуля |
| **zod** | Одна библиотека и для валидации входа API, и для проверки переменных окружения |
| **CommonJS на сервере** | Не требует расширений `.js` в импортах — меньше ловушек при ручном написании кода |

Версии на момент создания каркаса: Next 16.3, React 19.2, Express 5.2, Prisma 7.9,
Tailwind 4, zod 4. Мажоры свежие — перед написанием кода сверяться с документацией
конкретной версии, а не по памяти.

## 7. Известные особенности и долги

**Сборка `shared` для продакшена.** Сейчас пакет отдаёт TypeScript-исходники
(`main: src/index.ts`). Для разработки этого достаточно: `tsx` и Next.js читают их напрямую.
Для продакшен-сборки сервера понадобится бандлер (например `tsup`), иначе `tsc`
не соберёт импорт из соседнего пакета. Задача откладывается до этапа деплоя.

**Base UI лежит без использования.** Пакет оставлен на будущее: он даёт поведение
и доступность для модальных окон, выпадающих списков и комбобоксов — там, где руками
это дорого. Пока ни один компонент его не импортирует. Если к моменту, когда дойдём
до модалок, он так и не понадобится — удалить.

**Файлы для AI-агентов от генераторов.** `create-next-app` умеет класть в проект свой
`AGENTS.md` и `CLAUDE.md` (отключено флагом `--no-agents-md`), `prisma init` — папки
`.claude/`, `.agents/`, `.windsurf/` со skills. К правилам проекта отношения не имеют,
конституция одна и лежит в корне.

## Модуль дерева категорий и чтения каталога (18.09.2026)

Используется существующая модель Category. «Все товары» — служебный пункт обзора,
не строка БД. Папки создаются вручную, без группировки по названиям Kaspi.
Product связан с одной папкой, все его Variant наследуют её при фильтрации.

- `server/src/modules/categories/`: routes, controller, schemas, service — дерево
  и создание/переименование/удаление папок. getCategoryTree() собирает дерево одним запросом;
  createCategory() разрешает только два уровня. Создание и renameCategory() проверяют
  уникальность имени в Serializable-транзакции. deleteCategory() блокирует запись
  через FOR UPDATE и удаляет только пустую папку в ReadCommitted-транзакции.
- `server/src/modules/products/catalog.schemas.ts`: проверка поиска, пагинации,
  UUID папки и списка перемещаемых товаров.
- `server/src/modules/products/catalog.service.ts`: listCatalog() — страница
  артикулов и счётчик в одном снимке БД; moveProductsToCategory() — атомарный перенос.
- `server/src/modules/products/catalog.mapper.ts`: catalogRowSelect и toCatalogRow()
  определяют явный безопасный DTO; закупка и история даже не выбираются из БД.
- `server/src/modules/products/catalog.controller.ts`: HTTP-обработчики и аудит переноса.
- `shared/src/constants/catalog.ts`, `shared/src/types/catalog.ts`: размеры страниц,
  лимиты, служебное название и общий контракт дерева/таблицы/переноса.
- `front/src/features/categories/categories-api.ts`: дерево, создание, переименование и удаление.
- `front/src/features/categories/use-category-actions.ts`: формы переименования/удаления и ошибки.
- `front/src/features/categories/use-create-category-form.ts`: форма создания.
- `front/src/features/products/catalog-api.ts`: серверная таблица и перенос.
- `front/src/features/products/use-product-catalog.ts`: выбор/раскрытие папок,
  поиск с задержкой, пагинация, выделение и перенос.

Связанные данные выбираются для текущей страницы, без запроса из цикла по строкам.
Для поиска по подстроке обычный индекс sku не гарантирует ускорения; при росте
каталога оценить фактическое время и план запросов до добавления поисковых индексов.
Пагинация offset подходит для текущего размера каталога, но очень глубокие страницы
на значительно большей базе потребуют пересмотра. Дерево загружается целиком;
товары — только выбранной страницей. Новых зависимостей и миграций нет.

API подробной карточки и перемещение самих папок не входят в текущую реализацию.
Переименование и удаление пустых папок доступны. Вложенность ограничена двумя уровнями. Страница /dashboard/products подключает управляемые
компоненты TreeFolder и Tables через useProductCatalog. Компоненты лежат в
front/src/components/tree-folder/ и front/src/components/tables/, в каждой папке
page.tsx и style.module.scss. Строки товаров для Tables.children пользователь
добавляет самостоятельно. Компоненты не знают маршрута и не обращаются к API. Категория «Прима 320 Угловой» группирует
товары, но не объединяет их в один Product с модификациями.

## Модуль поставщиков (28.09.2026)

Новая модель `Supplier` и импорт её из выгрузки контрагентов МойСклада.
Поставщик — отдельная сущность, а не строка справочника: `DictionaryItem`
вида `SHIPMENT_ORIGIN` держит вперемешку витрины и поставщиков, и разделить
их пора было ещё на этапе офлайн-заказов.

- `server/src/lib/excel.ts`: чтение книги и ячеек — `readWorkbook`, `listSheets`,
  `requireSheet`, `readText`, `readNumber`. Вынесено из парсера офлайн-продаж,
  когда за той же работой пришёл второй импорт: одну и ту же ячейку нельзя
  читать двумя разными способами, иначе файл, который в одном разделе
  разбирается, в другом молча окажется пустым.
- `server/src/modules/suppliers/suppliers.parser.ts`: разбор выгрузки, отбор
  по группе «поставщики», отбрасывание телефона-заглушки МойСклада.
- `server/src/modules/suppliers/suppliers.service.ts`: сверка с базой
  (`matchExisting`), предпросмотр и запись `upsert`-ом по `externalId`.
- `server/src/modules/suppliers/suppliers.schemas.ts`: схема строки повторяет
  контракт целиком — строки предпросмотра приезжают обратно от клиента,
  и между показом и записью лежит сеть.
- `shared/src/constants/suppliers.ts`, `shared/src/types/suppliers.ts`: группа
  отбора, лимиты полей, DTO и контракты импорта.
- `front/src/features/suppliers/suppliers-api.ts`: список, предпросмотр, запись, правка.
- `front/src/features/suppliers/use-supplier-import.ts`: файл → лист → запись;
  единственный лист книги разбирается сразу, без выбора из одного варианта.

Справочник читается целиком и в списке, и при сверке: поставщиков десятки,
а пагинация на таком объёме — лишняя работа обеим сторонам. При росте
до сотен строку сверки (`matchExisting`) придётся сузить до нужных `externalId`
плюс отдельный запрос по имени.

Новых зависимостей нет: `exceljs` уже стоял ради импорта продаж.
Миграция одна — `suppliers`.

## Импорт товаров из МойСклада (28.09.2026)

Заполняет то, чего нет в Kaspi: закупочную цену с валютой, поставщика и сроки
предзаказа по складам. Новых товаров не заводит.

Лежит в модуле `products`, а не в `imports`: импорт пишет в `Variant`
и `VariantStock`, то есть это операция над каталогом, а файл — всего лишь
её источник. По тому же правилу импорт поставщиков лежит в `suppliers`,
а импорт продаж — в `imports`, потому что пишет в `Order`.

- `server/src/modules/products/moysklad.parser.ts`: колонки по заголовкам,
  отбор по типу строки, разбор цены-строки с запятой, сроки предзаказа
  по складам.
- `server/src/modules/products/moysklad.service.ts`: пометка задвоенных кодов,
  сверка с каталогом и справочником поставщиков, запись пачками.
- `server/src/modules/products/moysklad.schemas.ts`: схема строки повторяет
  контракт целиком, включая границу срока предзаказа — он уходит на площадку.
- `shared/src/constants/moysklad.ts`: раскладка «колонка файла → код склада»,
  сопоставление валют, типы строк, пределы.
- `shared/src/constants/currencies.ts`: `Currency`, подписи и названия.
- `front/src/features/products/moysklad-api.ts` и `use-moysklad-import.ts`.

**Почему запись пачками, а не одной транзакцией.** Полторы тысячи артикулов
с четырьмя складами каждый — это тысячи операторов, и одна транзакция держала бы
блокировки минутами. Обрыв на середине здесь безопасен: импорт обновляет
существующие записи, а не создаёт новые, поэтому повтор дозапишет остальное
и дублей не создаст. У импорта продаж наоборот — там одна транзакция
обязательна, потому что половина импортированного месяца при повторе
превратилась бы в дубли.

Сверка с каталогом читает все артикулы и всех поставщиков в память: `in`
в Prisma регистр не игнорирует, а в файле код записан как `zkz090`, у нас —
как `ZKZ090`. На тысячах артикулов это дешевле тысячи запросов по одному.
При росте каталога до десятков тысяч сверку придётся сузить до кодов из файла.

Новых зависимостей нет. Миграция одна — `variant_purchase`.

## История изменений (29.09.2026)

Универсальная запись «кто, когда и откуда поменял поля сущности». Лежит
в `AuditLog` рядом с журналом действий, отдельной таблицы нет — вторая история
рядом с журналом однажды разошлась бы с ним. Прежняя `VariantChange` удалена:
в неё никто не писал.

- `server/src/lib/history.ts`:
  - `recordHistory(tx, meta, entries)` — запись в транзакции изменения;
  - `diffFields(entityType, before, after)` — список изменившихся полей;
  - `historyValue(value)` — приведение значения к строке (Decimal — два знака).
- `shared/src/constants/history-fields.ts` — словарь: `HISTORY_ENTITY_TYPES`,
  `HISTORY_FIELD_LABELS`, `HISTORY_SOURCES`, `historyFieldLabel()`.
- `shared/src/types/history.ts` — `HistoryChange`, `HistoryContext`.
- `server/src/modules/audit/audit.schemas.ts` — фильтры `GET /api/audit`.

**Правило для нового кода.** Меняешь поля товара, поставщика или другой сущности
из `HISTORY_ENTITY_TYPES` — пиши историю через `recordHistory()` в той же
транзакции, список полей — через `diffFields()`. Новое поле — сначала ключ
и подпись в `HISTORY_FIELD_LABELS`, иначе TypeScript не пропустит.
Событие без изменённых полей (вход, предпросмотр) — `logAction()`, как раньше.

Почему не расширили `logAction()`: у него другой контракт — он вызывается после
операции и проглатывает сбой, чтобы журнал не ронял работу. Для истории
это неверно: изменение без записи о нём хуже неудачной операции.

## Импорт остатков из МойСклада (29.09.2026)

Отчёт «Остатки» — остаток, резерв, ожидание, себестоимость и дни на складе
по одному складу. Лежит рядом с импортом товаров в модуле `products`: пишет
в `VariantStock` и `Variant`.

- `server/src/modules/products/moysklad-stock.parser.ts` — заголовок глубже
  шапки отчёта, строки-папки и «Итого», момент отчёта в поясе Астаны.
- `server/src/modules/products/moysklad-stock.service.ts` — сверка, список
  на обнуление, запись пачками с историей.
- `server/src/modules/products/moysklad.common.ts` — общее двух импортов
  МойСклада: `markDuplicateCodes()`, `loadSkuIndex()`.
- `server/src/lib/excel.ts` — `readWorkbook()` узнаёт старый `.xls` по подписи
  и говорит пересохранить его, а не «файл не читается». Библиотеку под `.xls`
  не подключали: `xlsx` в npm заброшен на версии с известными уязвимостями.

**Главное отличие от импорта товаров — молчание файла значит.** Отчёт — полный
снимок склада, поэтому товар, которого в нём нет, продан, и его остаток
обнуляется. Список на обнуление считается на предпросмотре и приезжает
в запись от клиента — ровно то, что видел человек; сервер отбрасывает из него
товары, чей код в отчёте есть.

**«Дней на складе» хранится датой.** Отчёт даёт только среднее число дней, партий
в нём нет. Хранится `VariantStock.receivedAt` = момент отчёта − дни, а дни
считаются при выдаче каталога. Точный учёт партий (какая посадка ещё лежит)
появится вместе с посадкой товара.
