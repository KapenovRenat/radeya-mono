# Архитектура проекта

> Структура папок, слои и решения по стеку. Обновляется при появлении нового модуля,
> слоя или изменении структуры (п.10 в [AGENTS.md](../AGENTS.md)).

---

## 1. Монорепозиторий

Три пакета в одном репозитории, связаны через **npm workspaces** (корневой `package.json`):

```
radeya-mono/
├── server/    # Express + Prisma + PostgreSQL — API
├── front/     # Next.js (App Router) — магазин + dashboard
├── shared/    # Общий код server и front
└── node_modules/   # один на все пакеты (хостинг зависимостей)
```

У каждого пакета свой `package.json` — свой список зависимостей и свои команды.
Физически библиотеки лежат в корневом `node_modules`: одна копия, одинаковые версии.

Внутри `server/` или `front/` папки `node_modules` быть не должно — если появилась,
значит workspaces не отработали.

## 2. server — слои

```
server/
├── prisma/
│   ├── schema.prisma          # модели БД
│   └── migrations/            # SQL-миграции, обязательно в git
├── prisma.config.ts           # конфиг Prisma 7: путь к схеме и DATABASE_URL
├── src/
│   ├── index.ts               # запуск сервера, graceful shutdown
│   ├── app.ts                 # сборка Express: мидлвары + маршруты
│   ├── routes.ts              # подключение модулей к /api
│   ├── config/
│   │   └── env.ts             # валидация переменных окружения (zod)
│   ├── db/
│   │   └── client.ts          # единственный экземпляр Prisma Client
│   ├── generated/prisma/      # сгенерированный клиент, в git не попадает
│   ├── lib/                   # переиспользуемое, без привязки к домену
│   │   ├── errors.ts          # AppError и наследники
│   │   └── logger.ts
│   ├── middlewares/
│   │   ├── error-handler.ts   # ставится последним
│   │   ├── not-found.ts
│   │   └── request-log.ts
│   └── modules/               # фича = папка
│       └── health/
│           ├── health.routes.ts
│           ├── health.controller.ts
│           └── health.service.ts
├── .env                       # локальные значения, в git не попадает
└── .env.example               # список переменных без значений, в git
```

### Разделение ответственности

| Слой | Что знает | Чего не знает |
|---|---|---|
| `*.routes.ts` | путь, мидлвары, какой контроллер вызвать | всё остальное |
| `*.controller.ts` | `req` и `res` | SQL, бизнес-правила |
| `*.service.ts` | бизнес-правила | HTTP, `req`/`res` |
| `*.repository.ts` | запросы в БД через Prisma | бизнес-правила |

Смысл разделения: сервис можно вызвать из воркера (у которого нет `req`) и протестировать
без поднятия сервера. `repository` заводится, когда запросов становится много —
на мелком модуле сервис ходит в Prisma сам.

### Как добавить модуль

1. Папка `src/modules/<имя>/` с файлами `<имя>.routes.ts`, `.controller.ts`, `.service.ts`.
2. Схема валидации входа — `<имя>.schema.ts` (zod).
3. Одна строка в `src/routes.ts`: `apiRouter.use('/<путь>', <имя>Router)`.
4. Запись в `docs/api-reference.md` и в карту `index.md` — в той же задаче.

### База данных

Prisma 7 подключается к PostgreSQL **через драйвер-адаптер** (`@prisma/adapter-pg`) —
в 6-й версии этого не требовалось. Клиент создаётся один раз на процесс в `src/db/client.ts`:
каждый экземпляр держит собственный пул соединений, поэтому создавать их по месту вызова нельзя.

Сгенерированный клиент лежит в `src/generated/prisma` — внутри `src`, иначе он оказывается
вне `rootDir` и ломает проверку типов. Папка в git не попадает, восстанавливается командой
`npm exec --workspace server -- prisma generate`. Её нужно повторять после каждого
изменения `schema.prisma`.

### Ошибки

Сервисы бросают классы из `lib/errors.ts` (`NotFoundError`, `ForbiddenError` и т.д.),
а не возвращают `res.status(...)`. HTTP-код проставляет `error-handler`.
Наружу уходит единая форма `ApiErrorResponse` из `shared` — стек и внутренние детали
в ответ не попадают никогда.

## 3. front — структура

Маршруты в Next.js App Router лежат только в `src/app/`, имя папки задано фреймворком.
Разделение магазина и админки — через **группы маршрутов**: папка в скобках не попадает
в URL, но даёт разделу свой `layout` и свои стили.

```
front/
├── src/
│   ├── app/                   # ТОЛЬКО маршруты
│   │   ├── layout.tsx         # корневой layout: шрифты, Providers
│   │   ├── providers.tsx      # Redux-провайдер (клиентский компонент)
│   │   ├── globals.css        # токены shadcn + .theme-shop / .theme-dashboard
│   │   ├── (shop)/            # магазин: свой layout, класс theme-shop
│   │   ├── (dashboard)/       # админка: сайдбар, класс theme-dashboard
│   │   └── (auth)/            # вход, регистрация, «ожидайте подтверждения»
│   ├── components/
│   │   ├── ui/                # примитивы shadcn (Tailwind)
│   │   └── price-tag/         # наш компонент: index.tsx + style.module.scss
│   ├── features/              # логика по доменам: эндпоинты RTK Query, хуки
│   ├── shared/                # переиспользуемое внутри front
│   │   └── api/base-api.ts    # единая точка RTK Query
│   ├── store/                 # Redux Toolkit: makeStore, типизированные хуки
│   └── lib/utils.ts           # cn() от shadcn
└── public/
```

Правило по компонентам: набор один на всё приложение, деления по разделам нет.
Всё, что нужно одной странице, — рядом с ней в `_components/`.

### Состояние

Серверные данные — **только** через RTK Query: `baseApi` один на всё приложение, модули
дописывают эндпоинты через `injectEndpoints`. Кэш и повторные запросы берёт на себя он же,
руками их дублировать не нужно.

Клиентское состояние (корзина, фильтры, UI) — слайсы Redux Toolkit, добавляются
в `reducer` внутри `makeStore()`.

Стор создаётся фабрикой на каждого клиента, а не на уровне модуля: иначе при серверном
рендере состояние одного пользователя утекло бы к другому.

### Стили: две системы, один слой токенов

| Что | Чем стилизуется | Почему |
|---|---|---|
| `components/ui/` — примитивы shadcn | Tailwind | Приходят готовыми, обновляются командой `shadcn add` |
| `components/<имя>/` — наши компоненты | SCSS-модули | Папка + `index.tsx` + `style.module.scss` |
| Разметка страниц и layout | Tailwind | Быстрее для сеток и отступов |

**Компоненты не делятся по разделам.** Набор один на всё приложение: и витрина, и админка
используют одни и те же компоненты. Компонент не знает, где он стоит.
Разный вид получается из двух источников: тема раздела подставляет свои токены,
а вызывающая сторона передаёт `className` для точечных правок.

Отсюда контракт любого компонента:
- принимает `className` и склеивает его через `cn()` — внешние отступы и ширину задаёт вызывающий;
- пробрасывает остальные пропсы через `...props` — `onClick`, `disabled`, `aria-*` работают без переписывания;
- не задаёт себе внешние отступы и ширину — это ответственность страницы.

Разметка, нужная одной странице, живёт рядом с ней в `_components/`, а не в общей папке.

Связывает их **единственный слой токенов** — CSS-переменные. Классы Tailwind (`bg-primary`)
и SCSS (`var(--primary)`) читают одни и те же значения, поэтому тема меняется в одном месте.

**Правила для `style.module.scss`:**
- суффикс `.module` обязателен — иначе классы глобальные и конфликтуют между разделами;
- цвета, скругления и акценты — только через `var(--токен)`, без хардкода;
- `@apply` внутри SCSS не используем: две системы стилей в одном файле труднее отлаживать.

Правка `components/ui/` допустима, только если изменение нужно **обоим** разделам.
Иначе — новый компонент в своей папке.

### Темы

Четыре темы — это два измерения: раздел × цветовая схема. Файл `src/styles/themes.css`,
подключён из `globals.css`:

```
.theme-shop             магазин, светлая
.dark .theme-shop       магазин, тёмная
.theme-dashboard        админка, светлая
.dark .theme-dashboard  админка, тёмная
```

Класс раздела вешается на layout группы маршрутов, класс `dark` — на `<html>`.
Базовые значения токенов лежат в `globals.css` (`:root` и `.dark`), в `themes.css`
переопределяется только то, что отличается.

Собственные токены раздела (например `--shop-price`) объявляются там же и используются
в SCSS-модулях этого раздела.

### Шрифт

`Inter` с подмножествами `latin` и `cyrillic` — интерфейс русскоязычный, шрифт обязан
поддерживать кириллицу. Пресет shadcn предлагал Geist, но с кириллицей у него неясно.

## 4. shared — общий код

```
shared/src/
├── index.ts                   # единственная точка входа пакета
├── constants/
│   ├── roles.ts               # USER_ROLES, USER_STATUSES
│   └── order-sources.ts       # ORDER_SOURCES и подписи
└── types/
    └── api.ts                 # ApiErrorResponse, PaginatedResponse
```

Сюда попадает то, что нужно **обеим** сторонам: роли, статусы, источники заказов,
формы ответов API. Импорт всегда из корня пакета: `import { USER_ROLES } from '@radeya/shared'`.

Добавил файл — реэкспортируй его в `shared/src/index.ts`, иначе снаружи он не виден.

## 5. Решения по стеку

| Решение | Почему |
|---|---|
| **npm workspaces** | Один `node_modules`, общие версии, раздельные списки зависимостей для деплоя |
| **App Router** | Группы маршрутов дают магазину и админке раздельные layout и стили из коробки |
| **Redux Toolkit + RTK Query** | Слайсы для клиентского состояния, RTK Query — кэш и инвалидация серверных данных |
| **Tailwind + shadcn/ui** | Компоненты копируются в проект, правятся как свои; один инструмент стилей на оба раздела |
| **Prisma** | Типизированный клиент и нормальные миграции; схема пишется с нуля |
| **zod** | Одна библиотека и для валидации входа API, и для проверки переменных окружения |
| **CommonJS на сервере** | Не требует расширений `.js` в импортах — меньше ловушек при ручном написании кода |

Версии на момент создания каркаса: Next 16.3, React 19.2, Express 5.2, Prisma 7.9,
Tailwind 4, zod 4. Мажоры свежие — перед написанием кода сверяться с документацией
конкретной версии, а не по памяти.

## 6. Команды разработки

Все запускаются из корня репозитория:

| Команда | Что делает |
|---|---|
| `npm install` | Ставит зависимости всех пакетов и связывает `@radeya/shared` |
| `npm run dev:server` | API на `http://localhost:4000` с автоперезапуском |
| `npm run dev:front` | Next.js на `http://localhost:3000` |
| `npm exec --workspace front -- shadcn@latest add <компонент>` | Копирует компонент shadcn в `front/src/components/ui/` |
| `npm run typecheck` | Проверка типов во всех пакетах |
| `npm run build` | Сборка всех пакетов |

Проверка, что сервер жив: `http://localhost:4000/api/health`.

## 7. Известные особенности и долги

**Сборка `shared` для продакшена.** Сейчас пакет отдаёт TypeScript-исходники
(`main: src/index.ts`). Для разработки этого достаточно: `tsx` и Next.js читают их напрямую.
Для продакшен-сборки сервера понадобится бандлер (например `tsup`), иначе `tsc`
не соберёт импорт из соседнего пакета. Задача откладывается до этапа деплоя.

**Библиотека примитивов — Base UI.** shadcn 4 предлагает на выбор Base UI, React Aria и Radix.
Взят Base UI как рекомендованный самим shadcn: их документация и генерируемые компоненты
рассчитаны в первую очередь на него. Пресет — `base-nova` (иконки Lucide).

**Файлы для AI-агентов от генераторов.** `create-next-app` умеет класть в проект свой
`AGENTS.md` и `CLAUDE.md` (отключено флагом `--no-agents-md`), `prisma init` — папки
`.claude/`, `.agents/`, `.windsurf/` со skills. К правилам проекта отношения не имеют,
конституция одна и лежит в корне.
