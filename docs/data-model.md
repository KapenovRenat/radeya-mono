# Модель данных

Схема Prisma — `server/prisma/schema.prisma`. Здесь описано назначение моделей, значимые
поля и принятые решения. Перечень моделей одной строкой — в [index.md](../index.md).

---

## Общие правила

- **Идентификаторы — UUID**, а не автоинкремент. Последовательный id выдаёт объём базы
  наружу и упрощает перебор чужих записей по URL.
- **Пароли только хешируются**, алгоритм — argon2id. Поле называется `passwordHash`:
  шифрование обратимо, хеш — нет, и имя поля должно об этом напоминать.
- **Учётные записи не удаляются, а отключаются** флагом `isActive`. Удаление рвёт ссылки
  в журнале действий и в заказах.
- **Имена таблиц и колонок — как в схеме Prisma**, без `@@map`. Единственный путь к базе —
  Prisma Client; сырой SQL пишется редко и только параметризованный.

## User — сотрудник

Вход в дашборд по логину. **Саморегистрации нет:** учётные записи заводит админ.
Первый пользователь создаётся, пока таблица пуста, — проверка и вставка выполняются
в одной транзакции, иначе два одновременных запроса создадут двух админов.

| Поле | Тип | Заметки |
|---|---|---|
| `id` | `String` UUID | Первичный ключ |
| `login` | `String` уникальный | Латиница, цифры и `. _ -`, нижний регистр. Нормализуется до записи |
| `passwordHash` | `String` | argon2id. Наружу не отдаётся никогда |
| `name` | `String` | Имя сотрудника |
| `position` | `String` | Должность, произвольный текст. Заполняет админ при создании |
| `role` | `UserRole` | Без значения по умолчанию — выбирается явно |
| `isActive` | `Boolean` = `true` | Отключение вместо удаления |
| `createdAt` / `updatedAt` | `DateTime` | |
| `createdById` | `String?` UUID | Кто завёл. Self-relation `UserCreatedBy`, `onDelete: SetNull`. У первого админа пусто |

Индексы: уникальный на `login`, обычный на `role` — по нему строится список сотрудников.

### enum UserRole

`ADMIN` · `MANAGER` · `SELLER`

Значения обязаны совпадать с `USER_ROLES` в `shared/src/constants/roles.ts` — там же
лежат подписи для интерфейса. Роль проверяется на сервере; скрытая кнопка в интерфейсе
защитой не является.

## Customer — клиент магазина

Регистрируется сам с витрины. **Отдельная сущность и отдельный вход**, не смешивается
с `User`: у клиента нет ни роли, ни должности, а права сотрудников к нему неприменимы.
Одна таблица на оба типа означала бы кучу пустых полей и проверку «а это точно сотрудник?»
в каждом запросе.

| Поле | Тип | Заметки |
|---|---|---|
| `id` | `String` UUID | Первичный ключ |
| `login` | `String` уникальный | Как у сотрудника |
| `passwordHash` | `String` | argon2id |
| `name` | `String` | Имя клиента |
| `phone` | `String` уникальный | **Обязательный.** Нормализуется до записи в `+7XXXXXXXXXX` — иначе `+7 777 123-45-67` и `87771234567` окажутся разными значениями и уникальность не сработает |
| `email` | `String?` уникальный | **Необязательный.** PostgreSQL допускает любое количество `NULL` в уникальном индексе, поэтому «нужен не всем, но не повторяется» — это одно поле без ухищрений |
| `isActive` | `Boolean` = `true` | |
| `createdAt` / `updatedAt` | `DateTime` | |

## Session — сессия сотрудника

В куке лежит **только идентификатор**, всё состояние — в этой таблице.
Отсюда главное свойство: сессию можно погасить мгновенно, удалив строку.
С подписанным токеном так не выйдет — он действует до истечения срока,
и уволенный сотрудник остаётся в системе.

| Поле | Тип | Заметки |
|---|---|---|
| `id` | `String` UUID | Он же значение куки `radeya_sid` |
| `userId` | `String` UUID | `onDelete: Cascade` — удалили пользователя, сессии ушли |
| `expiresAt` | `DateTime` | 7 дней от создания |
| `createdAt` | `DateTime` | |
| `userAgent` | `String?` | Для раздела «активные сессии» и разбора инцидентов |
| `ip` | `String?` | |

Индексы: `userId`, `expiresAt`.

Проверка при каждом запросе смотрит и срок, и `isActive` пользователя: отключили
сотрудника — его открытая вкладка перестаёт работать на следующем же запросе.

## AuditLog — журнал действий

Только вставка и чтение. Ни `update`, ни `delete` из кода: журнал, который
можно править, журналом не является.

| Поле | Тип | Заметки |
|---|---|---|
| `id` | `String` UUID | |
| `at` | `DateTime` | Когда |
| `userId` | `String?` UUID | Пусто у действий до входа — например неудачной попытки |
| `userLogin` | `String` | **Снимок** на момент действия |
| `userRole` | `String` | **Снимок** на момент действия |
| `action` | `String` | Значение из `AUDIT_ACTIONS` в `shared` |
| `entityType` / `entityId` | `String?` | Над чем действие |
| `before` / `after` | `Json?` | Состояние до и после. Пароли и хеши сюда не попадают |
| `ip` | `String?` | |

Индексы: `at`, `userId`, `action`.

**Связи с `User` намеренно нет.** Логин и роль хранятся копией: иначе после
переименования или смены роли вся прошлая история покажет сегодняшние значения,
а восстановить исходные будет неоткуда.

Запись делает `logAction()` из `server/src/lib/audit.ts`. Сбой записи не роняет
основную операцию — ошибка уходит в логгер, действие проходит: журнал не должен
обрушивать работу системы.

## Warehouse — склад (точка выдачи)

Справочник складов Kaspi. Заводится из выгрузки каталога, дальше правится руками.

| Поле | Тип | Замечание |
|---|---|---|
| `id` | `uuid` | — |
| `code` | `String @unique` | Наш короткий код: `PP3`. Ключ сверки при повторном импорте |
| `kaspiStoreId` | `String @unique` | Как в выгрузке и в заказах Kaspi: `6871008_PP3` |
| `kaspiCityId` | `String?` | Код города по КАТО. У части складов в выгрузке пусто |
| `name` | `String?` | **Наше** название точки. В выгрузке его нет |
| `isActive` | `Boolean @default(true)` | Точку закрыли — отключаем, не удаляем |
| `kaspiOffersCount` | `Int?` | Товаров на складе по данным последней синхронизации |
| `kaspiTotalStock` | `Int?` | Сумма остатков на тот же момент |
| `kaspiStatsAt` | `DateTime?` | Когда сделан снимок |
| `createdAt` / `updatedAt` | `DateTime` | — |

**Три последних поля — снимок, а не живые данные.** После импорта товаров
настоящие цифры считаются по `VariantStock`. Снимок нужен, чтобы видеть общую
картину по складам **до** импорта — сразу после загрузки каталога из кабинета.
Дата обязательна: без неё через месяц не понять, свежие это цифры или прошлогодние.
Обновление снимка не считается изменением справочника — иначе каждая
синхронизация показывала бы «обновлено 4», хотя склады те же.

**Почему отдельная таблица, а не код склада строкой у товара.** На склад сошлются
и товары, и заказы. Строкой опечатка в `PP3` молча создаст несуществующий склад,
и расхождение всплывёт на отчёте, а не на вводе.

**Что импорт не перезаписывает:** `name` и уже заполненный `kaspiCityId`. Выгрузка
их не знает, а повторная загрузка файла — обычное дело: стирать введённое руками
она не должна.

**Удаления нет.** Склад, пропавший из новой выгрузки, остаётся в справочнике:
на него ссылаются прошлые заказы.

Импорт — `saveKaspiWarehouses()` в `server/src/modules/warehouses/warehouses.service.ts`,
контракт эндпоинта — в [api-reference.md](api-reference.md).

## Каталог

Восемь моделей. Общий принцип: **товар один, продаётся он в нескольких местах**.
Всё, что различается между Kaspi, сайтом и OZON — цена, статус, идентификатор —
лежит в `Listing`. В `Product` и `Variant` остаётся только то, что верно везде.

```
Category ──< Product ──< Variant ──┬──< Listing        (канал: цена, статус, ID площадки)
                                   ├──< VariantStock   (склад: остаток)
                                   ├──< VariantChange  (история изменений)
                                   ├──> Fabric ──< FabricShade
```

### Category — папка каталога

`id`, `name`, `slug @unique`, `parentId?`, `path`, `sortOrder`, `isActive`.

Схема допускает дерево, но API разрешает **два уровня**: корневая папка → подпапка.
Дерево **наше собственное**: Kaspi отдаёт свои
`categoryPathCodes`, но категории для сайта и учёта мы строим сами.

`path` — денормализованный путь предков `/id1/id5/`: без него «все товары
поддерева» превращается в рекурсию на каждый запрос каталога. Уникальность
имени — внутри родителя (`@@unique([parentId, name])`): «Угловые» может лежать
и под диванами, и под кроватями.

С 18.09.2026 дерево читается и создаётся через /api/categories. Корневые дубли
и различия только регистром проверяет createCategory() в Serializable-транзакции:
обычный unique в PostgreSQL не запрещает несколько одинаковых имён с parentId=null.
Служебный пункт «Все товары» не записывается в Category. Он означает отсутствие
фильтра и включает товары с categoryId=null. Название «Все товары» зарезервировано.
Новая папка получает path от родителя и служебный slug category-UUID. Папка модели
(например «Прима 320 Угловой») остаётся Category и сама по себе не создаёт Product.
Перенос меняет Product.categoryId и охватывает все его модификации.
Переименование меняет только name, сохраняя path/slug/parentId. Удаление разрешено
только без товаров и подпапок; сервис блокирует Category перед проверкой пустоты,
несмотря на существующий onDelete: SetNull у Product. Более глубокие ранее созданные
узлы не удаляются автоматически. Новых миграций нет.

### Product — карточка модели

`id`, `name`, `slug? @unique`, `categoryId?`, `brand?`, `description?`,
`kaspiFamilyId?`, `isActive`, `createdById?`.

Артикула и цены здесь нет. Импорт из Kaspi создаёт по товару на каждый артикул;
объединение в одну модель с несколькими тканями — ручной шаг, когда дойдём
до витрины. `kaspiFamilyId` хранится как есть и будет ключом такой склейки.

### Variant — модификация, то, что реально продаётся

| Поле | Тип | Замечание |
|---|---|---|
| `sku` | `String @unique` | **Артикул.** Ключ сверки с кабинетом и позициями заказов |
| `barcode` | `String?` | `ntin` из кабинета |
| `kaspiMasterTitle`, `kaspiTitle`, `kaspiModel` | `String?` | Названия кабинета. Пишет только синхронизация |
| `kaspiMasterSku`, `kaspiOfferId` | `String?` | ID карточки и предложения |
| `kaspiFileId`, `kaspiMerchantUid` | `String?` | Для будущих запросов в кабинет |
| `kaspiShopLink` | `String?` | Путь на витрину |
| `kaspiImages` | `Json?` | Массив `{ small, medium, large }`. Файлы не выкачиваем |
| `kaspiUpdates` | `Json?` | История изменений кабинета снимком |
| `kaspiUpdatedAt` | `DateTime?` | Когда кабинет менял товар |
| `anyKaspiDelivery`, `…Express`, `…Local`, `anyMerchantDelivery` | `Boolean` | Зеркало кабинета |
| `siteDelivery` | `Boolean` | **Наш пятый флаг:** заказ с сайта везём сами |
| `purchasePrice` | `Decimal?` | Закупка. Отдаётся **только в дашборд** (`GET /api/products/variants`, роль ADMIN). На витрину — никогда |
| `minChannelPrice`, `maxChannelPrice` | `Decimal?` | Минимум и максимум по каналам |
| `fabricId?`, `fabricShadeId?` | `uuid` | Ткань и оттенок для витрины |
| `status` | `ListingStatus` | **Продаём или нет.** Наше решение, общее для всех каналов |

**Почему артикул на модификации, а не на товаре.** Kaspi матчит позиции заказа
по артикулу конкретной модификации. Положим артикул на товар — заказы не сматчатся.

**Два статуса, и это не дублирование.** `Variant.status` — наше решение
продавать или нет, одно на все каналы. `Listing.status` — что сейчас по факту
на площадке, его пишет только синхронизация. Расхождение между ними («мы
продаём, а на Kaspi архив») — рабочий сигнал для интерфейса. Одним полем это
не выразить: чьё значение оно бы показывало?

При импорте `Variant.status` берётся из кабинета — архивный товар заводится
снятым. Иначе он попал бы в будущую выгрузку на площадки как продаваемый.

**Почему поля кабинета отдельно от наших.** `kaspiTitle` и `name` — разные вещи:
первое приехало из кабинета, второе правит человек. Держать их в одном поле
значит либо затирать правки синхронизацией, либо не видеть расхождения с площадкой.

**`minChannelPrice` / `maxChannelPrice` — осознанная денормализация.** Считать
минимум по размещениям на каждую строку списка — это запрос на каждый товар.
Пересчитываются при любом изменении цены.

### Listing — размещение на канале продаж

`variantId`, `channel` (`SITE | KASPI | OZON`), `status`, `price?`,
`discountPrice?`, `discountPercent`, `externalId?`, `externalSku?`,
`externalUrl?`, `publishedAt?`, `lastSyncedAt?`, `syncError?`.
`@@unique([variantId, channel])`.

**Само наличие записи означает «продаём здесь».** Нет строки — канал не
используется. Отдельный флаг «показывать на сайте» разошёлся бы с ценой.

**`status` пишет только синхронизация** — это то, что сейчас по факту на площадке.
Расхождение с `Variant.isActive` («мы продаём, а на Kaspi архив») — рабочий
сигнал для интерфейса, а не ошибка данных.

**Процент скидки считает сервер.** Обратный счёт от процента не воспроизводит
фактическую цену — расходится на сотни тенге.

### VariantStock — остаток на складе

`variantId`, `warehouseId`, `quantity?`, `preOrderDays`.
`@@unique([variantId, warehouseId])`.

Остаток физический, поэтому висит на модификации, а не на размещении: коробка
на складе одна, и показывать её тремя независимыми цифрами для трёх каналов —
прямой путь продать то, чего нет.

`quantity: null` — это не ноль, а «остаток не указан, товар под заказ».

**Срок предзаказа один на всех.** При импорте первое значение приезжает из
кабинета, дальше правится у нас и уходит обратно на площадку; у артикулов,
которых в Kaspi нет, его ставим сами. Второго, «кабинетного», поля нет
намеренно: два срока предзаказа на одну позицию означали бы, что где-то
показывается неверный.

Отсюда следствие для будущей синхронизации: `preOrderDays` **не
перезаписывается** данными кабинета молча — расхождение показываем, решение
за человеком.

### Fabric и FabricShade — ткани и оттенки

`Fabric`: `code @unique`, `name`, `type?`, `sortOrder`, `isActive`.
`FabricShade`: `fabricId`, `code`, `name`, `hex?`, `imageUrl?`,
`@@unique([fabricId, code])`.

**Kaspi названий тканей не знает** — ему важен только тип. Название и палитру
ведём у себя и выбираем на артикул из списка после синхронизации.

Оттенок принадлежит своей ткани: «серый Tessoro» и «серый Bravo» — разные
оттенки, общим справочником цветов их не выразить.

### VariantChange — история изменений артикула

`variantId`, `field`, `oldValue?`, `newValue?`, `source` (`KASPI_SYNC | MANUAL`),
`userId?`, `createdAt`.

Отдельно от `AuditLog`: тот про действия сотрудников, а сюда попадают и правки
человека, и то, что приехало из кабинета. Значения строками — история read-only,
считать по ней ничего не будем.

### Enum'ы

`SalesChannel` (`SITE`, `KASPI`, `OZON`), `ListingStatus` (`ON_SALE`, `OFF_SALE`),
`ChangeSource` (`KASPI_SYNC`, `MANUAL`). Значения обязаны совпадать с константами
в `shared/src/constants/sales-channels.ts`.

WB убран по решению от 16.09.2026 — вернуть его будет одной строкой в enum.
Ради этого каналы и сделаны значениями, а не колонками таблицы.

## Заказы

### SalesPoint — точка продаж

Единый справочник происхождения заказа: и площадки (Kaspi, Ozon, сайт),
и офлайн-магазины лежат в одной таблице.

Почему не «перечисление для площадок плюс таблица для офлайна»: фильтр в реестре
и разрез статистики пришлось бы каждый раз склеивать из двух источников, а запрос
«Kaspi и точка на Абая вместе» не написать одним `GROUP BY`. Офлайн-точки при этом
заводит пользователь в рантайме — перечислением их не выразить в принципе.

Три поля, у каждого своя работа:

| Поле | Роль | Меняется |
|---|---|---|
| `id` (uuid) | связь с заказом | никогда |
| `code` | стабильный читаемый ключ: `KASPI`, `OZON`, `SITE`, `OFF-1` | никогда |
| `name` | то, что видит человек: «Точка на Абая» | сколько угодно |

- **Связь по `id`, поиск системной точки по `code`.** Синхронизация ищет Kaspi
  по коду: uuid на каждой базе свой, а код одинаков везде.
- **Код офлайн-точки генерит сервер** (`OFF-1`, `OFF-2`), из названия он не
  выводится: транслит даёт спорные правила и неожиданные совпадения («Абая»
  и «Абай»), а читаемость и так даёт `name`. Тот же приём, что у служебного
  `slug` категорий.
- **Системные точки через API не создаются** — только сидом миграции. Иначе
  однажды кто-то заведёт вторую строку с кодом `KASPI`.
- **Переименование разрешено всем, включая системные:** связи идут по `id`,
  а синхронизация по `code`, и «Kaspi магазин» вместо «Kaspi» ничего не ломает.
- **Удаления нет вовсе**, только `isActive = false`. На точке висят заказы:
  удалить её значит либо потерять их, либо потерять историю. Закрытая точка
  исчезает из выпадашки ввода заказа, но остаётся в фильтрах и отчётах.
- **Название уникально без учёта регистра**, включая закрытые точки: две «Абая»
  в отчёте за прошлый год неотличимы.

### DictionaryItem — пополняемые списки

Четыре справочника офлайн-точки в одной таблице, различаются полем `kind`:
«Откуда пришёл клиент», «Статус доставки», «Откуда поехал товар», «Способ оплаты».

Почему одной таблицей, а не четырьмя: устроены они одинаково — название, порядок,
признак «закрыт», — и разделение дало бы вчетверо больше одного и того же кода:
модуль, API и экран управления на каждый список. Пятый список потом — это одно
значение в перечислении, а не новая таблица.

Обобщённые справочники имеют дурную репутацию — они превращаются в свалку.
Защита здесь в том, что **перечень `kind` закрытый и лежит в коде**: вид списка
выбирается из перечисления, а не приходит из запроса. Сами списки при этом
пополняются из интерфейса — в этом их смысл.

- **Удаления нет**, только `isActive = false`: на значении висят заказы.
  Закрытое значение не предлагается при вводе, но остаётся в фильтрах и отчётах.
- **Название уникально внутри своего списка** (`@@unique([kind, name])`):
  два одинаковых значения в одном списке неотличимы в отчёте.
- **Значения засиживаются миграцией из рабочей таблицы продаж как есть** —
  вместе с квадратными скобками и заглавными буквами. Импорт сопоставляет
  строки файла по названию, и любое «причёсывание» превратилось бы
  в непопадание при разборе.
- **«Ошибочный ввод»** в списке статусов доставки — особое значение: удалять
  заказы может только админ, поэтому ошибка продавца не стирается, а помечается
  и выпадает из статистики как не состоявшаяся продажа.
- **`SHIPMENT_ORIGIN` — временный список.** В нём вперемешку витрины
  («Астана [Витрина Ncity]») и поставщики («Павлодар [Руслан] Заказ»). Решение
  от 24.09.2026: склады и поставщики будут отдельными моделями, и тогда этот
  список разбирается на две связи, а сам вид убирается. Подробности —
  в [roadmap.md](roadmap.md), этап 3.

### OrderComment — комментарий к заказу

Лента, а не поле в `Order`: заказ по очереди трогают продавец, сборщик и доставка,
и одна колонка означала бы «кто написал последним, тот и стёр предыдущего».

- **Правок и удалений нет** ни в API, ни в коде. Комментарий, который можно
  подтереть, не отвечает на вопрос «кто это решил», а ради него всё и заводилось.
- **Роль лежит снимком** (`authorRole`) — на момент написания: продавец мог стать
  менеджером, а «это писал продавец» часть смысла записи.
- **Имя читается по связи** с `User`, а не снимком: переименовали сотрудника —
  поправилось во всех его комментариях. Тот редкий случай, когда снимок вреден.
- **В журнал действий комментарии не дублируются:** в самой записи уже есть автор,
  роль и время, а удалить её нельзя.

### Два источника в одной таблице

Данные заказа приходят из двух мест, и почти половина полей — только из второго:

| Источник | Доступ | Что даёт |
|---|---|---|
| Shop API `/orders` | токен `KASPI_API_TOKEN`, работает | статусы, даты, деньги, адреса, накладная, курьер |
| GraphQL кабинета | кука сессии, вручную | сроки этапов, зона и способ доставки, модерация, сумма рассрочки, история событий, контакты склада |

Поля кабинета заведены **сразу** и пока пустые: заполнит их отдельная кнопка
на заказе. Заводим заранее, чтобы не делать вторую миграцию на те же данные.
В схеме каждое такое поле помечено комментарием «только кабинет».

Ключ сопоставления источников — **номер заказа** (`code`): ресурсного id Kaspi
(`kaspiId`) в данных кабинета нет вовсе.

### Order — заказ

Ключевые решения:

- **Происхождение — связь `salesPointId`, обязательная.** Заказ без точки продаж
  не посчитать ни в одном разрезе статистики. Отдельной колонки «источник» нет:
  на этот вопрос отвечает `salesPoint.type`, и второе поле с тем же смыслом
  однажды разошлось бы с первым.
- **`sellerId` — кто завёл заказ**, пусто у заказов площадки: их никто не заводил
  руками. Отдельного поля «кто создал» для интерфейса не нужно: пусто — показываем
  название точки, заполнено — имя сотрудника. `Restrict`: сотрудника не удаляют,
  а отключают, и заказ обязан остаться с подписью.
- **`placedAt`, а не `createdAtKaspi`.** Дата оформления: у Kaspi это
  `creationDate`, у офлайн-точки — момент ввода продавцом. Имя нейтральное
  намеренно — статистика за период обязана считать все источники по одной дате,
  а `createdAtKaspi` у офлайн-заказа означал бы событие, которого не было.
  Не путать с `createdAt`: тот про нашу запись.
- **Два составных индекса под статистику:** `[salesPointId, placedAt]`
  и `[sellerId, placedAt]`. Оба разреза — «точка за период» и «продавец
  за период» — читаются одним проходом по индексу, без сортировки.
- **Номер заказа уникален по всей таблице**, поэтому номера офлайн-заказов
  начинаются с букв: у Kaspi номер состоит только из цифр, и совпадение
  невозможно. При совпадении синхронизация сделала бы `upsert` в офлайн-заказ
  и затёрла его. На всякий случай в `saveOrders` есть и вторая защита: заказ,
  привязанный не к Kaspi-точке, синхронизация не трогает.
- **`linkedOrderId` — та же продажа на площадке.** Офлайн-продажа, уехавшая
  Kaspi-доставкой, лежит в двух записях сразу. Правило статистики: **заказ
  с заполненной привязкой в суммы не попадает** — считается заказ площадки,
  иначе выручка удвоится. В отчёте по точке такие заказы идут отдельной
  справочной строкой: «ещё N заказов на сумму X относятся к заказам Kaspi».
  Отдельного флага для этого не нужно, признаком служит сама привязка.
- **`deliveryType` необязательный.** У офлайн-предзаказа доставка ещё не
  выбрана, и записать туда «свою доставку» значило бы сохранить догадку.
  У заказов площадки значение есть всегда — оно вычисляется из полей Kaspi.
- **`preOrder` общий для всех источников.** Второго поля под офлайн нет
  намеренно: смысл тот же — товара нет в наличии. Затирания синхронизацией
  не будет, она не трогает заказы не из точки Kaspi.
- **Скидка двумя полями:** `discountPercent` числом и `discountComment` текстом.
  В рабочей таблице в одной колонке лежат и `0.05`, и «ликвидация», и «800тг»,
  и суммы вроде `420000`. Одним полем это не выразить: процент должен остаться
  числом, иначе по нему ничего не посчитать, а причина — текстом, иначе её
  некуда деть.
- **`paidAmount` и `balanceDue` — только офлайн.** Kaspi платит целиком и сразу,
  недоплат там не бывает. Остаток `0` интерфейс показывает как «оплачено» —
  отдельного статуса не нужно, он выводится из суммы.
- **`externalNumber` — номер руками, не ключ.** В рабочей таблице он заполнен
  примерно у трети строк (19 из 49 за сентябрь 2026): у продажи с витрины
  номера обычно нет вовсе. Ключом служит `code`, его выдаёт система.
- **`paymentMode` и `paymentMethodId` — разные вещи.** Первое — сырое значение
  Kaspi, второе — способ оплаты из нашего пополняемого списка.
- **Два статуса Kaspi хранятся сырыми** (`kaspiStatus`, `kaspiState`) рядом
  с нашим вычисленным `status`. Наш — производная; ошибёмся в правиле —
  пересчитать можно только из исходных значений.
- **Тип доставки отдельным полем** (`deliveryType`): у заказа он не меняется,
  а стадия меняется. Одним полем два измерения не выразить.
- **Склад — связь, а не строка.** `warehouseId` может быть пуст: Kaspi называет
  точку, которой ещё нет в справочнике, и терять из-за этого заказ нельзя.
  Рядом лежит `kaspiPickupPointId` (`6871008_PP27`) — по нему свяжем позже.
  Город отгрузки хранится снимком: справочник поправят, а заказ должен помнить,
  откуда уехал.
- **Адрес покупателя у Kaspi-доставки почти всегда пуст** — домашний адрес
  площадка не отдаёт. Заполнен он у своей доставки, где мы везём сами.
- **Телефон у архивных заказов замаскирован** (`+0(000)-000-00-00`). Сохраняем
  как есть: «телефона нет» и «Kaspi его скрыл» — разные вещи, и видно это
  только по значению.
- **`raw` и `rawCabinet` раздельно.** Источники разные, мешать их в одном поле
  нельзя — потом не понять, откуда какое поле.

### OrderEntry — позиция заказа

В списке заказов позиций нет: они приходят отдельным запросом на каждый заказ,
поэтому тянутся своим проходом. `entryNumber` уникален внутри заказа и служит
ключом повторяемой загрузки; у заказов без позиций ставится заглушка `-1`,
иначе их состав будут тянуть бесконечно.

`sku` — наш артикул (`offer.code` в Shop API, `merchantProduct.code` в кабинете),
по нему связь с `Variant`. Связь необязательная: заказ может приехать
по артикулу, которого ещё нет в каталоге, и это не повод его терять.

### OrderMarker и OrderStep — только из кабинета

`OrderMarker` — кто и когда двигал заказ (`APPROVED_BY_BANK`,
`ACCEPTED_BY_MERCHANT`). `OrderStep` — этапы `APPROVAL`, `ACCEPTANCE`,
`TRANSMISSION`, `TRANSIT`, `DELIVERY` со сроками. Ценны именно сроками:
`timeoutAt` — дедлайн, после которого Kaspi наказывает, а в Shop API таких дат нет.

Обе таблицы заведены заранее и будут пустыми до появления доступа к кабинету.

### Enum'ы заказов

`SalesPointType` (`KASPI`, `OZON`, `SITE`, `OFFLINE`), `OrderDeliveryType`
(`KASPI`, `PICKUP`, `OWN`), `OrderStatus` — 13 стадий. Значения обязаны совпадать
с `shared/src/constants/order-statuses.ts` и `sales-points.ts`.

`SalesPointType` не путать с `SalesChannel`: тот про канал размещения товара
(`Listing.channel`), этот — про происхождение заказа. Значения похожи, смысл
разный, и сводить их в одно перечисление нельзя — офлайн-точка не место
размещения карточки.

Стадии у офлайн-заказов те же, что у Kaspi: таблица, фильтры и подписи общие,
а отдельный набор означал бы два словаря статусов в одном реестре.

`PICKUP` и `OWN_DELIVERY` стоят в `OrderStatus` рядом со стадиями намеренно:
у таких заказов нет упаковки и передачи курьеру, и в кабинете они живут
отдельными разделами. Тип доставки при этом всё равно хранится своим полем.

Алгоритм вычисления стадии и сопоставление с разделами кабинета —
в [kaspi-api-integration.md](kaspi-api-integration.md), раздел 5.

## Миграции

| Миграция | Что делает |
|---|---|
| `init_users` | Создаёт `User`, `Customer` и enum `UserRole` |
| `auth_sessions_audit` | Создаёт `Session` и `AuditLog` |
| `warehouses` | Создаёт `Warehouse` |
| `catalog` | Создаёт `Category`, `Product`, `Variant`, `Listing`, `VariantStock`, `Fabric`, `FabricShade`, `VariantChange` и три enum'а |
| `warehouse_stats` | Добавляет в `Warehouse` снимок синхронизации: `kaspiOffersCount`, `kaspiTotalStock`, `kaspiStatsAt` |
| `variant_status` | Заменяет `Variant.isActive` на `Variant.status` (`ON_SALE` / `OFF_SALE`) |
| `orders` | Создаёт `Order`, `OrderEntry`, `OrderMarker`, `OrderStep`, enum'ы `OrderSource`, `OrderDeliveryType`, `OrderStatus`; добавляет в `Warehouse` контакты точки и `pickupType` |
| `sales_points` | Создаёт `SalesPoint`, `OrderComment`, enum `SalesPointType`; сидит системные точки `KASPI`, `OZON`, `SITE`; переименовывает `Order.createdAtKaspi` в `placedAt`; убирает `Order.source` и enum `OrderSource`; добавляет `Order.salesPointId` (с бэкфиллом на Kaspi) и `Order.sellerId` |

| `offline_orders` | Создаёт `DictionaryItem` и enum `DictionaryKind`, сидит четыре списка значениями из рабочей таблицы продаж; снимает NOT NULL с `Order.deliveryType`; добавляет `externalNumber`, `linkedOrderId`, `paidAmount`, `balanceDue`, `discountPercent`, `discountComment` и четыре связи со справочниками; добавляет `OrderEntry.note` |

Файлы миграций коммитятся в git — без них базу не поднять заново.

**`sales_points` написана руками, а не сгенерирована.** Переименование колонки
Prisma оформляет как `DROP` + `ADD`, то есть потеряла бы дату оформления у всех
существующих заказов. В файле стоит `RENAME COLUMN` — данные остаются на месте.
Любая будущая миграция с переименованием требует той же ручной правки.
