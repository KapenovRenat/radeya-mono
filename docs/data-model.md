# Модель данных

Схема Prisma — `server/prisma/schema.prisma`. Здесь описано назначение моделей, значимые
поля и принятые решения. Перечень моделей одной строкой — в [index.md](../index.md).

---

## Общие правила

- **Идентификаторы — UUID**, а не автоинкремент. Последовательный id выдаёт объём базы
  наружу и упрощает перебор чужих записей по URL.
- **Пароли только хешируются**, алгоритм — argon2id. Поле называется `passwordHash`:
  шифрование обратимо, хеш — нет, и имя поля должно об этом напоминать.
- **Учётные записи не удаляются, а отключаются** флагом `isActive`. Удаление рвёт ссылки
  в журнале действий и в заказах.
- **Имена таблиц и колонок — как в схеме Prisma**, без `@@map`. Единственный путь к базе —
  Prisma Client; сырой SQL пишется редко и только параметризованный.

## User — сотрудник

Вход в дашборд по логину. **Саморегистрации нет:** учётные записи заводит админ.
Первый пользователь создаётся, пока таблица пуста, — проверка и вставка выполняются
в одной транзакции, иначе два одновременных запроса создадут двух админов.

| Поле | Тип | Заметки |
|---|---|---|
| `id` | `String` UUID | Первичный ключ |
| `login` | `String` уникальный | Латиница, цифры и `. _ -`, нижний регистр. Нормализуется до записи |
| `passwordHash` | `String` | argon2id. Наружу не отдаётся никогда |
| `name` | `String` | Имя сотрудника |
| `position` | `String` | Должность, произвольный текст. Заполняет админ при создании |
| `role` | `UserRole` | Без значения по умолчанию — выбирается явно |
| `isActive` | `Boolean` = `true` | Отключение вместо удаления |
| `createdAt` / `updatedAt` | `DateTime` | |
| `createdById` | `String?` UUID | Кто завёл. Self-relation `UserCreatedBy`, `onDelete: SetNull`. У первого админа пусто |

Индексы: уникальный на `login`, обычный на `role` — по нему строится список сотрудников.

### enum UserRole

`ADMIN` · `MANAGER` · `SELLER`

Значения обязаны совпадать с `USER_ROLES` в `shared/src/constants/roles.ts` — там же
лежат подписи для интерфейса. Роль проверяется на сервере; скрытая кнопка в интерфейсе
защитой не является.

## Customer — клиент магазина

Регистрируется сам с витрины. **Отдельная сущность и отдельный вход**, не смешивается
с `User`: у клиента нет ни роли, ни должности, а права сотрудников к нему неприменимы.
Одна таблица на оба типа означала бы кучу пустых полей и проверку «а это точно сотрудник?»
в каждом запросе.

| Поле | Тип | Заметки |
|---|---|---|
| `id` | `String` UUID | Первичный ключ |
| `login` | `String` уникальный | Как у сотрудника |
| `passwordHash` | `String` | argon2id |
| `name` | `String` | Имя клиента |
| `phone` | `String` уникальный | **Обязательный.** Нормализуется до записи в `+7XXXXXXXXXX` — иначе `+7 777 123-45-67` и `87771234567` окажутся разными значениями и уникальность не сработает |
| `email` | `String?` уникальный | **Необязательный.** PostgreSQL допускает любое количество `NULL` в уникальном индексе, поэтому «нужен не всем, но не повторяется» — это одно поле без ухищрений |
| `isActive` | `Boolean` = `true` | |
| `createdAt` / `updatedAt` | `DateTime` | |

## Session — сессия сотрудника

В куке лежит **только идентификатор**, всё состояние — в этой таблице.
Отсюда главное свойство: сессию можно погасить мгновенно, удалив строку.
С подписанным токеном так не выйдет — он действует до истечения срока,
и уволенный сотрудник остаётся в системе.

| Поле | Тип | Заметки |
|---|---|---|
| `id` | `String` UUID | Он же значение куки `radeya_sid` |
| `userId` | `String` UUID | `onDelete: Cascade` — удалили пользователя, сессии ушли |
| `expiresAt` | `DateTime` | 7 дней от создания |
| `createdAt` | `DateTime` | |
| `userAgent` | `String?` | Для раздела «активные сессии» и разбора инцидентов |
| `ip` | `String?` | |

Индексы: `userId`, `expiresAt`.

Проверка при каждом запросе смотрит и срок, и `isActive` пользователя: отключили
сотрудника — его открытая вкладка перестаёт работать на следующем же запросе.

## AuditLog — журнал действий

Только вставка и чтение. Ни `update`, ни `delete` из кода: журнал, который
можно править, журналом не является.

| Поле | Тип | Заметки |
|---|---|---|
| `id` | `String` UUID | |
| `at` | `DateTime` | Когда |
| `userId` | `String?` UUID | Пусто у действий до входа — например неудачной попытки |
| `userLogin` | `String` | **Снимок** на момент действия |
| `userRole` | `String` | **Снимок** на момент действия |
| `action` | `String` | Значение из `AUDIT_ACTIONS` в `shared` |
| `entityType` / `entityId` | `String?` | Над чем действие |
| `before` / `after` | `Json?` | Состояние до и после. Пароли и хеши сюда не попадают |
| `ip` | `String?` | |

Индексы: `at`, `userId`, `action`.

**Связи с `User` намеренно нет.** Логин и роль хранятся копией: иначе после
переименования или смены роли вся прошлая история покажет сегодняшние значения,
а восстановить исходные будет неоткуда.

Запись делает `logAction()` из `server/src/lib/audit.ts`. Сбой записи не роняет
основную операцию — ошибка уходит в логгер, действие проходит: журнал не должен
обрушивать работу системы.

## Warehouse — склад (точка выдачи)

Справочник складов Kaspi. Заводится из выгрузки каталога, дальше правится руками.

| Поле | Тип | Замечание |
|---|---|---|
| `id` | `uuid` | — |
| `code` | `String @unique` | Наш короткий код: `PP3`. Ключ сверки при повторном импорте |
| `kaspiStoreId` | `String @unique` | Как в выгрузке и в заказах Kaspi: `6871008_PP3` |
| `kaspiCityId` | `String?` | Код города по КАТО. У части складов в выгрузке пусто |
| `name` | `String?` | **Наше** название точки. В выгрузке его нет |
| `isActive` | `Boolean @default(true)` | Точку закрыли — отключаем, не удаляем |
| `kaspiOffersCount` | `Int?` | Товаров на складе по данным последней синхронизации |
| `kaspiTotalStock` | `Int?` | Сумма остатков на тот же момент |
| `kaspiStatsAt` | `DateTime?` | Когда сделан снимок |
| `createdAt` / `updatedAt` | `DateTime` | — |

**Три последних поля — снимок, а не живые данные.** После импорта товаров
настоящие цифры считаются по `VariantStock`. Снимок нужен, чтобы видеть общую
картину по складам **до** импорта — сразу после загрузки каталога из кабинета.
Дата обязательна: без неё через месяц не понять, свежие это цифры или прошлогодние.
Обновление снимка не считается изменением справочника — иначе каждая
синхронизация показывала бы «обновлено 4», хотя склады те же.

**Почему отдельная таблица, а не код склада строкой у товара.** На склад сошлются
и товары, и заказы. Строкой опечатка в `PP3` молча создаст несуществующий склад,
и расхождение всплывёт на отчёте, а не на вводе.

**Что импорт не перезаписывает:** `name` и уже заполненный `kaspiCityId`. Выгрузка
их не знает, а повторная загрузка файла — обычное дело: стирать введённое руками
она не должна.

**Удаления нет.** Склад, пропавший из новой выгрузки, остаётся в справочнике:
на него ссылаются прошлые заказы.

Импорт — `saveKaspiWarehouses()` в `server/src/modules/warehouses/warehouses.service.ts`,
контракт эндпоинта — в [api-reference.md](api-reference.md).

## Каталог

Восемь моделей. Общий принцип: **товар один, продаётся он в нескольких местах**.
Всё, что различается между Kaspi, сайтом и OZON — цена, статус, идентификатор —
лежит в `Listing`. В `Product` и `Variant` остаётся только то, что верно везде.

```
Category ──< Product ──< Variant ──┬──< Listing        (канал: цена, статус, ID площадки)
                                   ├──< VariantStock   (склад: остаток)
                                   ├──< VariantChange  (история изменений)
                                   ├──> Fabric ──< FabricShade
```

### Category — папка каталога

`id`, `name`, `slug @unique`, `parentId?`, `path`, `sortOrder`, `isActive`.

Дерево произвольной вложенности, **наше собственное**: Kaspi отдаёт свои
`categoryPathCodes`, но категории для сайта и учёта мы строим сами.

`path` — денормализованный путь предков `/id1/id5/`: без него «все товары
поддерева» превращается в рекурсию на каждый запрос каталога. Уникальность
имени — внутри родителя (`@@unique([parentId, name])`): «Угловые» может лежать
и под диванами, и под кроватями.

### Product — карточка модели

`id`, `name`, `slug? @unique`, `categoryId?`, `brand?`, `description?`,
`kaspiFamilyId?`, `isActive`, `createdById?`.

Артикула и цены здесь нет. Импорт из Kaspi создаёт по товару на каждый артикул;
объединение в одну модель с несколькими тканями — ручной шаг, когда дойдём
до витрины. `kaspiFamilyId` хранится как есть и будет ключом такой склейки.

### Variant — модификация, то, что реально продаётся

| Поле | Тип | Замечание |
|---|---|---|
| `sku` | `String @unique` | **Артикул.** Ключ сверки с кабинетом и позициями заказов |
| `barcode` | `String?` | `ntin` из кабинета |
| `kaspiMasterTitle`, `kaspiTitle`, `kaspiModel` | `String?` | Названия кабинета. Пишет только синхронизация |
| `kaspiMasterSku`, `kaspiOfferId` | `String?` | ID карточки и предложения |
| `kaspiFileId`, `kaspiMerchantUid` | `String?` | Для будущих запросов в кабинет |
| `kaspiShopLink` | `String?` | Путь на витрину |
| `kaspiImages` | `Json?` | Массив `{ small, medium, large }`. Файлы не выкачиваем |
| `kaspiUpdates` | `Json?` | История изменений кабинета снимком |
| `kaspiUpdatedAt` | `DateTime?` | Когда кабинет менял товар |
| `anyKaspiDelivery`, `…Express`, `…Local`, `anyMerchantDelivery` | `Boolean` | Зеркало кабинета |
| `siteDelivery` | `Boolean` | **Наш пятый флаг:** заказ с сайта везём сами |
| `purchasePrice` | `Decimal?` | Закупка. **Наружу не отдаётся никогда** |
| `minChannelPrice`, `maxChannelPrice` | `Decimal?` | Минимум и максимум по каналам |
| `fabricId?`, `fabricShadeId?` | `uuid` | Ткань и оттенок для витрины |
| `isActive` | `Boolean` | Общий выключатель: снял — ушло со всех каналов |

**Почему артикул на модификации, а не на товаре.** Kaspi матчит позиции заказа
по артикулу конкретной модификации. Положим артикул на товар — заказы не сматчатся.

**Почему поля кабинета отдельно от наших.** `kaspiTitle` и `name` — разные вещи:
первое приехало из кабинета, второе правит человек. Держать их в одном поле
значит либо затирать правки синхронизацией, либо не видеть расхождения с площадкой.

**`minChannelPrice` / `maxChannelPrice` — осознанная денормализация.** Считать
минимум по размещениям на каждую строку списка — это запрос на каждый товар.
Пересчитываются при любом изменении цены.

### Listing — размещение на канале продаж

`variantId`, `channel` (`SITE | KASPI | OZON`), `status`, `price?`,
`discountPrice?`, `discountPercent`, `externalId?`, `externalSku?`,
`externalUrl?`, `publishedAt?`, `lastSyncedAt?`, `syncError?`.
`@@unique([variantId, channel])`.

**Само наличие записи означает «продаём здесь».** Нет строки — канал не
используется. Отдельный флаг «показывать на сайте» разошёлся бы с ценой.

**`status` пишет только синхронизация** — это то, что сейчас по факту на площадке.
Расхождение с `Variant.isActive` («мы продаём, а на Kaspi архив») — рабочий
сигнал для интерфейса, а не ошибка данных.

**Процент скидки считает сервер.** Обратный счёт от процента не воспроизводит
фактическую цену — расходится на сотни тенге.

### VariantStock — остаток на складе

`variantId`, `warehouseId`, `quantity?`, `preOrderDays`.
`@@unique([variantId, warehouseId])`.

Остаток физический, поэтому висит на модификации, а не на размещении: коробка
на складе одна, и показывать её тремя независимыми цифрами для трёх каналов —
прямой путь продать то, чего нет.

`quantity: null` — это не ноль, а «остаток не указан, товар под заказ».

**Срок предзаказа один на всех.** При импорте первое значение приезжает из
кабинета, дальше правится у нас и уходит обратно на площадку; у артикулов,
которых в Kaspi нет, его ставим сами. Второго, «кабинетного», поля нет
намеренно: два срока предзаказа на одну позицию означали бы, что где-то
показывается неверный.

Отсюда следствие для будущей синхронизации: `preOrderDays` **не
перезаписывается** данными кабинета молча — расхождение показываем, решение
за человеком.

### Fabric и FabricShade — ткани и оттенки

`Fabric`: `code @unique`, `name`, `type?`, `sortOrder`, `isActive`.
`FabricShade`: `fabricId`, `code`, `name`, `hex?`, `imageUrl?`,
`@@unique([fabricId, code])`.

**Kaspi названий тканей не знает** — ему важен только тип. Название и палитру
ведём у себя и выбираем на артикул из списка после синхронизации.

Оттенок принадлежит своей ткани: «серый Tessoro» и «серый Bravo» — разные
оттенки, общим справочником цветов их не выразить.

### VariantChange — история изменений артикула

`variantId`, `field`, `oldValue?`, `newValue?`, `source` (`KASPI_SYNC | MANUAL`),
`userId?`, `createdAt`.

Отдельно от `AuditLog`: тот про действия сотрудников, а сюда попадают и правки
человека, и то, что приехало из кабинета. Значения строками — история read-only,
считать по ней ничего не будем.

### Enum'ы

`SalesChannel` (`SITE`, `KASPI`, `OZON`), `ListingStatus` (`ON_SALE`, `OFF_SALE`),
`ChangeSource` (`KASPI_SYNC`, `MANUAL`). Значения обязаны совпадать с константами
в `shared/src/constants/sales-channels.ts`.

WB убран по решению от 16.09.2026 — вернуть его будет одной строкой в enum.
Ради этого каналы и сделаны значениями, а не колонками таблицы.

## Миграции

| Миграция | Что делает |
|---|---|
| `init_users` | Создаёт `User`, `Customer` и enum `UserRole` |
| `auth_sessions_audit` | Создаёт `Session` и `AuditLog` |
| `warehouses` | Создаёт `Warehouse` |
| `catalog` | Создаёт `Category`, `Product`, `Variant`, `Listing`, `VariantStock`, `Fabric`, `FabricShade`, `VariantChange` и три enum'а |
| `warehouse_stats` | Добавляет в `Warehouse` снимок синхронизации: `kaspiOffersCount`, `kaspiTotalStock`, `kaspiStatsAt` |

Файлы миграций коммитятся в git — без них базу не поднять заново.
