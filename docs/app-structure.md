# Структура фронта: маршруты, layout, компоненты

Next.js App Router, каталог — `front/src/app/`. Перечень страниц одной строкой —
в [index.md](../index.md).

---

## Дерево маршрутов

```
front/src/app/
├── layout.tsx                      # корень: шрифты, провайдеры, lang="ru"
├── providers.tsx                   # Redux-провайдер
├── globals.css
│
├── (shop)/                         # магазин, тема theme-shop
│   ├── layout.tsx
│   └── page.tsx                    → /
│
└── dashboard/                      # админка, префикс /dashboard
    ├── layout.tsx                  # общая обвязка: theme-dashboard
    ├── (auth)/
    │   ├── layout.tsx              # форма по центру, без сайдбара
    │   └── login/page.tsx          → /dashboard/login
    └── (main)/
        ├── layout.tsx              # сайдбар и рабочая область
        ├── page.tsx                → /dashboard
        ├── accounts/
        │   ├── layout.tsx          # RoleGuard: только ADMIN
        │   ├── page.tsx            → /dashboard/accounts
        │   └── _components/        # только для этой страницы
        └── kaspi-sync/
            ├── layout.tsx          # RoleGuard: только ADMIN
            ├── page.tsx            → /dashboard/kaspi-sync
            └── _components/
```

Ограничение по ролям стоит в `layout.tsx` раздела, а не на странице: так оно
накроет все будущие подстраницы, и его нельзя будет забыть на новой.

Папка с префиксом `_` исключена из роутинга: в неё складываются компоненты,
нужные одной странице. Маршрут создаёт только файл `page.tsx`.

### Как читать скобки

Папка **в скобках — группа маршрутов**: в URL не попадает, нужна только для того,
чтобы дать своей ветке отдельный layout. Папка **без скобок попадает в адрес**.

Отсюда устройство админки: `dashboard` без скобок даёт префикс `/dashboard`,
а `(auth)` и `(main)` — две разные обвязки внутри одного префикса.

### Почему сайдбар не в `dashboard/layout.tsx`

Вложенные layout в App Router **не заменяют родительский, а оборачиваются в него**.
Положи сайдбар на уровень `dashboard/layout.tsx` — он появится и на форме входа,
убрать его оттуда будет уже нечем.

Поэтому уровни разведены:

| Уровень | Что даёт | Кому |
|---|---|---|
| `dashboard/layout.tsx` | Класс темы `theme-dashboard` | всей админке, включая вход |
| `dashboard/(main)/layout.tsx` | Сайдбар, рабочая область | разделам админки |
| `dashboard/(auth)/layout.tsx` | Форма по центру, `max-w-sm` | входу |

## Темы

Токены объявлены в `front/src/styles/themes.css` **только внутри классов**
`.theme-shop` и `.theme-dashboard`; блока `:root` там нет. Значит страница без класса темы
остаётся без переменных, и цвета молча не применяются.

Класс вешается на layout своего раздела: магазин — в `(shop)/layout.tsx`,
админка целиком — в `dashboard/layout.tsx`.

Тёмный вариант — `.dark .theme-shop` и `.dark .theme-dashboard`, то есть переключается
классом `dark` выше по дереву.

## Вход в дашборд — как это устроено на фронте

Токен нигде не хранится. Сервер ставит httpOnly-куку, `baseApi` отправляет запросы
с `credentials: "include"`, браузер прикладывает куку сам. В `localStorage` не пишется
ничего: оттуда значение достаётся скриптом, из httpOnly-куки — нет.

| Файл | Что делает |
|---|---|
| `features/auth/auth-api.ts` | `login`, `logout`, `me`; общий тег кэша `Auth` |
| `features/auth/use-auth.ts` | `useAuth()` — текущий пользователь; `useLogout()` — выход |
| `features/auth/use-login-form.ts` | Состояние формы входа и отправка |
| `features/auth/auth-guard.tsx` | Не пускает в разделы админки без входа |
| `shared/api/error-message.ts` | Текст ошибки из ответа RTK Query |

**Отдельного слайса с пользователем нет.** Кэш RTK Query и так лежит в сторе,
`useAuth()` читает его из любого компонента. Копия в слайсе была бы вторым источником
правды и однажды разошлась бы с первым.

**Тег `Auth` связывает три эндпоинта:** после `login` и `logout` запрос `me`
перезапрашивается сам, руками состояние обновлять не нужно.

**`AuthGuard` — защита интерфейса, а не безопасность.** Реальную проверку делает сервер
на каждом запросе. Смысл компонента в том, чтобы не показывать пустой дашборд с ошибками
там, где данных всё равно не будет.

## Два входа

Вход сотрудника и вход клиента магазина — **разные страницы с разными темами**,
они не переиспользуются:

| Кто | Адрес | Статус |
|---|---|---|
| Сотрудник | `/dashboard/login` | заглушка, форма на этапе 1 |
| Клиент магазина | в разделе магазина, адрес не выбран | появится вместе с витриной |

Причина в модели данных: `User` и `Customer` — разные сущности со своими правилами входа,
см. [data-model.md](data-model.md).

## Компоненты

| Где | Что лежит |
|---|---|
| `front/src/components/<имя>/` | Свой компонент: `tree-list.tsx` + `style.module.scss`. Образец — `price-tag/` |
| `front/src/features/<фича>/` | Логика фичи, включая эндпоинты RTK Query |
| `front/src/shared/api/` | `baseApi` — единая точка RTK Query и теги кэша |
| `front/src/lib/utils.ts` | `cn()` — склейка классов Tailwind |
| `front/src/lib/` | Общая логика без привязки к фиче: `format.ts`, `use-pagination.ts` |

`usePagination()` — постраничный показ списка, который уже целиком в памяти. Отдаёт
срез страницы, номера кнопок с разрывами (`1 … 49 50 51 … 133`) и диапазон «показано
с — по». Для серверной выборки не годится: там страницу отдаёт запрос, а не срез
массива. Первым его использует таблица разбора выгрузки Kaspi.

Правило по цветам: **только токены темы**, без хардкода. Хардкод перестаёт переключаться
между магазином и админкой и между светлой и тёмной темой.

### Готовых UI-китов нет

Все компоненты пишутся сами. shadcn/ui, его CLI, `tw-animate-css`
и `class-variance-authority` из проекта удалены. Осталось: Tailwind для раскладки,
Sass для внутренностей компонентов, `cn()` для склейки классов, Lucide для иконок.

Base UI лежит в зависимостях, но пока не используется — он не приносит стилей, только
поведение и доступность для модалок и выпадающих списков. Понадобится, когда дойдём
до модального окна складов.

### Различия между магазином и админкой

Два механизма, применяются по ситуации:

**Тема** — когда отличается только внешний вид. Один компонент, значения токенов
переопределены в `.theme-shop` и `.theme-dashboard`. Ничего передавать не нужно,
компонент не знает, где он стоит. Образец — `price-tag/`.

**Проп `variant`** — когда отличий больше, чем цвет: другие размеры, отступы, состав
элементов. Значения — `"shop" | "admin"`:

```tsx
<Button variant="admin">Сохранить</Button>
```

```tsx
className={cn(styles.button, styles[variant])}
```

в `style.module.scss` при этом лежат `.shop { … }` и `.admin { … }`.

Если отличается и разметка, и поведение — это уже два разных компонента, а не варианты
одного. Например карточка товара на витрине и строка товара в таблице админки.

## /dashboard/orders — заказы

- Тип: страница dashboard, только ADMIN (`OrdersLayout` с `RoleGuard`).
- Данные: `GET /api/orders` (список), `POST /api/orders/sync` (синхронизация),
  `GET /api/sales-points`, `GET /api/orders/:id` и `POST /api/orders/:id/entries/sync`
  (окно заказа), `GET`/`POST /api/orders/:id/comments`.
- Ключевые компоненты: Tables, Button, Dropdown, OrderRow, OrderDetailsModal;
  хуки `useOrdersList`, `useKaspiOrdersSync`, `useOrderDetails`, `useOrderComments`.
- Файлы: `front/src/app/dashboard/(main)/orders/page.tsx`, рядом `layout.tsx`,
  `_components/order-row.tsx` со своим `order-row.module.scss`
  и `_components/order-details/` — окно заказа.

Сверху две кнопки синхронизации — за 2 года и за 3 месяца. Пока идёт прогон,
обе заблокированы (иначе второе нажатие запустит второй обход Kaspi), рядом
показывается процент и счётчики, есть кнопка «Остановить». Прогон
возобновляемый: хук крутит шаги до `done` и складывает счётчики сам,
потому что сервер считает только свой шаг.

После прогона на странице остаются итоги и два предупреждения, если есть:
склады не из справочника (заказы сохранены без связи) и незнакомые значения
Kaspi — по ним видно, что площадка завела новый статус.

Ниже поиск по номеру заказа — серверный, с задержкой 300 мс: заказов десятки
тысяч, отбирать их в браузере нечем, на странице лежит только текущая страница.

**При загрузке страница дёргает `GET /api/orders/kaspi?raw=1` и печатает
в консоль браузера сырые заказы за 14 дней**, разобранные и сводку значений.
Это отладочный вывод для сверки статусов со складом: каждый заход на страницу
означает запрос в Kaspi, поэтому период короткий. Сверка закончится — вывод
убрать вместе с запросом.
Рядом `DateRangePicker` — период по дате заказа.

**Границы суток считает клиент.** Пикер отдаёт `YYYY-MM-DD`, а это сутки
в поясе пользователя; хук переводит их в начало и конец дня и шлёт серверу
моментами. Сервер пояса не знает, и «за 21 сентября» в Алматы и в UTC — разные
наборы заказов.

### DateRangePicker

Кнопка с выбранным периодом, по нажатию — календарь в портале
(`useAnchoredPanel`: `position: fixed`, разворот вверх при нехватке места
снизу, закрытие по клику вне, Escape и прокрутке).

- Период выбирается двумя кликами: первый ставит начало и сбрасывает конец,
  второй — конец. Клик «назад» границы не ломает, они переставляются местами.
- Пока конец не выбран, диапазон дорисовывается под курсором: иначе непонятно,
  что попадёт в выборку.
- **Месяц листается отдельно от выбора**, поэтому начало можно взять в прошлом
  году, а конец — сегодня. Для заказов это обычный случай.
- Дни соседних месяцев показаны бледными, но кликабельны: иначе ради 31 августа
  пришлось бы листать назад.
- Выбранное применяется только по «Применить»; пока панель открыта, правки
  живут в черновике — случайный клик по дате не должен перезагружать таблицу.
  Незакрытый период применить нельзя: одна дата — это ещё не диапазон.
- Сетка всегда 6×7, чтобы панель не прыгала при смене месяца. Сегодняшний день
  обведён контуром — заливка занята выбором.

Даты разбираются в **местном** времени: `new Date("2026-09-01")` браузер
считает UTC, и в поясе UTC+5 дата уезжает на день назад. Поэтому в
`calendar.ts` разбор через конструктор с числами.

### Точка продаж — одна, и она задаёт таблицу

Выбор точки — общий `Dropdown` с поиском; пункта «Все точки» нет. По умолчанию
выбирается точка Kaspi — **по типу `KASPI`**, а не по названию: название можно
переименовать. Пока точка не выбрана, список не запрашивается вовсе — иначе
на миг приехали бы заказы всех точек.

Вид таблицы (`OrderTableKind`) — от вида точки:

| Вид | Точки | Колонки |
|---|---|---|
| `marketplace` | Kaspi (позже OZON, сайт) | Дата и время, Статус, Номер, Покупатель, Город, Склад, Доставка, Сумма, Планируемая доставка |
| `offline` | Офлайн-точки | Дата и время, Статус, Номер, Покупатель, Город, Кто создал, Доставка, Сумма, Планируемая доставка + Номер заказа, Откуда товар, Статус доставки, Откуда клиент, Оплата, Скидка, Оплачено, Остаток |

«Точки продаж» в таблице нет — она выбрана в фильтре и у всех строк одна.
Колонки описаны один раз словарём `COLUMNS` в `order-row.tsx` (заголовок, класс,
что показать), наборы — списками ключей `TABLE_COLUMNS`: добавить или переставить
колонку — поправить список.

**Фильтры справочников** (статус доставки, оплата, откуда товар, откуда клиент)
показываются только у офлайн-точки: у заказов площадки эти поля всегда пустые.
Смена точки их сбрасывает.

### Окно заказа

Клик по строке открывает `OrderDetailsModal` (общий `Modal`, шире обычного —
64rem). С клавиатуры — номер заказа: он кнопка, у строки таблицы роли кнопки нет.
Только просмотр и комментарии; правка полей — отдельная задача.

Блоки, каждый в своём файле `_components/order-details/`:

| Блок | Файл | Что внутри |
|---|---|---|
| Заказ | `summary-section.tsx` | Номер, дата, наша стадия и сырой статус Kaspi рядом, причина отмены, точка, кто создал (офлайн), доставка, склад, предзаказ, «передать курьеру до», плановая доставка, накладная, привязанный заказ |
| Покупатель | `customer-section.tsx` | Имя, телефон, город, адрес, комментарий к доставке, откуда отгрузка |
| Оплата | `money-section.tsx` | Сумма; у площадки — доставка и способ оплаты Kaspi; у офлайн-точки — оплата, оплачено, остаток, скидка и справочники |
| Состав | `entries-section.tsx` | Позиции: фото и наше название, если артикул нашёлся в каталоге; иначе название с площадки и «нет в каталоге». Кол-во, цена, сумма |
| Комментарии | `comments-section.tsx` | Лента и поле «Добавить» (`useOrderComments`) |

Общая раскладка блока — `details-section.tsx` (`DetailsSection`, `Fields`,
`Field` — пары «подпись — значение», пустое показывается прочерком).
Вид всех блоков — `style.module.scss` там же, порядок блоков — `index.tsx`.

**Состав заказа Kaspi грузится при первом открытии.** Окно сразу показывает
заказ из базы (`GET /api/orders/:id`). Если это заказ Kaspi и состава ещё нет,
`useOrderDetails` сам вызывает `POST /api/orders/:id/entries/sync` — один раз
на заказ; пока идёт запрос, загрузчик крутится только в блоке «Состав». Ответ
кладётся в кэш заказа, второй раз окно открывается без запроса к Kaspi. Ошибка
Kaspi — сообщение и «Повторить» в блоке, повтор только по кнопке.

### Строка таблицы заказов

Колонки — по виду таблицы, см. выше.

- **Планируемая доставка** — `plannedDeliveryAt`, срок, который назначил Kaspi
  (`attributes.plannedDeliveryDate`). Пусто у отменённых и у тех, где срок ещё
  не назначен: там прочерк, а не пустая ячейка.

- **Статус** — кружок плюс подпись из `ORDER_STATUS_LABELS`. **У каждой из 13
  стадий свой цвет** (решение пользователя, 29.09.2026) — словарь `STATUS_DOT`
  в `order-row.tsx`, сами цвета — классы `.status*` в `order-row.module.scss`.
  Палитра идёт по пути заказа: начало — холодные, сборка и передача — тёплые,
  в пути и выдача — бирюзовые и зелёные, отмена и возврат — красные,
  коричневый, серый. Словарь — `Record` по всем стадиям: новая стадия без цвета
  не соберётся. Каждый цвет — через токен `--status-<стадия>` с запасным
  значением. Кружок `aria-hidden`: смысл несёт текст. Тот же кружок —
  в окне заказа (`statusDotClass()`).
- **Покупатель** — «фамилия имя» («А Аскарбек»), под ними телефон серым.
  Склеиваем из `customerLastName` и `customerFirstName`: поле `name` у Kaspi
  содержит **только имя**, и показывать одно его значит терять фамилию.
  Порядок как в кабинете и на складе. У архивных заказов Kaspi отдаёт маску
  вместо номера — показываем как есть, это честнее пустой ячейки.
- **Сумма** — через общий `formatMoney`, по правому краю, моноширинными цифрами.

Размеры страниц те же, что у каталога (10/20/50): таблица общая, и два разных
набора сбивали бы с толку без пользы.

## /dashboard/products — каталог с деревом папок

- Тип: страница dashboard, только ADMIN (существующий ProductsLayout с RoleGuard).
- Данные: GET/POST /api/categories, PATCH/DELETE /api/categories/:id, GET /api/products/variants.
- Ключевые компоненты: TreeFolder, Tables, Loader, CatalogRow; хуки useProductCatalog
  и useCreateCategoryForm.
- Файлы: `front/src/app/dashboard/(main)/products/page.tsx`, рядом `layout.tsx`
  и `_components/catalog-row.tsx` со своим `catalog-row.module.scss`.

Слева дерево папок: первым «Все товары», затем ручные категории. На узле с детьми
есть отдельная кнопка раскрытия; нажатие названия выбирает папку и загружает её
товары вместе с подпапками. Навигация реализована обычными списками и кнопками:
Tab/Enter/Space, aria-expanded для раскрытия, aria-current для выбора.
Кнопка «Создать категорию» всегда создаёт корневую папку.

**Действия папки — в меню на три точки** (`Dropdown`): «Создать подпапку»
(только у корневых, третий уровень запрещён на сервере), «Переименовать»,
«Выше», «Ниже», «Удалить». Крайние позиции блокирует сам `TreeFolder`
по индексу в своём уровне. Перестановка сохраняется: `PATCH /api/categories/order`
пишет `Category.sortOrder`, обновление дерева оптимистичное — папка переезжает
сразу, при ошибке возвращается на место и показывается текст под деревом.
Порядок считается по полному дереву, а не по отфильтрованному поиском:
серверу нужен весь уровень, поэтому `useCategoryActions` берёт дерево из кэша
сам, а не из страницы.

**Поиск по папкам** — поле в шапке панели, фильтрация на клиенте: дерево
приходит целиком, ходить за двумя уровнями на сервер незачем. Регистр не важен,
«ё» приравнена к «е». Совпал родитель — показывается со всеми детьми; совпала
подпапка — показывается родитель с подошедшими детьми и раскрывается
автоматически, иначе найденное остаётся спрятанным в свёрнутой папке.
Раскрытие поиском складывается с тем, что человек раскрыл руками, и не стирает его.
Ничего не нашлось — «Ничего не найдено» вместо дерева. Поиск по папкам
не влияет на таблицу: выбор папки остаётся прежним, пока его не сменили.
Родитель фиксируется при открытии формы и показывается по имени. После создания
дерево обновляется, родитель раскрывается, новая папка выбирается.
Удаление сначала открывает встроенную форму подтверждения с названием папки.
Непустая папка не удаляется (ошибка сервера 409). После удаления выбранной папки
выбирается её родитель либо «Все товары»; удалённый ID убирается из раскрытых веток.
Редактирование меняет только название, не перемещает папку. Пока идёт сохранение,
действия и выбор в дереве блокируются. После переименования обновляется и таблица,
чтобы названия категорий в строках не оставались прежними.

Справа поиск по названию или артикулу (серверный, задержка 300 мс) и Tables.
Размер страницы — 10/20/50; переключение размера, папки и поиска сбрасывает страницу.
Одна строка данных — Variant. Общая категория принадлежит Product.

Порядок строк задаёт сервер: сначала товары в продаже, внутри — по алфавиту
названия, третьим ключом артикул. Подробности и подводные камни (порядок enum,
коллация базы) — в [api-reference.md](api-reference.md), `GET /api/products/variants`.

### Строка таблицы каталога

Колонки: галка выделения, Статус, Фото, Товар, Артикул, Цена Kaspi, Закупка,
Себестоимость, Поставщик, Склады, Остаток, Резерв, Ожидание, Доступно, Предзаказ,
Дней на складе, меню действий. Подписей у первой и последней нет, поэтому
в списке `COLUMNS` их нет — они добавляются к `CATALOG_COLUMN_COUNT` числом.
Шапка и количество колонок живут там же, где строка (`CATALOG_COLUMN_COUNT`
идёт в Tables как `columnCount` — им же считается colSpan пустого состояния).

- **Галка** в шапке выделяет всю страницу и показывает чёрточку вместо птички,
  когда выбрано не всё. Выделение живёт на `productId`, а не на модификации:
  переносится товар целиком, со всеми артикулами. Выбранная строка подсвечена —
  пачку переносят целиком, и важно видеть, что именно уедет.
- **Меню действий** закреплено у правого края (`position: sticky`), поэтому
  при горизонтальной прокрутке точки остаются рядом со своим товаром. Ячейке
  обязателен фон, иначе сквозь неё видно уезжающие колонки; на hover и на
  выбранной строке фон переопределяется под цвет строки. Пока в меню один
  пункт «Редактировать», неактивный: карточки товара ещё нет.
- **Закупка** показывается с символом валюты рядом с суммой, а не в подписи
  колонки: у соседних строк валюта разная, и общая подпись врала бы.
  `formatMoney` здесь не годится — он подставляет тенге.
- **Поставщик** обрезан по ширине с многоточием, полное название — в `title`:
  «[Петропавловск] Максим ИП Контур» без ограничения растягивает таблицу.
- **Себестоимость** — через `formatMoney`, с ₸: она всегда в тенге, в отличие
  от закупки.
- **Склады** — только чипы «код · название», по одному на строку.
  Код обязателен и стоит первым: им склад зовётся в Kaspi и в заказах.
  Название приходит из `Warehouse.name`; выгрузка Kaspi его не содержит,
  поэтому первым его заполняет импорт из МойСклада, где склады названы
  словами в заголовках колонок.
- **Остаток, Резерв, Ожидание, Доступно, Предзаказ, Дней на складе** — отдельные
  колонки, но **строкой на склад в том же порядке**, что в «Складах»: у товара
  на двух складах вторая строка каждой колонки — второй склад. Одна цифра
  на товар не сказала бы, на каком складе она лежит. Высота строки общая
  (`--stock-line` в `catalog-row.module.scss`) — иначе строки разъедутся.
  Пусто — прочерк, а не 0: «не указано» и «ноль» — разное. Отрицательное
  «Доступно» подсвечено: продано больше, чем есть и едет. Предзаказ 0 —
  прочерк: товар в наличии.
- **Сортировка** — стрелка у подписей Цена Kaspi, Закупка, Остаток, Резерв,
  Ожидание, Доступно, Предзаказ, Дней на складе. Кнопка — вся подпись, а не
  только стрелка. Клики по кругу: от большего к меньшему → от меньшего
  к большему → без сортировки; другая колонка заменяет прежнюю (решение
  пользователя: сортировка одна). Активная колонка выделена жирным,
  у `<th>` стоит `aria-sort`. Сортирует сервер — с учётом поиска, папки
  и фильтров, по всему списку, а не по странице.

### Фильтры над таблицей

- **Склады** и **Поставщики** — общий `Dropdown` с `multiple` и поиском.
  Пусто — все. Склады: товар **назначен** на склад (есть строка склада, даже
  с нулевым остатком) — решение пользователя; в колонках складов тогда видны
  только выбранные склады. Поставщики: первым пунктом «Без поставщика».
- Смена фильтра или сортировки возвращает на первую страницу и сбрасывает
  выделение: третья страница другого списка — случайный набор строк.
- Состояние — в `useProductCatalog()` (`warehouseIds`, `supplierIds`, `sort`,
  `order`, `toggleSort`); в адрес страницы пока не пишется.

### Панель над таблицей

- **«Переместить в папку»** — активна, когда выбран хотя бы один товар,
  и показывает их количество. Открывает `MoveToCategoryDialog`.
- **«Массовое редактирование»** — неактивна: редактора пока нет.

`MoveToCategoryDialog` — нативный `<dialog>`, как модалка аккаунтов: ловушка
фокуса, Escape и подложка достаются бесплатно. Внутри тот же `TreeFolder`
с поиском, но без действий над папками — без `onCreate`/`onEdit`/`onDelete`
компонент их не рисует. Дерево берётся **без** фильтра левой панели:
переносить можно в любую папку, а не только в найденную поиском.

Два шага в одном окне: выбор папки, затем подтверждение с названием и
количеством. Перенос затрагивает пачку товаров, промах по соседней папке
обнаружится не сразу — поэтому спрашиваем. Выбор «Все товары» снимает
категорию: это обзор, а не место хранения, и в подтверждении это сказано прямо.

- **Статус** — только кружок, без подписи; колонка сжата до ширины заголовка.
  Раз смысл несёт цвет, кружок подписан иначе: `role="img"` с `aria-label`
  и `title` из `LISTING_STATUS_LABELS` — подсказка под курсором и текст для
  скринридера. Цвета берутся из `--status-on-sale` и `--status-off-sale`
  с запасными значениями: заведёте эти токены в `styles/themes.css` —
  подхватятся сами.
- **Фото** — обычный `<img>`, не `next/image`: домен картинок Kaspi пришлось бы
  прописывать в `next.config.ts`, а адреса приходят из кабинета. Нет картинки —
  плашка «нет фото», а не пустая ячейка. Квадрат держится на `aspect-ratio: 1/1`,
  а не только на `height`: preflight Tailwind ставит `img { height: auto }`
  и перебивает модуль — высота считалась от пропорций картинки Kaspi.
  Второй подвох того же preflight — `img { max-width: 100% }`: когда колонок
  стало много, таблица ужимала ячейку фото, ширина картинки сжималась, высота
  оставалась, и квадрат превращался в полосу. Поэтому у картинки
  `max-width: none` и `min-width: 4rem`, у ячейки `min-width: 5rem`.
  Обрезка `object-fit: cover`, то есть по центру, без искажения.
- **Товар** — витринное название Kaspi, под ним серым наше из кабинета;
  второе прячется, когда совпадает с первым. Единственная колонка, которой
  разрешён перенос строк: остальные держат строку, и таблица уезжает
  в горизонтальный скролл (`.scroll` у Tables), а не сплющивается.
- **Цена Kaspi** — две строки по центру: сумма к оплате сверху, под ней мельче
  зачёркнутая старая цена и плашка процента. Подпись колонки берётся из
  `SALES_CHANNEL_LABELS`: цена принадлежит каналу, и появится вторая — «Цена Сайт».
  Общий `PriceTag` здесь не используется: он один в строку и крупный, таким
  он нужен витрине. Строки денег из API переводит `moneyToNumber()`, показывает
  `formatMoney()` — тот же, что внутри `PriceTag`. Процент берётся из ответа
  сервера, а не считается от двух цен. Цены нет — прочерк, не «0 ₸».
- **Предзаказ** — «сразу» при нуле дней, иначе «N дн.».
- **Склады** — плашки: наше название склада либо код, рядом остаток, если он
  известен. `quantity: null` («под заказ») цифру не показывает.

Размещение берётся по каналу (`SALES_CHANNELS.KASPI`), а не по индексу массива:
появится цена сайта — и порядок задаст сортировка по названию канала.

После успешной загрузки (в том числе обновления страницы браузером) console.log
выводит ответ сервера с меткой «[Каталог товаров] Ответ сервера:»: items, total,
page, pageSize, totalPages. Выводится только текущая страница, не весь каталог.
Повторный рендер с тем же объектом ответа не создаёт повторный лог. При смене
страницы, папки или поиска новый полученный ответ тоже выводится. Лог включён
по прямому запросу пользователя, в том числе в production. **В DTO есть
закупочная цена** — эндпоинт закрыт ролью ADMIN, но лог видно в консоли браузера
у всякого, кто сидит под админом.

### TreeFolder
- Тип: переиспользуемый управляемый компонент дерева, сам к API не обращается.
- Файлы: `front/src/components/tree-folder/page.tsx`, `style.module.scss`.
- Props: items (CategoryTreeNode[]), selectedId (string|null), expandedIds,
  onSelect(id), onToggle(id), onCreate?(parentId), onEdit?(category), onDelete?(category),
  disabled?, allLabel?, isLoading?, error?,
  onRetry?, className и нативные атрибуты div, кроме children/onSelect/onToggle.
- Данные и обработчики передаются из useProductCatalog. Создание передаётся в
  useCreateCategoryForm.open. Раскрытие ветки не меняет выбранную папку.
- API не вызывается самим компонентом; действия выполняются переданными обработчиками.
  «Все товары» не имеет кнопок редактирования/удаления. Перенос самих папок не реализован.

### Tables
- Тип: переиспользуемая управляемая таблица с серверной пагинацией, без API внутри.
- Файлы: `front/src/components/tables/page.tsx`, `style.module.scss`.
- children — строки tr с ячейками td; компонент оборачивает их в tbody.
- head — необязательные строки tr с th; компонент оборачивает их в thead.
- columnCount — число колонок для colSpan состояний загрузки/ошибки/пустоты (по умолчанию 1).
- caption — доступное название таблицы и области горизонтальной прокрутки.
- page, pageSize, total — значения ответа сервера; onPageChange и onPageSizeChange —
  обработчики переключения. Размеры страницы 10/20/50. Число страниц считается из total.
- Навигация: первая, предыдущая, следующая и последняя страница; номер текущей
  и число страниц, диапазон строк, выбор размера. Во время загрузки переходы заблокированы.
- isLoading — Loader; error — сообщение об ошибке и onRetry; total=0 — emptyLabel.
  Если total>0 и children не переданы — сообщение о необходимости добавить строки.
- className и нативные атрибуты div поддерживаются. Горизонтальная прокрутка
  остаётся внутри таблицы. Компонент не делает slice и не сортирует children.

### Подключение строк пользователем
В существующий Tables на странице передать head с названиями столбцов и
columnCount с их количеством. В children отрисовать catalog.items через свои
строки (либо компоненты, возвращающие tr), key — variantId. Не добавлять ещё один
table или tbody. Проверка загрузки, ошибки, пустого ответа и пагинация уже внутри Tables.
Цены приходят строками, остаток null означает «не указан»; выбранный Product
может иметь несколько строк-модификаций.

### Проверка пользователем
1. Открыть /dashboard/products: дождаться дерева и ответа с items в консоли браузера.
2. Верхней кнопкой создать корневую папку, через + справа — подпапку; у подпапки
   нет +. Прямой POST с подпапкой в parentId должен вернуть 400. Перезагрузить страницу:
   папки сохраняются в БД, выбранный пункт после перезагрузки — «Все товары».
3. Выбрать папку, найти товар по части названия/артикула, сменить размеры 10/20/50:
   новые данные видны в консоли, запросы идут на сервер.
4. Проверить первую/последнюю страницу, пустую папку, ошибку API и кнопку повтора;
   пока свои строки не добавлены, отображается служебное сообщение.
5. После добавления children проверить колонки, ключи variantId и colSpan.
6. Переименовать обе папки; дубликат имени внутри того же родителя должен дать 409.
7. Попытаться удалить папку с подпапкой или товаром — 409, данные сохраняются.
   Удалить пустую выбранную подпапку — выбирается родитель; пустую корневую — «Все товары».
8. Проверить отмену форм, повторное нажатие при сохранении, клавиатуру, узкий экран
   и горизонтальную прокрутку широкой таблицы.

## Loader — общий индикатор загрузки

- Тип: переиспользуемый компонент для страницы и содержимого кнопки.
- Данные: не обращается к API; родитель показывает его во время загрузки.
- Файл: `front/src/components/loader/tree-list.tsx`.
- Стили: `front/src/components/loader/style.module.scss`.
- Пропсы: `label?: string` (по умолчанию «Загрузка ...»), `size?: number | string`
  (диаметр кольца, по умолчанию "1.25em"), `hideLabel?: boolean` (по умолчанию false),
  `className` и нативные атрибуты span, кроме children. Числовой size задаётся
  в пикселях, строковый — с CSS-единицами, например "2rem". Размер текста не меняется.
  hideLabel скрывает видимую надпись и отключает таймер букв; label остаётся
  доступным скринридеру. Например: `<Loader size={32} hideLabel />`.
- Слева вращается кольцо из четырёх сегментов, справа выводится label. Цвет кольца
  и подсветки букв — #f23428 по прямому запросу пользователя (локальная переменная
  --loader-accent). Цвет и размер текста наследуются от страницы или кнопки;
  диаметр кольца задаётся size и по умолчанию зависит от размера шрифта.
  Буквы подсвечиваются по одной слева направо, по 160 мс на символ, затем цикл
  повторяется. Активная буква переключается клиентским таймером React, цвет задаётся
  классом letterActive без CSS-функции linear(). При смене label цикл начинается
  с первой буквы. Таймер очищается при размонтировании и смене текста; настройка
  уменьшения движения отслеживается через matchMedia и останавливает таймер. Внешних отступов
  и фиксированного размера контейнера нет; положение на странице задаёт родитель.
- Доступность: role=status, aria-live=polite, aria-atomic=true; декоративный
  индикатор и анимированные буквы скрыты от скринридера, ему доступна отдельная
  цельная строка label. При prefers-reduced-motion обе анимации отключаются.
- Подключение: именованный импорт Loader из `@/components/loader`.
  Для страницы использовать Loader без label либо с нужным текстом;
  внутри Button на время запроса заменить обычное содержимое на Loader,
  например с label «Сохранение». Самой кнопке выставить disabled и aria-busy
  по состоянию запроса. Компонент не блокирует действия самостоятельно.
- Страницы и кнопки автоматически не изменены; компонент готов к подключению.
- Проверка пользователем: стандартный и пользовательский текст, красное кольцо
  из четырёх сегментов, последовательная подсветка букв, размеры 16/32/48 пикселей,
  скрытие надписи через hideLabel, работа внутри кнопки
  и отключение обеих анимаций при
  включённом уменьшении движения. Команды и тесты агентом не запускались.

## /dashboard/imports — импорты

Набор независимых блоков, по одному на источник данных. Разделение блоками,
а не вкладками: источников будет несколько, они не связаны между собой,
и переключение скрывало бы от человека, что ещё можно импортировать.

Раздел закрыт ролью ADMIN в `imports/layout.tsx` — как и остальные,
ограничение стоит на layout'е, чтобы его нельзя было забыть на новой подстранице.

- Тип: раздел dashboard.
- Данные: `POST /api/imports/offline-orders/preview` и `/commit`,
  `GET /api/suppliers`, `POST /api/suppliers/import/preview` и `/commit`,
  `POST /api/products/moysklad/preview` и `/commit`,
  `GET /api/warehouses`, `POST /api/products/moysklad/stock/preview` и `/stock/commit`.
- Файл: `front/src/app/dashboard/(main)/imports/page.tsx`.

### Блок «Excel продаж офлайн-точки»

Выбор точки, файл, лист, счётчики разбора, значения не из справочников,
таблица предпросмотра, кнопка записи. Порядок шагов задан самим интерфейсом:
пока не выбран файл, нечего выбирать из листов; пока не разобран лист, нечего
записывать. Кнопка записи выключена до последнего — это единственное
необратимое действие на странице.

- Компоненты: `OfflineOrdersImport`, `ImportPreviewTable`.
- Хук: `useOfflineImport()` — `front/src/features/imports/use-offline-import.ts`.

### Блок «Поставщики из МойСклада»

Файл, счётчики разбора, таблица предпросмотра, запись. Листа в выгрузке
контрагентов один, поэтому выбор листа показывается только когда их несколько:
выбирать из одного варианта незачем.

Счётчики намеренно показывают и то, что **не** поедет в базу: «строк в файле»
и «не поставщики» рядом с «поставщиков в файле». Выгрузка содержит весь
справочник контрагентов, и без этой пары человек не увидит разницы между
«файл разобран целиком» и «файл обрезался на середине».

Про защиту от дублей сказано прямо в тексте блока, а не только в документации:
иначе повторную заливку будут бояться нажать.

- Компоненты: `SuppliersImport`, `SupplierPreviewTable` —
  `front/src/app/dashboard/(main)/imports/_components/`.
- Хук: `useSupplierImport()` — `front/src/features/suppliers/use-supplier-import.ts`.
- Стили: общий `_components/style.module.scss` на оба блока.

**Чего в интерфейсе пока нет:** экрана правки карточки поставщика.
`PATCH /api/suppliers/:id` готов, и Telegram ID проставляется только через него.

### Блок «Товары из МойСклада»

Закупочная цена с валютой, поставщик и сроки предзаказа по складам. Новых
товаров не создаёт — дополняет уже сохранённые, найденные по колонке «Код».

Блок стоит **после** поставщиков намеренно: у товаров поставщик ищется
в справочнике, и порядок блоков подсказывает порядок заливки. Залил товары
раньше поставщиков — часть карточек останется без привязки, и файл придётся
разбирать заново.

В тексте блока прямо сказано, что импорт товаров не заводит: иначе «нет
в каталоге» у сотни строк выглядит как поломка, а не как устройство импорта.

- Компоненты: `MoyskladProductsImport`, `MoyskladPreviewTable`.
- Хук: `useMoyskladImport()` — `front/src/features/products/use-moysklad-import.ts`.

### Блок «Остатки из МойСклада»

Отчёт «Остатки» — один файл на один склад, склада в файле нет. Поэтому первым
идёт выбор склада (общий `Dropdown` в режиме `select` с поиском), и только потом
файл: поле файла выключено, пока склад не выбран. Сменили склад при разобранном
файле — файл разбирается заново: список на обнуление у другого склада другой.

Склад повторён в счётчиках и **в подписи кнопки записи** («Записать в PP3 ·
Склад Астана: 312 товаров, обнулить 14»): залить файл Костаная в Астану импорт
сам не распознает, видеть это должен человек.

Счётчик «Обнулится» и таблица под ним — товары, которые у нас на этом складе
есть, а в отчёте нет. Показываются до записи: это единственное разрушающее
действие блока. Отрицательный остаток в таблице не подсвечивается ошибкой —
это правда учёта.

- Данные: `GET /api/warehouses`, `POST /api/products/moysklad/stock/preview`
  и `/stock/commit`.
- Компоненты: `MoyskladStockImport`, `MoyskladStockPreviewTable`, `StockZeroTable` —
  `front/src/app/dashboard/(main)/imports/_components/`.
- Хук: `useMoyskladStockImport()` — `front/src/features/products/use-moysklad-stock-import.ts`.
- Стили: общий `_components/style.module.scss`.

## Dropdown — меню и выбор значения

Один компонент на две задачи, режим задаётся пропом `mode`.

| `mode` | Что это | Пропы |
|---|---|---|
| `menu` (по умолчанию) | Меню действий на три точки | `items: DropdownItem[]` |
| `select` | Выбор значения вместо нативного `<select>` | `options`, `value`, `onChange`, `placeholder` |
| `select` + `multiple` | Выбор нескольких значений | `value: string[]`, `onChange(values: string[])` |

Умолчание — `menu`, чтобы места вызова, написанные до появления режимов
(`TreeFolder`, строка каталога), продолжали работать без правок.

**Мультивыбор (`multiple`).** Список не закрывается по клику — несколько
значений отмечают подряд. Сверху «Выбрано: N · Сбросить», у пунктов галочка
в квадрате — по нему видно, что отметить можно несколько. На кнопке: ничего —
`placeholder`, одно — его название, несколько — «`label`: N», полный список —
в подсказке `title`. У списка `aria-multiselectable`.
Типы — две ветки (`DropdownSingleProps` / `DropdownMultipleProps`): массив
без `multiple` или строку с ним TypeScript не пропустит. Решение 29.09.2026:
мультивыбор — пропом `Dropdown`, а не отдельным `MultiSelect`.

**Почему не нативный `<select>`.** В него нельзя добавить ни поиск, ни пометку
«закрыто» рядом со значением, ни будущую кнопку «+ Добавить». Справочник
«Откуда поехал товар» — уже десяток значений и будет больше, листать его
без поиска невозможно.

**Поиск включается пропом `searchable`, а не сам по длине списка.** Порог
«больше десяти значений — показываем поиск» означал бы, что интерфейс меняется
сам, когда в справочник добавили одиннадцатое значение.

**Пометка `note`** — отдельное поле варианта, а не часть `label`: поиск идёт
по `label`, и «(закрыто)» внутри названия находило бы половину списка.

С клавиатуры: Escape закрывает, стрелки ходят по вариантам по кругу, из поля
поиска стрелка вниз ведёт на первый вариант, вверх — на последний. Поле поиска
лежит **вне** элемента с `role="listbox"`: внутри него может быть только
`role="option"`, иначе скринридер объявит поле ввода вариантом выбора.

Подпись над выпадашкой — `<span>`, а не `<label>`: внутри компонента кнопка,
и клик по подписи открывал бы список и тут же закрывал его вторым нажатием.
Связь с подписью идёт через `aria-label` кнопки, его задаёт проп `label`.

- Файл: `front/src/components/dropdown/index.tsx`, стили — `style.module.scss`.
- Режим `select` используется в `OrderDictionaryFilters` на `/dashboard/orders`.
