# Kaspi Shop API — полная интеграция (справочник для нового проекта)

> Всё про работу с Kaspi Merchant/Shop API: авторизация, шифрование токена, эндпоинты,
> синхронизация, маппинг полей, статусы заказов, БД, грабли.
> Экспорт из проекта **radeya-analytics** (Next.js + Drizzle + PostgreSQL).
> Цель: скормить в новую сессию, чтобы помощник знал, как реализовывать с нуля.

---

## 0. Общая картина

```
Kaspi Merchant Cabinet → выдаёт постоянный API-токен (X-Auth-Token)
     │
     │  (токен шифруется Fernet и хранится в БД: kaspi_stores.encrypted_token)
     ▼
GET https://kaspi.kz/shop/api/v2/orders           — список заказов (по датам, постранично)
GET .../orders/{id}/entries                        — состав заказа (позиции/SKU)
GET .../orders/{id}                                — детальный заказ
     │
     ▼
Синк (chunked, stateful) → раскладываем в таблицы kaspi_orders / kaspi_order_entries
     │
     ▼
Бизнес-логика: статусы, маршрутизация, Telegram-уведомления
```

Формат ответов Kaspi — **JSON:API** (`{ data: [{ id, type, attributes, relationships }], meta, included }`).

## 1. Авторизация

- Токен берётся продавцом в **Kaspi Merchant Cabinet** (Настройки → API). Постоянный.
- Передаётся в заголовке **`X-Auth-Token`** на каждый запрос.
- Обязательные заголовки:
  ```
  X-Auth-Token: <token>
  Accept: application/vnd.api+json;charset=UTF-8
  User-Agent: Mozilla/5.0 ... Chrome/120 ...   (без него бывает 403/блок)
  ```

### Хранение токена — шифрование Fernet (важно)

Токен НЕ храним в открытом виде. Шифруем **Python-совместимым Fernet** (чтобы был совместим с легаси):

- Ключ = `PBKDF2-HMAC-SHA256(password = JWT_SECRET_KEY, salt = "kaspi-token-encryption-salt-v1", iterations = 100000, dklen = 32)`
- Первые 16 байт ключа — HMAC-подпись, последние 16 — AES-128 ключ.
- Токен Fernet v0x80: `base64url( 0x80 | timestamp(8, BE) | IV(16) | AES-128-CBC(PKCS7) | HMAC-SHA256(32) )`
- `JWT_SECRET_KEY` — env, **должен совпадать между окружениями**, иначе токены из дампа не расшифруются.

> В новом проекте, если легаси-совместимость не нужна — можно взять любое симметричное шифрование (AES-GCM). Но принцип: **токен в БД зашифрован, ключ в env**.

## 2. Эндпоинты

### 2.1 Список заказов — `GET /orders`

Query-параметры:
```
page[number]=0                                  # с нуля
page[size]=100                                  # до 100
filter[orders][creationDate][$ge]=<ms>          # от (Unix ms)
filter[orders][creationDate][$le]=<ms>          # до (Unix ms)
filter[orders][code]=980052874                  # (опц.) по номеру заказа
filter[orders][state]=...  filter[orders][status]=...   # (опц.)
```
- Даты — **Unix-миллисекунды (UTC)**.
- Пагинация: сначала `page[number]=0`, из `meta.pageCount` узнаём число страниц, затем догружаем.
- Ответ: `{ data: KaspiOrder[], meta: { totalCount, pageCount, pageNumber, pageSize } }`.

**⚠️ Ограничение пагинации:** Kaspi реально отдаёт **~10k позиций на диапазон**. Поэтому нельзя тянуть год одним запросом — бьём на **чанки по 3 дня** (`MAX_KASPI_DATE_RANGE_DAYS = 3`).

### 2.2 Состав заказа — `GET /orders/{id}/entries`

- `{id}` = `data[].id` из списка (JSON:API resource id, НЕ номер заказа).
- `page[size]=100`.
- Ответ `data[]` c `attributes`: `entryNumber, quantity, basePrice, totalPrice, deliveryCost, category{code,title}, offer{code,name}` + `relationships.product.data.id`.
- **`offer.code` = артикул** (то, по чему матчим с товарами продавца).

### 2.3 Детальный заказ — `GET /orders/{id}`

- Иногда отдаёт больше полей, чем список (проверять на реальных данных — напр. адрес доставки).
- `?include[orders]=user` — подтянуть данные покупателя (relationships).

## 3. Синхронизация (chunked, stateful)

Почему так: у Kaspi лимит пагинации + у serverless (Vercel) лимит 60с на функцию. Решение — **один чанк за вызов**, состояние в БД, UI поллит до `done`.

### 3.1 Синк заказов
- Диапазон (напр. год или 14 дней) → `buildChunks(from, to, 3дня)` → массив чанков.
- Состояние в `kaspi_sync_state`: `overallStart, overallEnd, totalChunks, chunksDone, ordersSynced, status`.
- Каждый вызов `stepSync`: берёт следующий чанк → `fetchOrdersForChunk(token, chunk)` (все страницы чанка) → `mapKaspiOrder` → **upsert батчами по 500** в `kaspi_orders` (`onConflictDoUpdate` по orderCode/id). `chunksDone++`.
- Параллелизм при массовой тяге — до 8 (`DEFAULT_PARALLEL_LIMIT`).
- `force: true` — перезапуск синка (для инкрементального обновления последних N дней).

### 3.2 Синк состава (entries) — отдельно
- Тянется **по одному заказу** (`/orders/{id}/entries`), поэтому дорого → отдельный процесс.
- `startEntriesSync`: считает заказы без entries. `stepEntriesSync`: берёт **батч 20** заказов без entries (parallel 6), тянет их состав, вставляет в `kaspi_order_entries` (`onConflictDoNothing`).
- Для заказов с 0 позиций (или ошибкой) вставляем **stub-строку** (`entryNumber = -1`), чтобы не тянуть их бесконечно.
- Состояние — `kaspi_entries_sync_state`.

### 3.3 Инкрементальный синк (cron/кнопка «обновить 14 дней»)
```
runOrdersSync(storeId):   startSync(from = now-14д, to = now, force) → крутим stepSync пока running
runEntriesSync(storeId):  startEntriesSync → крутим stepEntriesSync с лимитом шагов за вызов
```

| `kaspiDelivery.waybillNumber` | `waybill_number` | накладная |
| `kaspiDelivery.express` | `is_express` | |
| `customer.{firstName,lastName,name}` | `customer_name` | |
| `customer.cellPhone` | `customer_cell_phone` | |

**Поля из `raw_data.attributes`, которых нет отдельными колонками, но важны:**
- `preOrder` (bool) — **предзаказ** (товара нет в наличии).
- `plannedDeliveryDate` (ms) — плановая доставка клиенту.
- `kaspiDelivery.courierTransmissionDate` (ms) — фактическая передача курьеру (проставлена → «переданы на доставку»).
- `kaspiDelivery.courierTransmissionPlanningDate` (ms) — **план передачи курьеру** = дедлайн «Отвезите в пункт приёма».
- `kaspiDelivery.returnedToWarehouse` (bool) — гипотеза: вернулся на склад (проверить).

## 5. Статусы заказов (полная модель)

### 5.1 Поля-источники
`status`, `state`, `waybillNumber`, `preOrder`, `assembled`, `courierTransmissionDate`, `deliveryMode`, `isKaspiDelivery`.

Возможные значения:
- `status`: `APPROVED_BY_BANK`, `ACCEPTED_BY_MERCHANT`, `COMPLETED`, `CANCELLING`, `CANCELLED`, `RETURNED` (+ `RETURN_REQUESTED`/`KASPI_DELIVERY_RETURN_REQUESTED` — уточнять).
- `state`: `NEW`, `SIGN_REQUIRED`, `PICKUP`, `DELIVERY`, `KASPI_DELIVERY`, `ARCHIVE`.
- `deliveryMode`: `DELIVERY_PICKUP`, `DELIVERY_LOCAL`, `DELIVERY_REGIONAL_*`.

### 5.2 Два измерения
1. **Тип доставки** (фиксирован): Kaspi Доставка / Самовывоз / Своя доставка.
2. **Стадия**: Новый → (Предзаказ | Упаковка) → Передача → Переданы → Доставлен + отмены/возвраты.
Плюс флаг `preOrder`.

### 5.3 Алгоритм (сверху вниз, первый сработавший)
```
CANCELLED                     → Отменён
RETURNED                      → Возврат
RETURN_REQUESTED              → Ожидают решения по возврату
CANCELLING                    → Ожидают возврата/отмены
COMPLETED / DELIVERED         → Доставлен
ACCEPTED_BY_MERCHANT | waybill (принят):
    preOrder                  → Предзаказ
    deliveryType = pickup     → Самовывоз
    deliveryType = own        → Своя доставка
    courierTransmissionDate   → Переданы на доставку
    assembled                 → Передача
    иначе                     → Упаковка
state = SIGN_REQUIRED         → На подписании
иначе                         → Новый
```
**Тип доставки:**
```
state = PICKUP                             → pickup (самовывоз клиентом)
state = KASPI_DELIVERY | isKaspiDelivery   → kaspi
isKaspiDelivery = false                    → own (своя доставка)
иначе                                      → kaspi
```
⚠️ Не путать `DELIVERY_REGIONAL_PICKUP` (это Kaspi-доставка в ПВЗ) с настоящим самовывозом (`state=PICKUP`).

### 5.4 Готовый код — см. отдельный `kaspi-order-statuses-guide.md` (функции `deliveryType` + `mapOrderStatus`).

## 6. Важные бизнес-даты

- **«Принят мерчантом»** = `status=ACCEPTED_BY_MERCHANT` ИЛИ появился `waybillNumber` (накладная надёжнее — статус меняется не сразу).
- **Дата сдачи поставщику** (наш кейс) = `courierTransmissionPlanningDate − 2 дня` (Asia/Almaty). «Планируемой даты прибытия» в API НЕТ — есть только передача курьеру и доставка.
- **Все даты — Unix ms (UTC)**. Для отображения форматировать в нужный пояс (`Asia/Almaty`, UTC+5).

Индексы: уникальность заказа по `(store_id, order_code)` (или по Kaspi id); entries — по `(order_id, entry_number)`.

## 8. Грабли (обязательно учесть)

1. **Пагинация ~10k** на диапазон → чанки по 3 дня.
2. **60с лимит serverless** → синк по одному чанку за вызов, состояние в БД, поллинг.
3. **User-Agent обязателен** — без него Kaspi может отдать 403.
4. **Адрес клиента:** для **Kaspi Доставки** `deliveryAddress` часто **пустой** (Kaspi не отдаёт домашний адрес — приватность; вместо него «точка передачи» = ПВЗ/Zammler). Полный адрес есть у **своей доставки**. Проверять `детальный /orders/{id}` — иногда полей больше.
5. **Артикул = `offer.code`** из entries, матчить с кодом товара продавца (напр. из МойСклад/Excel).
6. **`entryNumber`** уникален внутри заказа — ключ для upsert позиций. Stub `-1` для заказов без позиций.
7. **Таймзона:** ms в UTC; границы дат для фильтров и отображение — считать в UTC+5 (Almaty), иначе «съезжает» день.
8. **Токен:** один и тот же `JWT_SECRET_KEY` между окружениями (иначе дамп с зашифрованными токенами не расшифруется).

## 10. Выгрузка каталога товаров — парсинг кабинета

**Решение принято, детали проектируются на этапе 2.**

Официальный API отдаёт только заказы. Каталога товаров в нём нет: в позициях заказа
приходит лишь `offer.code` (артикул) и название, без фотографий и характеристик.
Поэтому товары забираются **парсингом кабинета продавца**.

### Основной источник — выгрузка XML из кабинета

Кнопка «Действия с файлами» отдаёт два файла, и это **основной путь**:
стабильный формат вместо HTML, который поедет при первом редизайне.

| Файл | Что внутри | Проверено на выгрузке 15.09.2026 |
|---|---|---|
| `ACTIVE.xml` | Товары в продаже, `available="yes"` | 687 товаров |
| `ARCHIVE.xml` | Снятые с продажи, `available="no"` | 641 товар |

Статус берётся из того, **какой это файл**, а не из поля внутри.

```xml
<offer sku="LE634-2">
  <model>Диван прямой Леон, обивка велюр, 225см, серый [Arben  Noel steel]</model>
  <brand>RADEYA</brand>
  <availabilities>
    <availability available="yes" storeId="6871008_PP4" preOrder="0" stockCount="1.0"/>
    <availability available="yes" storeId="6871008_PP3" preOrder="0" stockCount="2.0"/>
  </availabilities>
  <cityprices>
    <cityprice cityId="591010000">284200</cityprice>
    <cityprice cityId="710000000">284200</cityprice>
  </cityprices>
</offer>
```

#### Что важно знать о формате

**`preOrder` — это дни, а не флаг.** Встречаются 0, 7, 8, 9, 10, 11, 12, 14, 15, 20,
22, 25, 30. Ровно там, где `preOrder="0"`, есть `stockCount` — 243 из 243 в ACTIVE.
Читается так: `preOrder=0` + `stockCount=2.0` → два в наличии; `preOrder=11` без
остатка → под заказ за 11 дней. Это и есть «Остатки: Не указаны» в кабинете.

**Складов у товара может быть несколько.** В ACTIVE у семи товаров их два,
в ARCHIVE у одного — **33**. Остаток свой на каждом складе. Одним полем не выразить.

**`cityId` — свойство склада, а не товара.** Связь строго один к одному:
`PP3 → 710000000`, `PP4 → 591010000`, `PP6 → 551010000`, `PP27 → 391010000`.
Код города по КАТО хранится в справочнике складов.

**`availability` и `cityprice` — два независимых списка**, связи в файле нет.
Сопоставляются по позиции: в реальной выгрузке порядок совпадает. Длины разошлись —
парсер не выдумывает, а помечает запись проблемной.

**Бренд не всегда RADEYA** — встречаются `Leset [Москва]`, `Fixcom`, `mebel-sibiri`.

**В ARCHIVE есть мусор:** 19 товаров с пустым `<model/>`, пустыми `<availabilities/>`
и `<price>0</price>` вместо `cityprices`. Парсер их не роняет, а помечает.

#### Чего в выгрузке нет

**Картинок, штрихкода, скидки и процента скидки.** Ни одного узла `picture`.
Поэтому схема гибридная: XML даёт костяк на 1328 товаров дёшево и стабильно,
парсер кабинета добирает превью, штрихкод и скидки — **отдельным шагом**.

#### Разбор названия

`<model>` содержит название и подназвание одной строкой. Правило: до первой запятой —
название, после — подназвание. У товаров без запятой («Порту») подназвание пустое,
это не ошибка.

> **В JSON кабинета названия два, и это разные строки.** Не «одно плюс код ткани» —
> проверено на диване Соул:
>
> ```
> masterTitle: RADEYA диван Соул, обивка велюр, 230х85х90 см, серый
> title:       диван прямой Соул, обивка велюр, 230 см, серый [Arben Ultra smoke]
> ```
>
> `masterTitle` — название карточки на витрине Kaspi (синяя ссылка в кабинете),
> `title` — наше собственное из выгрузки (серая строка под ней). У них могут
> отличаться и габариты, и порядок слов. Показываем оба: витринное как основное,
> наше — второй строкой.

### Как заходим

**Вход по номеру телефона и паролю.** Это принципиально: с **16 сентября 2026** Kaspi
требует код подтверждения на почту при входе через email, а для входа по номеру телефона
ничего не изменилось. Поэтому автоматизация полная — воркер логинится сам, полуручной
режим не нужен.

> Если когда-нибудь код начнут запрашивать и для телефона, автоматический вход станет
> невозможен. Запасной вариант: вход руками раз в N дней, дальше работа сохранёнными
> куками сессии до их истечения. Читать почту и доставать код автоматически мы не будем —
> это обход защиты аккаунта.

Реализация — **headless-браузер (Playwright)**, а не HTTP-клиент с куками: кабинет
на `kaspi.kz/mc/#/products` — SPA, данные приходят скриптами, в исходном HTML их нет.

Куки сессии сохраняются и переиспользуются: логинимся заново только когда сессия протухла.

### Зачем оставляем XML, если JSON отдаёт всё

Резонный вопрос: JSON — надмножество выгрузки, зачем тогда разбор `ACTIVE.xml`
и `ARCHIVE.xml`. Причина в том, **чем эти два источника отличаются по природе**.

| | XML-выгрузка | JSON кабинета |
|---|---|---|
| Что это | Официальная функция кабинета, «Действия с файлами» | Внутренний запрос SPA, недокументированный |
| Контракт | Заявленный формат, меняется предсказуемо | Может измениться без предупреждения |
| Как получить | Скачать файл руками, логин не нужен | Playwright, вход по телефону, 7–70 обращений |
| Полнота | Костяк: артикул, название, цена, остатки | Всё, плюс картинки, штрихкод, категории, скидка |
| Риск | Ручная операция | Блокировка по IP, смена внутреннего API, капча |

**Основной путь — JSON.** Он полнее и автоматизируется.

**XML остаётся ручным резервом.** Парсер кабинета — самое хрупкое место системы:
ляжет он в неудачный момент, и без выгрузки мы останемся вообще без данных.
Разбор XML уже написан и работает, поддержки почти не требует — выбрасывать
рабочий запасной путь ради экономии двухсот строк невыгодно.

Дополнительная польза: **сверка двух источников ловит ошибки**. Уже на первой
разведке всплыло расхождение 694 против 687 — по одному источнику его было бы
не видно вовсе.

> Решение пересмотреть, если JSON-парсер год отработает без сбоев, а XML так
> ни разу и не понадобится. До тех пор держим оба.

### Источник данных — внутренний JSON кабинета

**Разведано 15.09.2026, вариант принят.** Кабинет — SPA, и список товаров он берёт
своим же XHR-запросом. Забираем этот JSON, а не разметку: вёрстка поедет при первом
редизайне, а JSON переживёт смену интерфейса.

```
https://mc.shop.kaspi.kz/bff/offer-view/list?m=6871008&p=0&l=10&a=true
```

| Параметр | Значение | Что означает |
|---|---|---|
| `m` | `6871008` | Идентификатор продавца, он же в шапке кабинета |
| `p` | `0` | Номер страницы, **счёт с нуля** |
| `l` | `10` | Размер страницы |
| `a` | `true` | В продаже. Архив — предположительно `false`, не проверено |

Сходится с интерфейсом: 694 товара по 10 = 70 страниц, столько и нарисовано.

#### Форма ответа — проверено 15.09.2026

```json
{ "data": [ …товары… ], "total": 694 }
```

Список лежит в `data`, рядом `total` — сколько всего товаров **в этом режиме**.
Голым массивом ответ не приходит.

`l=100` работает: приходит ровно сто записей. `total` при этом остаётся полным,
поэтому по нему сразу видно, сколько страниц предстоит и не потерялось ли что-то
по дороге.

**694 — это только `a=true`.** Архив берётся отдельным обходом с `a=false`,
и статус товара определяется тем, в каком обходе он пришёл, — ровно как со
статусом из имени файла в XML-выгрузке.

> **Расхождение, требует разбора.** В кабинете «В продаже (694)», в `ACTIVE.xml` —
> 687 товаров. Семь штук где-то теряются. Вскроется при сопоставлении по `sku`.

#### Что в JSON есть — маппинг полей

Проверено на реальном ответе (товар `VE804`, мини-диван Веста).

| Наше поле | Путь в JSON | Тонкость |
|---|---|---|
| Артикул | `sku` → `"VE804"` | **Ключ сопоставления** с XML, нашей базой и позициями заказов |
| ID карточки Kaspi | `masterSku` → `"148612962"` | Он же в конце `shopLink` |
| ID оффера | `offerId` | Понадобится, когда начнём менять цены из админки |
| Название на витрине | `masterTitle` | Синяя ссылка в кабинете. Название карточки Kaspi |
| Наше название | `title` (= `model`) | Серая строка под ссылкой. Пришло из нашей выгрузки |
| Бренд | `brandName` → `"RADEYA"` | См. предупреждение о `brand` ниже |
| Цена | `price` → `247000` | Целое число, уже без валюты и пробелов |
| Цены по городам | `allCityPrices` | Объект `{ КАТО: { price, oldPrice, discount } }` |
| Штрихкод | `barcode.ntin` → `"0200222438302"` | **Берём `ntin`.** Рядом лежат `barcode` и `gtin` |
| Картинки | `imagesV2[]` | Готовые адреса `small` / `medium` / `large` |
| Категория | `categoryPathCodes` | От частного к общему: `Sofas → Living room → Furniture` |
| Остатки по складам | `availabilities[]` | Та же форма, что в XML: `storeId`, `stockCount`, `preOrder` |
| Коды складов | `points` → `["PP3"]` | Массив, как и ожидалось |
| Статус | `available` + `archivedAt` | |
| Ссылка на витрину | `shopLink` | Относительный путь на `kaspi.kz` |
| Обновлено | `updatedAt` | ISO с точностью до наносекунд |

**Картинок несколько, и адреса готовые.** `imagesV2[0]` — превью, остальные галерея.
Три размера на каждую, плюс флаги `verified`, `infographics`, `aiGenerated`.
Файлы не выкачиваем — сохраняем адрес.

**Чего в XML не было вовсе:** картинки, штрихкод, категории, скидка, `masterSku`,
`shopLink`, оценка качества карточки (`contentRating.ratingEvaluation`).

> **Штрихкод — это `ntin`.** В объекте `barcode` три поля: `barcode`, `ntin`, `gtin`.
> У проверенного товара `barcode` и `ntin` совпадают, `gtin` пуст — так что на одном
> примере разницы не видно. Берём `ntin`.

**`familyId` группирует модификации:** `[Master - Sofas][radeya]{Веста}{мини-диван}{прямой}{155}`.
Это готовый ключ для будущей связки `Product` → `Variant`: товары одной модели
в разных обивках получат одинаковый `familyId`. Проверить на товаре с модификациями.

> **Осторожно с брендом.** `brand: "Fixcom"`, но `brandName: "RADEYA"` и
> `brandCode: "radeya"`. Что такое `brand` — неясно, возможно производитель или
> поставщик. Берём `brandName`, но на выгрузке стоит сверить оба поля.

#### Цены: Kaspi хранит их сам, и по городам

Главное открытие: **процент скидки считать не нужно** — он лежит в данных.

```json
"allCityPrices": {
  "710000000": { "price": 247000, "oldPrice": null, "discount": 0 }
}
```

| Поле Kaspi | Что это | Наше название |
|---|---|---|
| `oldPrice` | Зачёркнутая цена. `null` — скидки нет | Основная цена |
| `price` | По ней покупают | Цена со скидкой (или основная, если скидки нет) |
| `discount` | Процент, посчитан площадкой | Процент скидки |

Терминология Kaspi (`oldPrice`) сбивает с толку: зачёркнутая цена не устарела,
она действующая, скидка считается от неё. В нашей модели она — **основная**.

**Цена лежит на каждый город отдельно** — в ответе около трёхсот записей по КАТО.
У проверенного товара во всех городах одно и то же число. Ради этого и весит
23.7 КБ ответ на десять товаров.

> **Открытый вопрос.** Бывают ли у одного товара разные цены по городам — не проверено.
> Парсер обязан это заметить: берём уникальные значения по всем городам, и если их
> больше одного, помечаем запись проблемной, а не берём первое попавшееся молча.

**Товар со скидкой — проверено 15.09.2026.** Детская кровать Рони 300 (`RON174`):

```json
{ "price": 299000, "oldPrice": 480000, "discount": 38 }
```

В карточке: крупная `299 000 ₸`, зачёркнутая `480 000 ₸`, плашка `-38 %`.
Формула сходится: `(480 000 − 299 000) / 480 000 = 37,7 %` → округление вверх
до `38 %`. Второй товар из того же ответа подтверждает:
`390 000 → 239 000`, `discount: 39` — считается `38,7 %`.

Значит округление **до ближайшего целого**, и наша формула из `shared/` даст
ровно то же число, что показывает Kaspi.

> **Открытый вопрос.** Сверка с `<cityprice>` в XML: какая из двух цен попадает
> в выгрузку у товара со скидкой. Теперь известен товар для проверки — `RON174`,
> достаточно найти его в `ACTIVE.xml`.

#### Три цены в нашей модели

| Цена | Где живёт | Замечание |
|---|---|---|
| Закупочная | у товара (`Variant`) | Не зависит от площадки. **Наружу не отдаётся никогда** — это маржа |
| Основная (Kaspi) | у размещения (`MarketplaceListing`) | На OZON будет своя |
| Со скидкой | там же | Пусто — товар без скидки |

**В админке вбиваем две цены, процент считаем сами** — решение принято, потому что
так устроен сам Kaspi. Обратный путь (`146 600 − 15 % = 124 610`) не воспроизводит
фактическую цену `124 990`: расходится на 380 ₸, а на 1328 товарах разъедется по всему
каталогу. Цены выставляются «красивыми» числами вручную, арифметика их не даст.

```
percent = round((price - discountPrice) / price * 100)
```

На реальной карточке: `(146 600 − 124 990) / 146 600 = 14,74 %` → `15 %` — ровно то,
что показывает Kaspi. Функция расчёта ляжет в `shared/`: считать одинаково нужно
и на сервере, и в форме.

Правила: цена со скидкой не больше основной и не ноль; пустая цена со скидкой —
это «скидки нет», а не «скидка 0 %».

> **На будущее, когда цены поедут из админки.** Понадобится различать желаемое
> и фактическое: мы отправили цену — доехала она или нет, видно только из следующей
> выгрузки. Поэтому в размещении будут наши значения и снятые с площадки, а их
> расхождение — сигнал, что изменение не применилось. Без этого ошибка отправки
> останется незамеченной.

### Статус продажи принадлежит площадке, а не товару

Один и тот же товар может продаваться на Kaspi и быть снят с продажи на OZON или WB.
Поэтому поля `isOnSale` у товара быть не должно: с приходом второй площадки оно
станет враньём, а третья потребует миграции.

Правильная форма — отдельная запись на пару «товар × площадка»:

```
MarketplaceListing
  variantId        ссылка на модификацию
  marketplace      KASPI | OZON | WB
  externalId       ID карточки на площадке — masterSku «148612962»
  externalOfferId  ID нашего предложения — offerId «6aa8e47e7a16394b32a31f8e»
  externalUrl      путь на витрину — shopLink «/p/...-148612962/»
  status           ON_SALE | OFF_SALE
  price            основная цена на этой площадке
  discountPrice    цена со скидкой, пусто — скидки нет
  updatedAt
  unique(variantId, marketplace)
```

Новая площадка тогда — новое значение перечисления, а не изменение схемы.
Сюда же со временем переедут `kaspiPrice` из модели `Variant`: цена площадки —
свойство размещения, а не товара. Своя цена сайта остаётся на товаре, магазин
не маркетплейс.

#### Три идентификатора, и все три нужны

| Поле | Источник в JSON | Зачем |
|---|---|---|
| `sku` **у товара**, не здесь | `sku` → `"VE804"` | Наш артикул. Ключ сопоставления с XML и позициями заказов |
| `externalId` | `masterSku` → `"148612962"` | Карточка в каталоге Kaspi. По нему — переход в магазин и запрос характеристик |
| `externalOfferId` | `offerId` | Наше предложение. Понадобится, когда цены поедут из админки |

`sku` — наш и один на все площадки, поэтому живёт у модификации. Два остальных
принадлежат конкретной площадке: на OZON у того же товара будут свои.

**Ссылку храним готовой, а не собираем из id.** `shopLink` приходит в ответе,
и брать его дешевле, чем угадывать формат адреса. При каждом обновлении
перезаписываем: slug зависит от названия и меняется вместе с ним. `externalId`
при этом остаётся стабильным якорем — если ссылка протухнет, товар найдётся по нему.

> **Мелочь к проверке.** `shopLink` относительный. Какой домен подставлять
> (`kaspi.kz/shop/p/...` или иначе) — не проверено, выяснится одним кликом.

Модель заводится на этапе сохранения в базу. Сейчас парсер просто отдаёт статус
в результате, но именно под эту форму.

### Характеристики товара — в списке их нет

В ответе `list` характеристик **нет**: `attributes: []`, `colourCode: null`, хотя цвет
у товара очевидно есть. Это эндпоинт списка — он отдаёт то, чем рисуется таблица.
Характеристики живут в карточке товара, её кабинет грузит отдельным запросом.

Косвенно признаки видны в двух местах: в `familyId` (`{Веста}{мини-диван}{прямой}{155}`)
и прямо в названии — `155х80х79 см`, `обивка велюр`, `темно-серый`, `[Anfora 27]`.
Разбирать название регулярками не будем: сломается на первом товаре с другим
порядком слов. Тот же довод, по которому отказались считать цену из процента.

**Где искать настоящие:** открыть карточку товара в кабинете и посмотреть её XHR.
Второй возможный источник — публичная витрина по `shopLink` / `masterSku`.

> Прежде чем городить второй проход по 1328 карточкам, нужно решить, какие
> характеристики действительно нужны в нашей админке. Для мебели это обычно
> габариты, материал обивки, цвет, механизм трансформации — и часть из них
> уже лежит в названии и `familyId`.

## 11. Дерево папок в админке — строится из данных Kaspi

**Задача:** на странице товаров в админке — иерархия папок, как в МойСклад:
`Кресла → Винсент / Луми / Овал`, внутри модели — обивки и размеры.

### Откуда берётся каждый уровень

| Уровень | Источник | Надёжность |
|---|---|---|
| Категории: `Мебель → Гостиная → Диваны` | `categoryPathCodes` | Высокая — это массив, разбирать нечего |
| Модель: `Веста`, `Винсент`, `Луми` | первая `{}` в `familyId` | **Гипотеза**, проверить на выборке |
| Товары внутри модели | офферы по `sku` | — |

`categoryPathCodes` идёт **от частного к общему** — для дерева разворачиваем:

```
["Master - Sofas", "Sofas", "Living room", "Furniture"]
 → Furniture → Living room → Sofas → Master - Sofas
```

### familyId разбирать по позициям нельзя — проверено

Гипотеза «первая фигурная скобка — модель» **опровергнута на втором же товаре**:

```
диван:   [Master - Sofas][radeya]{Веста}{мини-диван}{прямой}{155}
                                  └ модель └ тип     └ форма └ размер

кровать: [Master - Cribs][radeya]{Детская кровать}{Рони}{90}
                                  └ тип            └ модель └ размер
```

Порядок разный, количество скобок разное. Позиционный разбор соврёт на первой же
смене категории — а значит, товары уедут не в те папки.

**Решение: не разбирать вовсе.** Для дерева важно не то, что означает каждая
скобка, а то, что **`familyId` одинаков у всех модификаций одной модели**.
Этого достаточно: группируем по строке целиком, как по ключу.

| | |
|---|---|
| Ключ группировки | `familyId` целиком, без разбора |
| Название папки | наше, задаётся человеком |
| Черновик названия | можно предложить из `masterTitle`, но правится руками |

Квадратные скобки при этом читаются надёжно — они совпадают с полями
`categoryCode` и `brandCode` из того же ответа.

> Заодно снимается риск: Kaspi поменяет состав скобок — группировка переедет,
> но названия папок останутся нашими и на месте.

### Размер достаём по содержимому, а не по позиции

Размер в сантиметрах нужен в названии — по нему работники различают модификации.

```
{Веста}{мини-диван}{прямой}{155}   → 155
{Детская кровать}{Рони}{90}        → 90
```

**Правило: скобка, состоящая из одних цифр, — это размер.** Признак содержимого,
а не место в строке, поэтому перестановка скобок между категориями его не ломает —
в отличие от позиционного разбора, на котором мы уже обожглись.

Числовых скобок должно быть ровно одна. Ноль или больше одной — **помечаем товар
проблемным**, а не берём первую попавшуюся. Тот же принцип, что с ценами по городам:
парсер не угадывает.

> Это главный габарит — ширина. Полный размер живёт в названии: у дивана
> `155х80х79 см`, у кровати `90x200 см`. Если понадобятся все три, доставать
> их придётся оттуда или из характеристик, а не из `familyId`.

**Хранить отдельным полем, а не склеивать в название.** Строка «Веста 155» собирается
при показе. Если склеить при сохранении, размер перестанет быть данными: по нему
не отфильтруешь и не отсортируешь, а изменить его можно будет только правкой текста.

### Дерево — наши записи, а не вычисление на лету

Автоматика даёт черновик, но совпасть с нынешними папками она не может:

- **категории на английском** — `Sofas`, а не «Диваны»;
- **названия моделей обрежутся** — `familyId` даёт «Флоренс», а папка называется
  «Флоренс Кресло»; «Гравити» вместо «Кресло-мешок Гравити»;
- **половины папок в Kaspi нет вообще** — «Аксессуары», «Картины», «Безымянные
  товары», «Заказы клиентские» — это наша структура.

Поэтому узел дерева — строка в базе: код от Kaspi плюс **наше название**, которое
импорт не перезаписывает. Тот же паттерн, что у `Warehouse`, и он уже проверен.
Свои папки, которых в Kaspi нет, добавляются руками.

Товар **лежит** в узле, а не вычисляется из `familyId` при каждом показе: иначе
Kaspi переименует модель — и товар молча переедет в другую папку.

| `brand` vs `brandName` | Сверить на выгрузке | `brand: "Fixcom"` при `brandName: "RADEYA"` — неясно, что это |
| 694 против 687 | Сопоставить по `sku` | В кабинете «В продаже (694)», в `ACTIVE.xml` — 687 |

### Обязательные требования

- **Логин и пароль — только в корневом `.env`**, никогда в коде и не в git.
  По возможности отдельная учётная запись с минимальными правами.
- **Проверка результата обязательна.** Не нашли ожидаемые поля — это **ошибка**,
  а не «ноль товаров». Иначе редизайн кабинета молча обнулит каталог.
- **Пауза между обращениями.** Частые запросы приводят к блокировке по IP.
- **Лог каждого обмена** — что запросили, что получили, сколько разобрали.
- **Изоляция в отдельный модуль** `server/src/modules/kaspi-catalog/`: парсер
  ломается чаще всего, и его починка не должна задевать остальной код.
- **Ручной режим как запасной** — загрузка файлом, если парсер лежит.

### Чего делать не будем

Заказы парсингом не берём — для них есть API. Парсер сломается на первом редизайне,
а API стабилен: дублировать его разметкой значит менять надёжный путь на хрупкий.
