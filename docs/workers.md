# Воркеры — фоновые задачи

Фоновые процессы, которые работают без человека: забирают заказы Kaspi,
шлют уведомления поставщикам, следят за собой. Здесь — решения пользователя
(01.10.2026), устройство и порядок работ. Telegram-часть старой админки,
на которую опираемся, — [telegram-bot.md](telegram-bot.md).

---

## 1. Решения пользователя (01.10.2026)

| Вопрос | Решение |
|---|---|
| Интервал | Выбор в настройках, 1–10 минут, по умолчанию 2 |
| Наложение циклов | Следующий цикл не начинается, пока не закончился текущий |
| Период заказов | Выбор в настройках: 1, 2 или 3 месяца, по умолчанию 1 |
| Состав новых заказов | Подтягивается сразу воркером — по нему ищется поставщик |
| Журнал | Номер заказа, дата оформления и дата появления у нас, что сделано. Страница с пагинацией и фильтрами: заказ, период, название товара, тип события |
| Задержка перед отправкой поставщику | Выбор в настройках: 10 минут, 30 минут, 1 час; по умолчанию 1 час. Нужна, чтобы заказ, отменённый сразу после оформления, не плодил уведомлений |
| Отменили до отправки | Поставщику ничего не шлём |
| Отменили или вернули после отправки | Шлём поставщику отмену / возврат |
| Другие статусы | Поставщику не шлём: ему нужны новый заказ, отмена, возврат |
| Часы отправки | 08:00–17:00 по Астане, дни недели — галочками в настройках. Ночные уходят утром ближайшего разрешённого дня: суббота ночью при выключенном воскресенье — понедельник утром |
| Вид сообщения поставщику | Карточка-картинка, как в старой админке (см. ниже) |
| Telegram ID поставщика | Правится в настройках: выпадашка поставщиков → окно с данными и полем Telegram ID → «Сохранить» |
| Оповещения разработчику | Отдельная галочка и свой Telegram ID: состояние воркера — упал, восстановился, перезапущен |
| Применение настроек | Только после «Сохранить» |
| Самовосстановление | Обязательно: воркер чинится сам, каждое падение и восстановление — в журнал и разработчику |
| Где запускается | Отдельным процессом — на усмотрение разработки |
| Кому слать (01.10.2026) | Предзаказ — поставщику товара. **Заказ в наличии — кладовщику** склада отгрузки, как в старой админке |
| Дата сдачи на карточке | `plannedPointDeliveryDate` из **кабинета** Kaspi (GraphQL `getOrderDetails`), не из Shop API. Сохраняется в базу при каждом получении заказов — и кнопкой, и воркером. В окне заказа — строка «Планируемая дата прибытия» |
| Две позиции одного получателя в заказе | Две карточки — по одной на позицию |
| Бот | Тот же, что у старой админки. Старая админка выключена — дублей не будет |
| Отмена «в пути» (`CANCELLING`) | Как в старой админке: «Забрать с Zammler в г. X» |

### Карточки поставщику (образцы пользователя)

- **Новый заказ:** фото товара (заглушка, если фото нет), «ЗАКАЗ #6593 (1083386593)» —
  последние четыре цифры и полный номер, точка продаж («Каспи магазин»),
  «Отгрузка на Zammler в г. Астана», «Дата сдачи: 27 сентября», название товара,
  «Основная ткань: …», «Артикул изделия: …». Фон: предзаказ — тёмно-красный,
  наличие — тёмно-зелёный.
- **Отмена:** красная плашка «ОТМЕНА ЗАКАЗА», «Тип: Отмена клиентом»,
  товар, артикул, действие «→ Складировать».
- **Возврат:** плашка «ВОЗВРАТ ЗАКАЗА», «Тип: Возврат», товар, артикул,
  действие «→ Принять возврат».

## 2. Устройство

### Процессы

- **`server/src/worker.ts`** — отдельный процесс (`npm run worker`), рядом с API.
  Падение воркера не роняет API, а перезапуск API не обрывает цикл. На боевом
  сервере — второе приложение PM2.
- Запускается только при `WORKERS_ENABLED=true` в `.env`. Локально по умолчанию
  выключен: копия боевой базы с галочкой «Работает» иначе начала бы тянуть
  заказы и слать поставщикам с ноутбука.
- **API следит за воркером** (`worker-monitor.ts`): воркер раз в 15 секунд пишет
  «пульс». Пульса нет дольше 2 минут при включённом воркере — событие «воркер
  не отвечает» и оповещение разработчику; пульс вернулся — «снова на связи».

### Цикл

```
читаем настройки из базы
  выключен → ждём, проверяя настройки каждые 15 с
  включён  → цикл:
      блокировка PostgreSQL (одна на воркер и ручную кнопку синхронизации)
      заказы за период → сравнение со старым → события
      состав новых заказов (до 20 за цикл, свежие первыми)
      дата прибытия из кабинета — активным заказам (новые сразу, остальные раз в час)
      [этап 3] отправка поставщикам
  → ждём интервал (настройки сохранили — пересчитываем сразу)
```

- **Наложений нет:** следующий цикл планируется после конца текущего.
- **Потолок цикла — 10 минут** (`WORKER_RUN_TIMEOUT_MS`): дольше — цикл
  прерывается, событие «превышено время», дальше по расписанию.
- **Ошибка цикла** воркер не останавливает: событие, следующий цикл по расписанию.
  Три ошибки подряд — оповещение разработчику; первый успешный после них —
  «восстановился».
- **Падение процесса** — PM2 поднимает заново. Воркер при старте видит,
  что прошлый процесс не остановился штатно, — событие «перезапуск после сбоя».
- **Ручная кнопка синхронизации** на странице заказов берёт ту же блокировку.
  Занято воркером — 409 «повторите через минуту».

### Журнал

Пишется только то, что произошло; «цикл прошёл, ничего нового» — нет
(иначе 720 пустых строк в сутки). Номер заказа и даты хранятся копией —
журнал должен остаться как был. Фильтр по названию товара ищет по текущему
составу заказа: так находятся и события, записанные до загрузки состава.

## 3. Этапы

1. **Каркас и заказы** — процесс, цикл, блокировка, пульс и наблюдение,
   настройки и состояние, блок «Воркеры» в настройках, события заказов,
   состав новых заказов, оповещения разработчику, Telegram ID поставщиков.
2. **Журнал в интерфейсе** — страница с таблицей, пагинацией и фильтрами.
3. **Telegram поставщикам** — карточки-картинки, правила задержки и часов,
   отмены и возвраты, анти-дубль.
