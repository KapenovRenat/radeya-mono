## 1. Модель остатков (решение пользователя)

Цифры живут в `VariantStock` — строка на товар и склад.

| Поле | Что значит |
|---|---|
| `quantity` — Остаток | Сколько товара на складе **свободно**. Зарезервированное в остаток не входит |
| `reserved` — Резерв | Сколько обещано по заказам и ещё не уехало |
| `preOrderQuantity` — Предзаказ | Сколько продано под предзаказ, когда остатка не было, — нужно привезти |
| `expected` — Ожидание | Сколько заказано у поставщика и едет |
| `preOrderDays` | Срок предзаказа в днях — **не путать** с `preOrderQuantity` |

**Доступно = Остаток + Ожидание.**

| Событие | Остаток | Резерв | Предзаказ | Ожидание |
|---|---|---|---|---|
| Заказ, товар есть | −n | +n | | |
| Заказ, остатка нет (предзаказ) | | | +n | |
| Заказ уехал со склада | | −n | | |
| Отмена до отгрузки | +n | −n | | |
| Отмена предзаказа | | | −n | |
| Заказ поставщику → «Ожидается» | | | | +n |
| Заказ поставщику получен (приёмка) | +n | | | −n |
| Оприходование / списание | +n / −n | | | |

Почему остаток вычитается при резерве, а не «остаток 1 и резерв 1»: менеджер
видит в остатке ровно то, что можно продать, и не принимает один товар за два.

> **Импорт из МойСклада** делается один раз перед релизом, дальше МойСклад
> не используется. В МойСкладе «Остаток» **включает** резерв, поэтому при этом
> импорте остаток нужно записывать как «остаток МС − резерв МС». Сейчас импорт
> пишет остаток МС как есть — поправить до релиза.
>
> **«Доступно» в каталоге** пока считается по формуле МойСклада
> (`Остаток − Резерв + Ожидание`, `availableStock()` в `catalog.mapper.ts`).
> На новую формулу переходим вместе с этапом B и поправкой импорта —
> по отдельности они разошлись бы.

## 2. Документы склада — этап A (сделано)

Один документ на два вида: **оприходование** (`ENTER`) и **списание** (`WRITE_OFF`).
Позже третьим видом станет **приёмка** — вместе с заказом поставщику (этап C).

| | Оприходование | Списание |
|---|---|---|
| Когда | Излишек, возврат клиента, начальный остаток — товар без поставщика | Брак, порча, недостача |
| Остаток при проведении | +n | −n, в минус нельзя |
| Цена строки | Себестоимость товара, правится руками | Себестоимость товара на момент проведения, не правится |
| Себестоимость товара | При проведении становится ценой строки | Не меняется |

**Номер** — 5 цифр на экране (`00128`), уникальный, выдаёт PostgreSQL
(`autoincrement`). Удалённый черновик оставляет дырку: номера не переиспользуются.

**Сумма** = Σ количество × цена, считается на сервере в `Decimal` до тиына.

### Жизнь документа

```
черновик ──(Провести, ADMIN)──> проведён
   │
   └─(Удалить)─> удалён
```

- **Черновик** остатков не трогает. Его правят и удаляют сотрудники с правом `STOCK_DOCUMENTS_EDIT`
  (`ADMIN`, `MANAGER`).
- **Комментарий обязателен** — от 20 символов (решение пользователя 06.10.2026):
  пустое поле подсвечено красным «Заполните комментарий ОСМЫСЛЕННО!»,
  «Создать» и «Сохранить» неактивны; сервер проверяет то же.
- **Проведение** — галочка «Проведено», только с правом `STOCK_DOCUMENTS_POST`. Проводится по «Создать» / «Сохранить»: запись черновика
  и проведение — одна транзакция (остатки, себестоимость, история, отметка
  «проведён»). Ошибка на любом шаге — не меняется ничего, даже черновик
  не записывается. Новый документ можно провести сразу.
- **Проведённый** не правится и не удаляется. Ошибку исправляют встречным
  документом. Отмены проведения нет.
- Проводится ровно то, что на экране: галочка уходит вместе с документом.
- У оприходования рядом с «Цена» — подсказка «?»: изменение цены перезапишет
  себестоимость товара при проведении.

### Что делает проведение

1. Документ уже заблокирован записью черновика (`FOR UPDATE` при правке; новый
   до конца транзакции никому не виден) — его не поправят и не проведут дважды.
2. Оприходованию заводит недостающие строки `VariantStock` (товар впервые на складе).
3. Блокирует строки остатка `FOR UPDATE` **в порядке id товара** — два документа
   по одним товарам встают в очередь без взаимной блокировки.
4. Списание: проверяет, что остатка хватает каждому товару; нет — `409`
   со списком «артикул — есть N, списываете M», ничего не меняется.
5. Пишет остаток (`null` считается нулём), `stockAt = сейчас`:
   - оприходование: `receivedAt` — средняя дата поступления, взвешенная по
     количеству (старый остаток со старой датой + новая партия с сегодняшней);
   - списание: остаток стал 0 или меньше — `receivedAt` пуст.
6. Оприходование: цена строки → `Variant.costPrice`. Списание: цены строк
   и сумма документа пересчитываются по текущей себестоимости.
7. История товара (`AuditLog`, `STOCK_DOCUMENT_POSTED`): остаток и себестоимость
   «было → стало», в контексте — склад и номер документа.

### Права

Видеть — `STOCK_DOCUMENTS_VIEW`, править черновики — `STOCK_DOCUMENTS_EDIT`,
проводить — `STOCK_DOCUMENTS_POST` ([permissions.md](permissions.md)). В документе видна
себестоимость, поэтому `STOCK_DOCUMENTS_VIEW` выдают осознанно.

## 3. Склады без Kaspi

Справочник складов один — `Warehouse`. Склады Kaspi (`PP3`, `PP27`…) приходят
из выгрузки с `kaspiStoreId`. Наши склады без Kaspi (шоурум «Астана Ncity» в ТЦ)
заводятся руками в «Настройки → Склады»: код (`NCITY`) и название, `kaspiStoreId` пуст.

- Заказы Kaspi на такой склад не попадают: синхронизация ищет склад только
  среди тех, у кого есть `kaspiStoreId`.
- В XML для Kaspi такой склад попадать не должен — учесть при генерации XML.
- Код вида `PPn` руками не заводится: его потом приняла бы за свой выгрузка Kaspi.
- Товар «лежит в шоуруме» — это строка `VariantStock` склада шоурума.
  Перевозка между складами сейчас — списание + оприходование; позже —
  документ «Перемещение» четвёртым видом.

## 4. Дальше

**Этап B — резерв и предзаказ по заказам.** Шаг воркера заказов и офлайн-заказы:
таблица `OrderReservation` (строка на позицию заказа — защита от двойного резерва),
только новые заказы с точки отсечки. Нужен склад заказа — сначала задача
«Склад заказа не определён» из STATUS.md. Офлайн-заказу склад выбирает продавец.
Пришедший товар под предзаказ — предложено переводить в резерв автоматически,
старые предзаказы первыми (решения нет).

**Этап C — заказ поставщику и приёмка.** Статусы: создан → утверждён → ожидается
→ получен. «Ожидается» прибавляет ожидание, приёмка переводит его в остаток.
В заказе поставщику можно поправить себестоимость.
