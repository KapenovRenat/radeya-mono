# Окружение и конфигурация

Переменные окружения, конфиги сборки и команды работы с базой.

---

## Один .env на весь монорепозиторий

Файл лежит **в корне проекта**, отдельных `.env` в `server/` и `front/` нет.
Образец со всеми переменными — `.env.example`, копируется в `.env` и заполняется.

`.env` в git не попадает: `.gitignore` игнорирует `.env` и `.env.*` на любом уровне,
исключение только для `.env.example`.

### Как каждый пакет находит корневой файл

| Пакет | Механизм | Файл |
|---|---|---|
| `server/` (приложение) | `dotenv` с путём от `__dirname`, три уровня вверх — одинаково работает из `src/` через `tsx` и из собранного `dist/` | `server/src/config/env.ts` |
| `server/` (Prisma CLI) | `dotenv` с путём `../.env`; Prisma всегда запускается с `cwd = server/`, иначе не найдёт свой конфиг | `server/prisma.config.ts` |
| `front/` | Next.js читает `.env` только из своей папки и вверх не поднимается, поэтому корневой файл подгружается явно в конфиге | `front/next.config.ts` |

> **Плата за удобство.** Раньше секреты сервера физически не лежали рядом с фронтом.
> Теперь процесс Next.js при старте получает в `process.env` в том числе `DATABASE_URL`.
> В браузер это не утекает — наружу Next отдаёт только переменные с префиксом
> `NEXT_PUBLIC_`, — но правило становится жёстче: **никакой секрет не должен получить
> префикс `NEXT_PUBLIC_`**, иначе он окажется в бандле, который открыт любому посетителю.

### Переменные

| Переменная | Кто использует | Назначение |
|---|---|---|
| `NODE_ENV` | server | `development` / `test` / `production` |
| `PORT` | server | Порт API, по умолчанию 4000 |
| `DATABASE_URL` | server, Prisma | Строка подключения к PostgreSQL. Спецсимволы в пароле кодируются: `@` → `%40`, `:` → `%3A`, `/` → `%2F` |
| `CORS_ORIGIN` | server | Разрешённые источники, несколько — через запятую |
| `LOG_LEVEL` | server | `debug` / `info` / `warn` / `error` |
| `KASPI_MERCHANT_ID` | server | Идентификатор продавца в Kaspi, только цифры. Необязательный: без него не работает загрузка каталога из кабинета, остальное поднимается |
| `NEXT_PUBLIC_API_URL` | front | Адрес API для браузера |

**Куки сессии кабинета Kaspi в `.env` нет и не будет.** Она вставляется в поле на
странице «Синхронизация с Kaspi» и живёт только в памяти процесса, пока выбрано
«запомнить». Это доступ в кабинет — на диске ему не место: оттуда он уезжает
в бэкап, в образ и однажды в git.

Набор переменных сервера проверяется схемой zod на старте: чего-то не хватает —
процесс падает сразу с внятным текстом, а не через час в случайном запросе.
Схема — `server/src/config/env.ts`.

## База данных и миграции

Все команды запускаются из корня проекта.

**Создать миграцию по изменениям в схеме:**

```bash
npm run prisma:migrate --workspace=server -- --name имя_миграции
```

**Сгенерировать клиент после правки схемы:**

```bash
npm run prisma:generate --workspace=server
```

**Открыть Prisma Studio:**

```bash
npm run prisma:studio --workspace=server
```

### Создание администратора

Публичного эндпоинта регистрации нет. Первый администратор заводится из терминала:

```bash
npm run create:admin --workspace=server
```

Скрипт спросит логин, имя, должность и пароль (ввод пароля не отображается),
проверит их по правилам из `shared` и создаст пользователя с ролью `ADMIN`.
Остальных сотрудников админ заводит уже из дашборда.

Файл — `server/src/scripts/create-admin.ts`.

### Shadow-база

`prisma migrate dev` создаёт временную **shadow-базу**, чтобы проверить, что миграция
накатывается на чистую схему. Роли нужно право создавать базы:

```bash
psql -U postgres -c "ALTER ROLE radeya_app CREATEDB;"
```

Право нужно **только для разработки**. На сервере гоняется `prisma migrate deploy` —
он shadow-базу не создаёт, и `CREATEDB` продакшен-роли выдавать не надо.

### Миграции в git

Папка `server/prisma/migrations/` **не игнорируется** и обязана быть в репозитории:
без файлов миграций базу нельзя поднять заново и нельзя воспроизвести состояние схемы.

### Генерацию клиента делать при остановленном сервере (Windows)

`prisma generate` перезаписывает файлы в `server/src/generated/prisma/`. Пока их
держит запущенный `tsx watch`, Windows не даёт их заменить: **миграция проходит,
генерация молча не срабатывает**. Симптом — база уже новая, а клиент старый:

```
Unknown argument `status`. Did you mean `stocks`?
```

В списке доступных полей при этом видно прошлую версию схемы — по нему и
опознаётся ситуация. Порядок: остановить `dev:server` → `prisma:migrate`
или `prisma:generate` → запустить сервер обратно.

Перезапуска мало, если процесс остался жив в другой вкладке терминала: старый
сервер продолжает держать порт и отвечать старым клиентом. Проверить, кто слушает:

```bash
netstat -an | grep -i listen | grep 4000
```

## Зависимости сборки

| Пакет | Где | Зачем |
|---|---|---|
| `sass` | `front`, devDependency | SCSS-модули (`*.module.scss`). Без него Next.js падает на импорте стилей. Ставится как `npm i -D sass -w front` |
| `dotenv` | `front` и `server` | Подгрузка корневого `.env`. Во фронте объявлена явно, а не берётся из подъёма зависимостей монорепо — иначе сборка ломается от чужой установки |
| `@prisma/adapter-pg` | `server` | Prisma 7 ходит в PostgreSQL через драйвер-адаптер |
| `tsx` | `server`, devDependency | Запуск TypeScript в разработке без сборки |

---

## Известные ограничения

- `shared/` отдаёт TypeScript-исходники, а не собранный пакет. Для разработки этого хватает
  (`transpilePackages` на фронте, `tsx` на сервере), для продакшен-сборки понадобится бандлер.
