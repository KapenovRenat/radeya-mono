## Как мы работаем

Правило изменилось по ходу работы, действующая версия — в [AGENTS.md](AGENTS.md):

## Сделано

### Каркас и окружение

- Монорепозиторий npm workspaces: `server`, `front`, `shared`. Работает end-to-end.
- **Единый `.env` в корне.** Отдельных `.env` в пакетах нет. Как каждый пакет его
  находит — в [docs/deployment.md](docs/deployment.md).
- Готовых UI-китов нет: shadcn/ui, `tw-animate-css`, `class-variance-authority`
  удалены. Остались Tailwind (раскладка), Sass (компоненты), `cn()`, Lucide.
  `@base-ui/react` лежит в зависимостях без использования — на будущее, под модалки.
- SVG через SVGR (`@svgr/webpack` + правило в `next.config.ts`, `removeViewBox: false`).

### Маршруты фронта

### Этап 1 — доступы (готово)

- Модели `User`, `Customer`, `Session`, `AuditLog`. Две миграции: `init_users`,
  `auth_sessions_audit`.
- Вход **по логину**, сессия в **httpOnly-куке**, состояние сессии в таблице —
  можно погасить мгновенно. Пароли argon2id (`@node-rs/argon2`).
- Отказ при входе всегда единый 401, без разделения «нет логина» / «неверный пароль».
  При несуществующем логине сравнение всё равно выполняется по фиктивному хешу —
  иначе разницу видно по времени ответа.
- `requireAuth`, `requireRole(...roles)`. На фронте `AuthGuard` и `RoleGuard` —
  это удобство интерфейса, настоящая проверка на сервере.
- Первый админ — **командой в терминале**, публичного эндпоинта регистрации нет:
  `npm run create:admin --workspace=server`.
- Раздел «Аккаунты»: таблица сотрудников, создание через модалку на нативном
  `<dialog>`, вкладка «История» с журналом действий.
- Журнал: `logAction()`, снимок логина и роли на момент действия, только вставка
  и чтение, сбой записи не роняет операцию.

### Синхронизация с Kaspi — два источника (готово, в базу не пишет)

**Разбор XML-выгрузки.** `POST /api/kaspi-catalog/preview` — файлы `ACTIVE.xml`
и `ARCHIVE.xml` из кабинета. Счётчики, список складов, таблица, фильтр
«только с проблемами». Остаётся **ручным резервом**.

**Загрузка из кабинета.** `POST /api/kaspi-catalog/fetch` — обход внутреннего
JSON `mc.shop.kaspi.kz/bff/offer-view/list`, два режима за вызов (в продаже
и архив), по 100 товаров с паузой 500 мс. Это **основной путь**: в JSON есть
картинки, штрихкод, категории, скидка, `masterSku`, `familyId` — всё, чего нет в XML.

- Кука сессии вставляется в поле на странице, хранится **только в памяти
  процесса** и только при «запомнить». Ни в `.env`, ни в базу, ни в логи.
- Полнота сверяется с `total` из ответа кабинета; обрыв возвращает частичный
  результат и номер страницы, чтобы не терять полученное.
- Спорные места помечаются проблемой, а не разбираются наугад.
- Таблица: картинки, штрихкод, цены со скидкой, размер, склады, статус.
  Поиск по артикулу и обоим названиям, фильтр по статусу, пагинация 10/20/30.

### Справочник складов

Модель `Warehouse`, миграция `warehouses`. `POST /api/warehouses/import-kaspi` —
импорт из предпросмотра выгрузки и из кабинета, повторяемый: сверка по `code`,
наше название и заполненный город не перезаписываются, пропавшие склады
не удаляются. Рядом со справочными полями — снимок синхронизации
(`kaspiOffersCount`, `kaspiTotalStock`, `kaspiStatsAt`).

Кода города (КАТО) в JSON кабинета нет — `cityId` оттуда всегда пуст и понимается
как «неизвестно». Дозаполняется разбором XML-выгрузки или руками.

### Каталог — товары пишутся в базу (готово)

Восемь моделей: `Category`, `Product`, `Variant`, `Listing`, `VariantStock`,
`Fabric`, `FabricShade`, `VariantChange`. Миграции `catalog`, `warehouse_stats`,
`variant_status`. Подробности — в [docs/data-model.md](docs/data-model.md).

- **Артикул на `Variant`**, цена и статус площадки — в `Listing`, остаток —
  в `VariantStock`. Наличие `Listing` на канале означает «продаём здесь».
- **Два статуса.** `Variant.status` — наше решение продавать, одно на все каналы.
  `Listing.status` — что по факту на площадке. Расхождение — рабочий сигнал.
- **Ткани у нас.** Kaspi знает только тип ткани; название и палитру ведём сами
  (`Fabric` → `FabricShade`), на артикул выбираем вручную после синхронизации.
- `POST /api/products/import-kaspi` — **заводит только новые** артикулы.
  Существующий пропускается целиком: у него уже может быть наша категория,
  ткань, закупка и цена сайта.
- Загруженное сохраняется отдельным нажатием, после просмотра таблицы.
  Синхронизация в базу не пишет никогда.
- В таблицу идут только новые товары; всё сохранённое скрыто, иначе на второй
  синхронизации из полутора тысяч строк интересны три.

## Принятые решения (не пересматривать без причины)

| Решение | Почему |
|---|---|
| Сессии в таблице БД, не JWT | Уволил сотрудника — доступ закрывается сразу |
| Пароль сотрудника постоянный, без смены при первом входе | Решение пользователя. Следствие в рисках роадмапа |
| Первый админ только из терминала | Публичная форма регистрации однажды окажется открытой в проде |
| Клиенты магазина — отдельная модель `Customer` | У клиента нет роли и должности, права сотрудников к нему неприменимы |
| Два статуса: `Variant.status` (наше решение, одно на все каналы) и `Listing.status` (что по факту на площадке) | Сняли у себя — снято везде. Но Kaspi может увести карточку в архив сам, и это надо видеть. Одним полем не выразить |
| Каналы продаж — значения enum, не колонки таблицы | Новый канал добавляется строкой. WB убран 16.09.2026, вернуть — тоже строка |
| Каталог Kaspi — не парсингом HTML-страниц | Вёрстка поедет при первом редизайне |
| Кука кабинета — в поле на странице и в памяти процесса, не в `.env` | Это доступ в кабинет; на диске он уезжает в бэкап, в образ и однажды в git |
| Вход в кабинет Kaspi — **по номеру телефона** | С 16.09.2026 вход по email требует код с почты |
| Товар с модификациями: `Product` → `Variant` | Артикул и цена живут на модификации: Kaspi матчит заказы по артикулу |
| Цены: вбиваем основную и со скидкой, процент считаем | Как на Kaspi. Обратный счёт от процента не воспроизводит фактическую цену — расходится на сотни тенге |
| Закупочная цена — на модификации, цены площадки — у размещения | Товар = цвет, и закупка у каждого своя. Наружу не отдаётся никогда |
| Ткани и оттенки — наш справочник, не поле Kaspi | Kaspi знает только тип ткани. Название и палитру ведём сами, на артикул выбираем из списка |
| Срок предзаказа — одно поле, не «наше» и «кабинетное» | Предзаказ один на всех; два поля означали бы, что где-то показывается неверное |
| Каталог берём из JSON кабинета, а не из разметки | Вёрстка поедет при первом редизайне, внутренний JSON — нет |
| XML-выгрузка остаётся ручным резервом | JSON — недокументированный внутренний запрос; парсер ляжет — без выгрузки останемся без данных вовсе |
| Храним `masterSku`, `offerId` и `shopLink` | Переход в магазин, будущее изменение цен. Достать их потом отдельным проходом по 1328 товарам — дороже |
| Узлы дерева папок — записи в БД, не вычисление из `familyId` | Иначе Kaspi переименует модель — и товар молча переедет в другую папку |

Roadmap — три этапа: доступы, товары, заказы. Остальное в блоке «после 0–3»
с сохранёнными наработками. См. [docs/roadmap.md](docs/roadmap.md).

### Порядок работ

1. **Единый JSON товара на фронт — задача на 17.09.2026.** Сейчас данные товара
   разложены по пяти таблицам (`Product`, `Variant`, `Listing`, `VariantStock`,
   `Fabric`/`FabricShade`), а фронту нужен один собранный вид. Сделать DTO
   каталога и эндпоинты чтения: список товаров и карточка одного. В DTO —
   товар, его модификации, цены по каналам, остатки по складам, ткань и оттенок,
   картинки, статусы. **Закупочная цена наружу не отдаётся.** Состав полей
   согласовать с пользователем до кода: что именно нужно на странице.
2. **Авторизация в кабинете — отложено, пока вручную.** Разведка 16.09.2026
   показала: токен Kaspi Shop API рабочий, но каталог по нему не читается —
   ни официальным API, ни внутренним запросом кабинета (он принимает только
   куку). Ждём ответа Kaspi о доступе; если дадут — обход кабинета не нужен
   вовсе. Если нет, выбранный вариант — **расширение браузера**: вы логинитесь
   в кабинет сами, расширение отдаёт куку в админку одним нажатием. Пароль при
   этом нигде не хранится. Разбор проб и сравнение вариантов —
   в [docs/kaspi-api-integration.md](docs/kaspi-api-integration.md), раздел 10.
3. **Обновление уже сохранённых товаров.** Сейчас импорт заводит только новые.
   Нужна сверка: что изменилось в кабинете, показ расхождений, решение человека.
   Поля, которые правим мы (срок предзаказа, наши названия), не перезаписываются.
4. **Пункт меню** на `/dashboard/kaspi-sync` — за пользователем, меню его зона.
5. **Карточка товара** — закупка, цены по каналам, выбор ткани и оттенка,
   категория. Отсюда же начнёт заполняться `VariantChange`.
6. **Генератор комбинаций** ткань × оттенок с артикулами пачкой и массовое

7. **Кнопка проверки доставки Kaspi** — четыре флага в базе есть, запроса

8. **Характеристики товара** — их нет в ответе списка (`attributes: []`).
   Нужна отдельная разведка XHR карточки в кабинете. Сначала решить, какие

9. **Дерево категорий** — наше, из `categoryPathCodes` как подсказки.

## Известные проблемы

**Не проверено пользователем:** создание сотрудника через модалку и запись
в журнал. Обход кабинета, сводка складов и сохранение товаров в базу проверены
вживую 16.09.2026 — каталог загружен и сохранён.

**`npm run typecheck` на сервере красный.** Две строки в
`server/src/modules/kaspi-catalog/kaspi-catalog.parser.ts:106` — `toArray<T>`
вызывается без параметра типа, и `T` схлопывается в `unknown`. Чинится
указанием типов: `toArray<RawAvailability>(...)` и `toArray<RawCityPrice>(...)`.
Ошибка старая, к каталогу отношения не имеет; правку пользователь пока
не подтвердил.

**`prisma generate` на Windows не перезаписывает клиент при запущенном сервере.**
Миграция проходит, генерация молча нет — и запросы падают с `Unknown argument`.
Останавливать `dev:server` перед миграцией. Подробности и симптомы —
в [docs/deployment.md](docs/deployment.md).

**Кука кабинета живёт в памяти процесса и вставляется руками.** Перезапустили
сервер — вставлять заново. Как часто она протухает сама, пока неизвестно.
Это следующая задача: вход по телефону и паролю.

**Ответ `/api/kaspi-catalog/fetch` — один долгий запрос.** Замерено 16.09.2026:
около 25 секунд на полный обход. Прогресса на экране нет, отменить нельзя.
Если обходов станет больше или добавится выкачивание картинок, понадобится
фоновая задача.

**В компонентах пользователя** (`front/src/components/input/`, `button/`,
`dashboard-nav-menu/`):
- `` cn(styles.X, `${className}`) `` — при отсутствии `className` в разметку
  попадает класс со словом `undefined`. Нужно убрать шаблонную строку.
- `className={styles.X}` стоит **после** `{...props}` — класс, переданный снаружи,
  теряется.
- `Input` не пробрасывает `id`, поэтому `<label htmlFor>` ни к чему не привязан.
- `Input` не ставит `aria-invalid` — красная рамка из SCSS не срабатывает.

**Прочее:**
- Сохранение товаров идёт пачками по 100 из-за общего лимита тела в 1 МБ.
  Маршрутный `express.json` не помогает: тело разбирается раньше маршрутов.
  Тот же скрытый предел висит над `POST /api/kaspi-catalog/preview` — две
  большие выгрузки в него не пролезут.
- `VariantChange` создана, но пока пуста: писать в неё начнём с редактированием
  цен и полей товара.
- В выгрузке Kaspi нет картинок, штрихкодов и скидок — только парсером.
- `shared` отдаёт TypeScript-исходники. Для разработки хватает, для продакшен-сборки
  нужен бандлер (`tsup`).
- Пароль `radeya_app` слабый — локально допустимо, для сервера нужен длинный случайный.
- `prisma migrate dev` требует у роли право `CREATEDB` (shadow-база).
  На проде не нужно — там `migrate deploy`.
- `front/AGENTS.md` и `front/CLAUDE.md` может восстановить `next dev` — удалять.
- Директива `"use client"` пропадала из файла после автоформата IDE. Если Next
  ругается на хуки в серверном компоненте — проверить первую строку.
