# Текущее состояние

Ветка: **`feature/orders`**. Дата среза: 29.09.2026.

## Как мы работаем

Действующая версия правил — в [AGENTS.md](AGENTS.md): **пользователь верстает,
я пишу всю логику** — сервер, `shared/`, и логику фронта по запросу. Вёрстку
по прямой просьбе тоже пишу (так сделаны таблицы товаров и заказов, общие
компоненты, страница импортов и блок статистики), но по умолчанию в разметку
и SCSS не лезу.

## Сделано

### Этап 1 — доступы (готово)

Вход по логину, сессия в httpOnly-куке, состояние сессии в таблице.
`requireAuth`, `requireRole`. Первый админ заводится командой в терминале.
Раздел «Аккаунты» с журналом действий.

### Этап 2 — товары (готово в основном)

- **Каталог из Kaspi** грузится из кабинета и сохраняется в базу.
- **Страница `/dashboard/products`**: дерево папок с поиском и порядком, таблица
  с выделением, переносом в папку, фото, ценой со скидкой, закупкой с валютой,
  поставщиком и чипами складов «код · название · остаток · срок предзаказа».
- **Названия моделей** выводятся правилом `readModelName()`, переименование
  сохранённых — скриптом `rename-products`.
- **Позиции заказов не тянутся.** `OrderEntry` заполняется только импортом
  офлайн-продаж; состав заказов Kaspi (`/orders/{id}/entries`) — отдельный
  проход, это запрос на каждый заказ, к текущей синхронизации не приделывается.

### Поставщики и данные из МойСклада (готово, 28.09.2026)

- **Модель `Supplier`**: `externalId` (UUID МойСклада, `@unique`) — ключ
  повторного импорта, плюс название, адрес, телефон, `telegramId`, `isActive`.
  Удаления нет, только закрытие.
- **Импорт поставщиков** из выгрузки контрагентов: берётся только группа
  «поставщики» (в файле 5700 покупателей Kaspi), сверка по UUID, повторная
  заливка дублей не создаёт. В базе **17 поставщиков**, проверено на боевом
  файле: первый прогон завёл 12, второй — ещё 5, прежние не задвоились.
- **Импорт товаров** из выгрузки номенклатуры: закупочная цена с валютой,
  поставщик, сроки предзаказа по складам. Новых товаров не заводит — дополняет
  найденные по колонке «Код» без учёта регистра. Заодно проставляет
  `Warehouse.name` там, где он был пуст.
- **`Variant.purchaseCurrency`** (enum `Currency`: KZT, RUB) и
  **`Variant.supplierId`** со связью на `Supplier`.
- Оба блока — на `/dashboard/imports`, третьим и вторым. Поставщики выше товаров:
  у товаров поставщик ищется в справочнике, порядок блоков задаёт порядок заливки.

- `GET /api/audit?entityType=Variant&entityId=…` — история товара для карточки.

### Остатки из МойСклада (готово, 29.09.2026)

- Отчёт «Остатки» — **один файл на склад**, склад выбирается выпадашкой.
  Остаток, резерв, ожидание, себестоимость (`Variant.costPrice`, ₸), средняя
  дата поступления. Товар, которого нет в отчёте, обнуляется на этом складе.
- Каталог: «Склады» — код и название; Остаток, Резерв, Ожидание, Доступно,
  Предзаказ, Дней на складе — отдельными колонками, строкой на склад;
  колонка «Себестоимость».

### Этап 3 — заказы (в работе)

- **Синхронизация с Kaspi работает**: `POST /api/orders/sync`, отрезки по 3 дня,
  курсор, две кнопки на странице с прогрессом и отменой.
- **Точки продаж** — общий справочник для площадок и офлайн-магазинов.
  Все заказы обязательно привязаны к точке; удаления точек нет, только закрытие.
- **Офлайн-заказы заведены целиком**: продавец, деньги клиента (оплачено,
  остаток), скидка двумя полями, четыре пополняемых списка, комментарии лентой,
  привязка к заказу площадки.
- **Импорт продаж из Excel** — `/dashboard/imports`: предпросмотр без записи,
  потом запись. Проверен на боевом файле.
- **Статистика** — блок на `/dashboard`: период, итог и плашки по каждой точке.
- **Реестр заказов**: поиск по номеру, фильтры по точке и четырём справочникам,
  период, колонки офлайн-продажи скрываются при выбранной площадке.

### Общие компоненты

`Modal`, `Dropdown`, `Checkbox`, `DateRangePicker`, `Tables`, `TreeFolder`,
`PriceTag`, `Input`, `Button`, `Loader`. Всплывающие панели — через общий хук
`useAnchoredPanel`; прокрутка внутри панели её не закрывает, прокрутка страницы —
закрывает.

`Dropdown` умеет два режима через проп `mode`: `menu` (пункты-действия)
и `select` (выбор значения вместо нативного `<select>`), плюс проп `searchable` —
поиск по списку. Фильтры справочников на `/dashboard/orders` переведены на него.

Чтение книг `.xlsx` — общее, в `server/src/lib/excel.ts`: им пользуются все три
импорта (продажи, поставщики, товары).

## Принятые решения (не пересматривать без причины)

| Решение | Почему |
|---|---|
| Сессии в таблице БД, не JWT | Уволил сотрудника — доступ закрывается сразу |
| Первый админ только из терминала | Публичная форма регистрации однажды окажется открытой в проде |
| Каталог Kaspi — из JSON кабинета, не парсингом HTML | Вёрстка поедет при первом редизайне |
| Кука кабинета — в поле на странице и в памяти процесса | Это доступ в кабинет; на диске он уезжает в бэкап и однажды в git |
| Закупка отдаётся в дашборд | Эндпоинт под ADMIN. На витрину — никогда |
| Деньги — строками с двумя знаками | `number` на цене теряет тиын и складывается с ошибкой |
| Заказы: сырые `kaspiStatus` и `kaspiState` рядом с нашим `status` | Ошибёмся в правиле — пересчитаем из исходных, не дёргая Kaspi |
| Синхронизация заказов возобновляемая, с курсором | Два года это 244 отрезка по 3 дня |
| Поля кабинета при синхронизации по токену не обновляются | Иначе каждый прогон затирал бы их пустотой |
| Незнакомые значения Kaspi помечаются проблемой | Полного перечня статусов площадка не публикует |
| Границы суток для фильтра дат считает клиент | Сервер не знает пояс пользователя |
| Площадки и офлайн-точки — один справочник `SalesPoint` | Иначе фильтр и статистика каждый раз склеивались бы из перечисления и таблицы |
| Колонки `source` нет, есть `salesPoint.type` | Два поля с одним смыслом однажды разойдутся |
| Дата заказа называется `placedAt` | У офлайн-заказа Kaspi ничего не создавал, а период считается по одной дате для всех источников |
| Продавец — одно поле `sellerId`, не «завёл» + «продал» | Пока это один человек. Второе поле добавим, когда появится переброска продаж |
| Строка Excel = один заказ | Решение пользователя: два товара в одну дату — две продажи |
| Четыре справочника в одной таблице `DictionaryItem` | Устроены одинаково; перечень видов закрыт и лежит в коде |
| Комментарии заказа — лента, без правок и удалений | Комментарий, который можно подтереть, не отвечает на вопрос «кто это решил» |
| Привязанный заказ не входит в суммы статистики | Та же продажа посчитана на площадке; сложить — удвоить выручку |
| Отменённые и возвраты не входят в выручку никуда | Это не выручка |
| Номера офлайн-заказов с буквенным префиксом | Цифровой номер Kaspi так совпасть не сможет, и синхронизация не затрёт офлайн-заказ |
| Импорт в два шага: предпросмотр, потом запись | Импорт, который пишет сразу, однажды зальёт в заказы чужую таблицу |
| Спорное в импорте не угадывается | Молча подставленное значение выглядит как настоящее, и ошибка всплывёт через месяц в отчёте |
| Импорт каталога из Kaspi **только создаёт**. Обновления сохранённых товаров не будет | Решение пользователя, 28.09.2026. Единственная операция, способная затереть наши данные, просто не пишется. Остатки, предзаказ, закупка и поставщик ведутся у нас и уходят в XML на площадку — тянуть их обратно значит затирать своё чужим. Плата: цена и статус, изменённые в кабинете, к нам не приедут, пока цены ведутся там |
| Поставщик — отдельная модель `Supplier`, ключ сверки — UUID МойСклада | Наименования в выгрузке дают 630 групп дублей («Ж Сания» девять раз), UUID уникален у всех 5752 строк. По имени сверять — склеить разных контрагентов в одного |
| `externalId` у поставщика, заведённого руками, остаётся пустым | Это идентификатор чужой системы. Выдуманный UUID не совпадёт с настоящим, когда тот же поставщик приедет из МойСклада, — и поле против дублей само бы их и создало |
| Артикул в выгрузке МойСклада ищется по колонке «Код», не «Артикул» | «Артикул» заполнен у 40 строк из 1799, «Код» — у всех 1785 товаров, и формат совпадает с нашими артикулами |
| Закупка хранится с валютой и к одной не приводится | Курса на дату закупки мы не знаем; пересчёт по сегодняшнему превратил бы закупку в выдумку |
| Задвоенный код в выгрузке товаров пропускается целиком, обе строки | Правило «берём ту, где цена не ноль» работает на сегодняшнем файле и сломается на первом дубле с двумя ценами |
| Пустая ячейка склада в выгрузке = склад товар не возит | Ноль означал бы «есть в наличии» — это другое утверждение, подставлять его вместо пустоты нельзя |
| История — в `AuditLog`, пишется `recordHistory()` в транзакции изменения | Изменение без записи о нём хуже неудачной операции. `logAction()` проглатывает сбой — для журнала входов это верно, для истории нет |
| В истории ключ поля, подпись — из словаря в `shared` | Переименуют подпись — старая история не разойдётся с новой, фильтр по полю не потеряет половину |
| Ссылки в истории — названием, не UUID | «Антон → Сания» понятно и после переименования, UUID — нет |
| Отчёт «Остатки» — снимок склада: чего нет в файле, обнуляется | Иначе проданный товар навсегда сохранил бы старую цифру и ушёл на Kaspi. Обнуляется ровно список из предпросмотра |
| В отчёте остатков пусто → 0, отрицательное — как есть | Решение пользователя. Минус — продажа без посадки, правда учёта. На Kaspi уйдёт нулём при выгрузке XML |
| Себестоимость — одна на товар, в тенге | Решение пользователя: основная характеристика. Значение из последнего залитого склада, прежнее — в истории. Выбора валюты нет: себестоимость в ₽ не вычесть из цены в ₸ |
| «Доступно» и «Дней на складе» не хранятся | Производное расходится со слагаемыми; число дней назавтра неверно. Хранится дата поступления |
| `.xls` не читаем, просим пересохранить | `xlsx` в npm заброшен с известными уязвимостями |
| Время отчёта МойСклада — по Астане (UTC+5) | Решение пользователя: вся система по Астане. Файл, похоже, пишет московское — 0,08 дня, не сверяли |

Roadmap — в [docs/roadmap.md](docs/roadmap.md).

## В работе / следующий шаг

**Фильтры и сортировка каталога — план дан 29.09.2026, ждёт утверждения.**

1. `Dropdown`: проп `multiple` — мультивыбор (`values: string[]`), список
   не закрывается по клику, «Выбрано: N · Сбросить».
2. Фильтры на `/dashboard/products`: склады и поставщики (мультивыбор),
   `warehouseIds` и `supplierIds` в `GET /api/products/variants`.
3. Сортировка стрелками в заголовках: цена, закупка, остаток, резерв,
   ожидание, доступно, предзаказ. Порядок и страница — одним параметризованным
   SQL (Prisma не сортирует по сумме дочерних строк), колонка — только
   из закрытого списка. Пустые — в конце.
4. Картинки в таблице товаров — строго квадратные 4rem. Сейчас сплющиваются
   в узкую полосу: preflight Tailwind ставит `img { max-width: 100% }`, а таблица
   с новыми колонками ужимает ячейку фото.

Открытые вопросы плана: сортировка по одной колонке или многоуровневая;
как сортировать закупку в ₽ и ₸ (предложено — внутри валюты); фильтр складов —
«назначен» или «в наличии» (предложено — «назначен»).

**Зачем остатки:** остаток вместе со сроком предзаказа уходит в XML
(`stockCount` и `preOrder`), по которому Kaspi выставляет товар на продажу.
Порядок работы — раздел 13 в [kaspi-api-integration.md](docs/kaspi-api-integration.md).
Выгрузить отчёт «Остатки» по каждому складу и залить — по файлу на склад.

### Отложено: защита импорта продаж от повторной заливки

Повторный импорт того же листа Excel создаёт дубли заказов: номера выдаются
новые, и повтор ничем не отсекается. План разобран 28.09.2026 и отложен
по решению пользователя — вернёмся позже.

Лечится двумя полями в `Order` — из какого листа и строки приехал заказ —
плюс уникальным индексом и пропуском уже записанных со счётчиком
в предпросмотре. Нерешённый вопрос: считать ли ошибкой заливку одного листа
в две разные точки продаж (от этого зависит, входит ли `salesPointId` в ключ).
Остаточный риск: вставка строки в середину уже импортированного листа сдвигает
номера, и такие строки ключом не ловятся.

### Дальше по заказам

1. Позиции заказов Kaspi (`/orders/{id}/entries`) — отдельный проход.
2. Карточка заказа: комментарии, позиции, ручная правка полей.
3. Проставление продавца админом у импортированных заказов (сейчас пусто,
   имя из «чей рабочий день» лежит в комментарии).
4. Ручной ввод офлайн-заказа продавцом — форма со справочниками и выбором товара.
5. **Кнопка «Добавить» в выпадашках справочников.** Значения `DictionaryItem`
   пополняются только через `POST /api/dictionaries`; в интерфейсе добавить
   новый статус доставки или способ оплаты негде. Нужен пункт «+ Добавить»
   в самом списке `Dropdown` — чтобы заводить значение там, где его не хватило,
   не уходя на отдельный экран. Полноценный экран управления справочниками
   (переименование, закрытие, порядок) — следом за кнопкой.
6. **Кнопка «Создать поставщика».** `Supplier` заводится только импортом
   из МойСклада. Нужен `POST /api/suppliers` и форма: название, адрес, телефон,
   Telegram ID. `externalId` у заведённого руками остаётся пустым — это UUID
   чужой системы, придумывать его нельзя.
7. Привязка офлайн-заказа к заказу Kaspi — поле есть, интерфейса выбора нет.
8. Cron на последние дни; кнопка, дотягивающая поля кабинета.

### Дальше по товарам

1. **Назначение склада товару руками.** Выбираешь склад из списка («Склад
   Астана»), ставишь остаток или срок предзаказа, сохраняешь. Складов у товара
   может быть несколько, у каждого свой срок. Сейчас это пишут только два
   импорта, руками не поправить.
   У товара, только что приехавшего из кабинета, складов не назначено вообще —
   форма должна начинаться с «добавить склад», а не с показа уже назначенных,
   иначе на новом товаре она откроется пустой и делать в ней будет нечего.
2. **Генерация XML для Kaspi.** Все поля уже есть в схеме: `kaspiStoreId`,
   `preOrderDays`, `quantity`, статус. Порядок работы — раздел 13
   в [kaspi-api-integration.md](docs/kaspi-api-integration.md). Открытый вопрос:
   чем управляется `available` — автоматически по наличию склада или отдельным
   переключателем.
3. Карточка товара: закупка, цены по каналам, ткань и оттенок.
4. Генератор комбинаций ткань × оттенок с артикулами пачкой.
5. Разовый импорт из МойСклада, после него МойСклад отключается.

## Известные проблемы

**Повторный импорт продаж создаёт дубли заказов** — см. «Отложено» выше.
К импортам поставщиков и товаров это не относится: там повтор безопасен
по устройству.

**Запись импорта продаж не проверена на живой базе** — прогонялся только разбор
файла. Первый импорт стоит делать на одной точке и потом смотреть глазами.
Импорты поставщиков и товаров на боевых файлах проверены.

**Статистика не проверена на данных** — код написан, цифры глазами не сверялись.

**Ручного создания и правки нет у трёх сущностей.** Товар заводится только
импортом из кабинета Kaspi; поставщик — только импортом из МойСклада
(`PATCH /api/suppliers/:id` есть, интерфейса нет, `telegramId` ставится только
через API); `VariantStock` пишут только три импорта. Всё это в очереди.

**«Аккаунты → История» засыпается записями истории.** Каждый импорт кладёт
запись на каждый товар — сотни строк. На сервере есть фильтр `action`
и по сущности, на странице журнала фильтра ещё нет.

**Истории в карточке товара нет** — нет самой карточки. Эндпоинт готов.

**Картинки в таблице товаров сплющиваются** в узкую полосу — в плане, пункт 4.

**Себестоимость из разных складов перезаписывает друг друга** — по решению
пользователя она одна на товар. Прежнее значение видно только в истории.

**`Warehouse.name` заполняется импортом из МойСклада.** Выгрузка Kaspi названий
складов не содержит, и до 28.09.2026 в справочнике они были пустыми — везде
в интерфейсе был виден голый код `PP3`. Названия лежат в
`MOYSKLAD_WAREHOUSE_COLUMNS` и проставляются только тем складам, у которых
поле пустое. Появится новый склад — его название надо либо вписать руками,
либо добавить в раскладку.

**Отладочный вывод на странице заказов.** При каждой загрузке `/dashboard/orders`
идёт запрос в Kaspi (`?raw=1`) и печать сырья в консоль. Убрать вместе
с параметром, когда сверка статусов закончится.

**Стадия импортированных заказов угадывается только для однозначных статусов**
(«Доставлен Клиенту», «Отмена заказа», «Ошибочный ввод»). Остальные получают
«Новый» — подставлять правдоподобную стадию значит записать догадку.

**Две похожие подписи в таблице заказов:** «Номер» (наш `code`) и «Номер заказа»
(`externalNumber` из файла). Предложено переименовать первую в «Номер в системе»,
решения нет.

**Самовывоз и своя доставка считаются «деньгами в пути»**, пока заказ
не переведён в «Доставлен». Если самовывоз означает «клиент забрал и всё» —
правило надо менять.

**«Упаковка» и «Передача» не различаются** у заказов Kaspi: признака в Shop API
либо нет, либо наши строки устарели.

**Возвраты грубее, чем на складе.** В кабинете пять подсостояний, в Shop API два.

**Расхождение в количестве заказов Kaspi:** 4806 у нас против 4802 у пользователя.
Не разобрано. Проверять сравнением по дням.

**Название модели у ~700 товаров — тип изделия, а не модель.** Поле редактируемое,
решение пользователя — оставить.

**`prisma generate` на Windows не перезаписывает клиент при запущенном сервере.**
Миграция проходит, генерация молча нет, и `migrate dev` при этом рапортует
об успехе. Симптом — `Cannot read properties of undefined (reading 'findMany')`
или `Unknown argument 'новоеПоле'` в рантайме.

Срабатывало трижды за 28.09.2026. Порядок: **стоп-сервер → миграция → старт**,
а не «миграция на ходу». Проверка (PowerShell, у пользователя нет `grep`):
`Select-String -Path server\src\generated\prisma\*.ts -Pattern "НовоеИмя" -List`.
Не помогло — снести `server/src/generated/prisma` и сгенерировать заново.

**Кука кабинета живёт в памяти процесса** и вставляется руками.

**Отчёты скриптов не в `.gitignore`.** `server/rename-products.txt` уедет в коммит.

**В компонентах пользователя** (`input/`, `button/`, `dashboard-nav-menu/`):
`cn(styles.X, ${className})` даёт класс со словом `undefined`; `className` стоит
после `{...props}` и теряется; `Input` не пробрасывает `id` и не ставит `aria-invalid`.
