# Текущее состояние

Ветка: **`feature/worker-order-supplier`**. Дата среза: 01.10.2026.

## Как мы работаем

Действующая версия правил — в [AGENTS.md](AGENTS.md): **пользователь верстает,
я пишу всю логику** — сервер, `shared/`, и логику фронта по запросу. Вёрстку
по прямой просьбе тоже пишу (таблицы товаров и заказов, общие компоненты,
страницы импортов и настроек, блок статистики), но по умолчанию в разметку
и SCSS не лезу.

- **Терминал пользователя — cmd**, не PowerShell: команды давать для cmd
  (`del`, `findstr`, `curl`), не `Remove-Item` и `Select-String`.
- **Ветку для commit-сообщения брать из `.git/HEAD`**, не из документов.
- **После каждой миграции — `prisma:generate` отдельной командой при остановленном
  сервере и воркере** (см. «Известные проблемы»).

## Сделано

### Этап 1 — доступы (готово)

Вход по логину, сессия в httpOnly-куке, состояние сессии в таблице. Первый админ
заводится командой в терминале. Раздел «Аккаунты» с журналом действий.

### Доступ по ролям (готово, 01.10.2026, ветка `feature/fix-roles-updates`)

- **`can(roles?)` у каждого маршрута**: `can()` — любой вошедший,
  `can([ADMIN, MANAGER])` — только эти роли. `router.use(can())` на модуль —
  страховка: забытый `can()` не делает маршрут публичным. `requireRole` удалён.
- Роли — `USER_ROLES` в `shared` (`ADMIN`, `MANAGER`, `SELLER`, `VIEWER`).
  Новая роль: `USER_ROLES` + `USER_ROLE_LABELS` + enum в `schema.prisma` + миграция.
  Должность («Дизайнер») — подпись, доступ решает роль.
- **Чтение открыто всем вошедшим:** заказы, окно заказа, комментарии, каталог,
  папки, склады, поставщики, статистика. Действия — по ролям. Полная таблица —
  «Права и роли» в [api-reference.md](docs/api-reference.md).
- **Закупка и себестоимость** — только `CATALOG_PURCHASE_ROLES` / `CATALOG_COST_ROLES`
  (сейчас ADMIN): сервер отдаёт `null`, фронт прячет столбцы, сортировка по закупке
  без доступа — 403.
- Фронт: `useCan()` — `can([ADMIN])` в JSX; `RoleGuard` без ролей — всем вошедшим.

### Этап 2 — товары (готово в основном)

- **Каталог из Kaspi** грузится из кабинета и сохраняется в базу.
- **`/dashboard/products`**: дерево папок, таблица с выделением, переносом,
  фото, ценой, закупкой с валютой, поставщиком, складами; фильтры складов
  и поставщиков (мультивыбор), сортировка по одной колонке.
- **Названия:** модель — `readModelName()`; на экране — `variantDisplayName()`
  (карточка Kaspi, иначе модель) — одно правило на каталог и состав заказа.
- **Поиск каталога** — по части строки без регистра: артикул, модель, оба
  названия Kaspi. Вся строка одним куском — «Мелодия коричневый» не найдёт,
  если слова не рядом (предложено искать по словам, решения нет).

### Вход в кабинет Kaspi по email и паролю (готово, 30.09.2026)

- `/dashboard/settings` → «Кабинет Kaspi»: email, пароль, «Проверить подключение»
  (трасса ответов Kaspi в консоль). Пароль и куки — AES-256-GCM, `KASPI_SECRETS_KEY`.
- **Вход по требованию:** `withCabinetSession(run)` — жива сохранённая сессия,

  [kaspi-api-integration.md](docs/kaspi-api-integration.md), «Как отправить свой запрос».
- «Синхронизация с Kaspi» при работающем входе — только «Загрузить все товары».
- **«Планируемая дата прибытия»** — GraphQL `getOrderDetails` кабинета (запрос

  новые сразу, остальные раз в час. Обновляют воркер, кнопка синхронизации,

### Этап 3 — заказы (в работе)

- Синхронизация с Kaspi (`POST /api/orders/sync`), точки продаж, офлайн-заказы,
  импорт продаж из Excel, статистика, реестр по одной точке, окно заказа,
  цвета 13 стадий.
- Ручная синхронизация и воркер — под одной блокировкой PostgreSQL: идёт цикл
  воркера — кнопка отвечает «повторите через минуту».

### Воркеры (этапы 1 и 3 готовы, не проверены на живых заказах; 01.10.2026)

Всё — [docs/workers.md](docs/workers.md): решения пользователя (раздел 1),
устройство, файлы (раздел 4), отправка (раздел 5).

- **Процесс** `npm run dev:worker` (из корня), только при `WORKERS_ENABLED=true`.
  `server/src/modules/workers/`: `engine/` — общий движок, `jobs/orders/` —
  воркер заказов по шагам, `jobs/index.ts` — реестр.
- **Цикл воркера заказов:** заказы Kaspi за 1–3 мес → журнал изменений
  (`WorkerEvent`) → составы новых → даты прибытия из кабинета → отправка в Telegram.
- **Самовосстановление:** ошибка цикла не останавливает, 3 подряд — оповещение;
  падение процесса — «перезапуск после сбоя»; нет пульса — наблюдатель в API
  пишет «не отвечает».
- **Отправка:** в наличии со склада Астаны (PP3) → группа «Из наличия в Астане»;
  всё остальное → поставщику товара. Задержка 10/30/60 мин, окно 8–17 по Астане
  и дни недели, точка отсечки — момент включения галочки. Kaspi Доставка без даты
  сдачи — ждёт; своя доставка / самовывоз — без даты. Отмена до отправки — не шлём;
  после — отмена/возврат тому же получателю. Анти-дубль — `OrderDispatch`.
- **Карточка-картинка** — Satori + resvg, шрифты Roboto в `server/assets/fonts/`
  (латиница и кириллица под разными именами).
- **Настройки:** блок «Воркеры» (настройки, состояние, причины неотправки,
  «Проверка отправки» — тестовая карточка «ТЕСТ — НЕ ЗАКАЗ» на один ID или всем),
  блок «Получатели в Telegram» (группа Астаны, поставщики).

## Принятые решения (не пересматривать без причины)

| Решение | Почему |
|---|---|
| Сессии в таблице БД, не JWT | Уволил сотрудника — доступ закрывается сразу |
| Первый админ только из терминала | Публичная форма регистрации однажды окажется открытой в проде |
| Каталог Kaspi — из JSON кабинета, не парсингом HTML | Вёрстка поедет при первом редизайне |
| Закупка отдаётся в дашборд только ролям из `CATALOG_PURCHASE_ROLES` | На витрину — никогда; продавцу закупочные цены не нужны |
| Деньги — строками с двумя знаками | `number` на цене теряет тиын |
| Заказы: сырые `kaspiStatus` и `kaspiState` рядом с нашим `status` | Ошибёмся в правиле — пересчитаем из исходных, не дёргая Kaspi |
| Синхронизация заказов возобновляемая, с курсором | Два года это 244 отрезка по 3 дня |
| Поля кабинета синхронизация по токену не обновляет | Иначе каждый прогон затирал бы их пустотой |
| Незнакомые значения Kaspi помечаются проблемой | Полного перечня статусов площадка не публикует |
| Границы суток для фильтра дат считает клиент | Сервер не знает пояс пользователя |
| Площадки и офлайн-точки — один справочник `SalesPoint` | Иначе фильтр и статистика склеивались бы из двух мест |
| Дата заказа — `placedAt` | Период считается по одной дате для всех источников |
| Продавец — одно поле `sellerId` | Второе добавим, когда появится переброска продаж |
| Строка Excel = один заказ | Решение пользователя |
| Комментарии заказа — лента без правок и удалений | Подтираемый комментарий не отвечает на «кто решил» |
| Привязанный заказ и отменённые/возвраты не входят в выручку | Иначе двойной счёт и не-выручка |
| Номера офлайн-заказов с буквенным префиксом | Синхронизация Kaspi не затрёт офлайн-заказ |
| Импорт в два шага: предпросмотр, потом запись; спорное не угадывается | Иначе ошибка всплывёт через месяц в отчёте |
| Импорт каталога из Kaspi **только создаёт** (28.09.2026) | Остатки, предзаказ, закупка ведутся у нас и уходят в XML |
| Поставщик — `Supplier`, ключ сверки — UUID МойСклада; `externalId` руками не придумывается | По имени — 630 групп дублей |
| Артикул в выгрузке МойСклада — колонка «Код» | «Артикул» заполнен у 40 строк из 1799 |
| Закупка с валютой, к одной не приводится; сортировка по числу без валюты | Курса на дату закупки нет |
| История — в `AuditLog` в транзакции изменения; ключ поля, подпись из словаря | Изменение без записи хуже неудачной операции |
| Отчёт «Остатки» — снимок склада, пропавшее обнуляется; пусто → 0, минус как есть | Иначе проданный товар навсегда сохранил бы старую цифру |
| Себестоимость — одна на товар, в тенге | Решение пользователя |
| «Доступно» и «Дней на складе» не хранятся | Производное расходится со слагаемыми |
| `.xls` не читаем | `xlsx` в npm заброшен с уязвимостями |
| Реестр заказов — одна точка, по умолчанию Kaspi | У площадки и офлайн-точки разные таблицы |
| Состав заказа Kaspi — при первом открытии окна, у новых — воркером | Полный проход — 4800 запросов |
| Сортировка каталога — по одной колонке; фильтр «Склады» — «назначен» | Решение пользователя |
| Мультивыбор — пропом `Dropdown` | Один компонент выбора — одно поведение |
| Вся система по Астане (UTC+5) | Решение пользователя |
| **Доступ — `can([...])` у маршрута, роли в коде**, не таблица прав с галочками (01.10.2026) | Решение пользователя: просто и универсально. Галочки в настройках потребуют переделки |
| Чтение открыто всем вошедшим, действия — по ролям | Сотрудникам нужно видеть заказы и товары |
| Вход в кабинет Kaspi **по требованию**, не постоянный (30.09.2026) | Частые входы — блокировка учётной записи |
| Email и пароль Kaspi — в базе зашифрованными, ключ в `.env` | Бэкап базы без ключа доступа не даёт |
| GraphQL кабинета — запрос слово в слово как у кабинета | Урезанный запрос может быть отвергнут |
| Дата прибытия — только активным заказам, раз в час | Один запрос на заказ; частые запросы — блокировка |
| Воркер — отдельный процесс, все воркеры в одном (01.10.2026) | Падение воркера не роняет API; VPS 1 ГБ |
| Воркеры запускаются только при `WORKERS_ENABLED=true` | Копия базы с ноутбука не должна слать поставщикам |
| Следующий цикл — после конца текущего, потолок 10 мин | Решение пользователя: не начинать, пока не закончился |
| В журнал — только события, не «ничего нового» | 720 пустых строк в сутки |
| Маршрут: наличие Астаны → группа, остальное → поставщику (01.10.2026) | Решение пользователя |
| Kaspi Доставка без даты сдачи — не отправлять, ждать | Решение пользователя |
| Две позиции — две карточки | Решение пользователя |
| Отправка — с точки отсечки (момент включения) | Иначе первый цикл высыпал бы весь период |
| Отмена одна на позицию; отмены первыми в цикле | «В пути» и «отменён» — одна отмена; отмена останавливает отгрузку |

Roadmap — в [docs/roadmap.md](docs/roadmap.md).

## Известные проблемы

**Воркер и отправка в Telegram на живых заказах не проверены.** Тестовая карточка
с кириллицей после исправления шрифтов не проверена.

**Эмодзи старых карточек (🚨, ✅) не рисуются** — Satori нужен набор картинок.

**`prisma generate` на Windows не перезаписывает клиент при запущенном сервере
или воркере.** Миграция проходит, генерация молча нет. Симптом — `Property 'xxx'
does not exist on type PrismaClient` или `Unknown argument`. Порядок: стоп сервер
и воркер → миграция → `npm run prisma:generate --workspace=server` → старт.
Проверка (cmd): `findstr /m "ИмяМодели" server\src\generated\prisma\*.ts`.
Не помогло — удалить `server\src\generated\prisma` и сгенерировать заново.
Случалось 5 раз.

**Повторный импорт продаж создаёт дубли заказов** — см. «Отложено».

**Не подтверждено на живых данных:** запись импорта продаж, статистика, загрузка
состава Kaspi при открытии, импорт остатков с обнулением, SQL сортировки каталога
по складам, записи истории в `AuditLog`.

**Ручного создания и правки нет у трёх сущностей:** товар (только импорт из кабинета),
поставщик (только импорт; правка — только Telegram ID в настройках), `VariantStock`.

**«Аккаунты → История» засыпается записями истории** — фильтра на странице нет.

**Истории в карточке товара нет** — нет самой карточки.

**Себестоимость из разных складов перезаписывает друг друга** — по решению пользователя.

**`Warehouse.name` заполняется импортом из МойСклада** (`MOYSKLAD_WAREHOUSE_COLUMNS`);
новый склад — вписать руками или добавить в раскладку.

**Отладочный запрос сырья Kaspi на странице заказов** — только у ADMIN; убрать,
когда сверка статусов закончится.

**Стадия импортированных заказов угадывается только для однозначных статусов.**

**Две похожие подписи в таблице заказов:** «Номер» и «Номер заказа» — решения нет.

**Самовывоз и своя доставка считаются «деньгами в пути»** до «Доставлен».

**«Упаковка» и «Передача» не различаются** у заказов Kaspi; **возвраты грубее**,
чем в кабинете (5 подсостояний против 2).

**Заказов Kaspi у нас 4806, у пользователя 4802** — не разобрано.

**Название модели у ~700 товаров — тип изделия** («диван»). На экране не мешает:
показывается название Kaspi (`variantDisplayName`).

**Отчёты скриптов не в `.gitignore`:** `server/rename-products.txt` уедет в коммит.

**В компонентах пользователя** (`input/`, `button/`, `dashboard-nav-menu/`):
`cn(styles.X, ${className})` даёт класс `undefined`; `className` после `{...props}`
теряется; `Input` не ставит `aria-invalid`.

**Прочее:**
- Сохранение товаров пачками по 100 из-за лимита тела в 1 МБ.
- `shared` отдаёт TypeScript-исходники; для продакшен-сборки нужен бандлер (`tsup`).
- Пароль `radeya_app` слабый — для сервера нужен длинный случайный.
- `front/AGENTS.md` и `front/CLAUDE.md` может восстановить `next dev` — удалять.
- У `<dialog>` нельзя задавать `display` в обычном классе, только через `[open]`.
- В переписке 01.10.2026 на скриншоте попала кука кабинета Kaspi — пользователю
  предложено перевойти в кабинет.
