# Текущее состояние

Ветка: **`feature/orders`**. Дата среза: 24.09.2026.

## Как мы работаем

Действующая версия правил — в [AGENTS.md](AGENTS.md): **пользователь верстает,
я пишу всю логику** — сервер, `shared/`, и логику фронта по запросу. Вёрстку
по прямой просьбе тоже пишу (так сделаны таблицы товаров и заказов, общие
компоненты, страница импортов и блок статистики), но по умолчанию в разметку
и SCSS не лезу.

## Сделано

### Этап 1 — доступы (готово)

Вход по логину, сессия в httpOnly-куке, состояние сессии в таблице.
`requireAuth`, `requireRole`. Первый админ заводится командой в терминале.
Раздел «Аккаунты» с журналом действий.

### Этап 2 — товары (готово в основном)

- **Каталог из Kaspi** грузится из кабинета и сохраняется в базу.
- **Страница `/dashboard/products`**: дерево папок с поиском и порядком, таблица
  с выделением, переносом в папку, фото и ценой со скидкой.
- **Названия моделей** выводятся правилом `readModelName()`, переименование
  сохранённых — скриптом `rename-products`.
- **Позиции заказов не тянутся.** `OrderEntry` заполняется только импортом
  офлайн-продаж; состав заказов Kaspi — отдельный проход.

### Этап 3 — заказы (в работе)

- **Синхронизация с Kaspi работает**: `POST /api/orders/sync`, отрезки по 3 дня,
  курсор, две кнопки на странице с прогрессом и отменой.
- **Точки продаж** — общий справочник для площадок и офлайн-магазинов.
  Все заказы обязательно привязаны к точке; удаления точек нет, только закрытие.
- **Офлайн-заказы заведены целиком**: продавец, деньги клиента (оплачено,
  остаток), скидка двумя полями, четыре пополняемых списка, комментарии лентой,
  привязка к заказу площадки.
- **Импорт продаж из Excel** — `/dashboard/imports`: предпросмотр без записи,
  потом запись. Проверен на боевом файле.
- **Статистика** — блок на `/dashboard`: период, итог и плашки по каждой точке.
- **Реестр заказов**: поиск по номеру, фильтры по точке и четырём справочникам,
  период, колонки офлайн-продажи скрываются при выбранной площадке.

### Общие компоненты

`Modal`, `Dropdown`, `Checkbox`, `DateRangePicker`, `Tables`, `TreeFolder`,
`PriceTag`, `Input`, `Button`, `Loader`. Всплывающие панели — через общий хук
`useAnchoredPanel`.

## Принятые решения (не пересматривать без причины)

| Решение | Почему |
|---|---|
| Сессии в таблице БД, не JWT | Уволил сотрудника — доступ закрывается сразу |
| Первый админ только из терминала | Публичная форма регистрации однажды окажется открытой в проде |
| Каталог Kaspi — из JSON кабинета, не парсингом HTML | Вёрстка поедет при первом редизайне |
| Кука кабинета — в поле на странице и в памяти процесса | Это доступ в кабинет; на диске он уезжает в бэкап и однажды в git |
| Закупка отдаётся в дашборд | Эндпоинт под ADMIN. На витрину — никогда |
| Деньги — строками с двумя знаками | `number` на цене теряет тиын и складывается с ошибкой |
| Заказы: сырые `kaspiStatus` и `kaspiState` рядом с нашим `status` | Ошибёмся в правиле — пересчитаем из исходных, не дёргая Kaspi |
| Синхронизация заказов возобновляемая, с курсором | Два года это 244 отрезка по 3 дня |
| Поля кабинета при синхронизации по токену не обновляются | Иначе каждый прогон затирал бы их пустотой |
| Незнакомые значения Kaspi помечаются проблемой | Полного перечня статусов площадка не публикует |
| Границы суток для фильтра дат считает клиент | Сервер не знает пояс пользователя |
| Площадки и офлайн-точки — один справочник `SalesPoint` | Иначе фильтр и статистика каждый раз склеивались бы из перечисления и таблицы |
| Колонки `source` нет, есть `salesPoint.type` | Два поля с одним смыслом однажды разойдутся |
| Дата заказа называется `placedAt` | У офлайн-заказа Kaspi ничего не создавал, а период считается по одной дате для всех источников |
| Продавец — одно поле `sellerId`, не «завёл» + «продал» | Пока это один человек. Второе поле добавим, когда появится переброска продаж |
| Строка Excel = один заказ | Решение пользователя: два товара в одну дату — две продажи |
| Четыре справочника в одной таблице `DictionaryItem` | Устроены одинаково; перечень видов закрыт и лежит в коде |
| Комментарии заказа — лента, без правок и удалений | Комментарий, который можно подтереть, не отвечает на вопрос «кто это решил» |
| Привязанный заказ не входит в суммы статистики | Та же продажа посчитана на площадке; сложить — удвоить выручку |
| Отменённые и возвраты не входят в выручку никуда | Это не выручка |
| Номера офлайн-заказов с буквенным префиксом | Цифровой номер Kaspi так совпасть не сможет, и синхронизация не затрёт офлайн-заказ |
| Импорт в два шага: предпросмотр, потом запись | Импорт, который пишет сразу, однажды зальёт в заказы чужую таблицу |
| Спорное в импорте не угадывается | Молча подставленное значение выглядит как настоящее, и ошибка всплывёт через месяц в отчёте |
| Импорт каталога из Kaspi **только создаёт**. Обновления сохранённых товаров не будет | Решение пользователя, 28.09.2026. Единственная операция, способная затереть наши данные, просто не пишется. Остатки, предзаказ, закупка и поставщик ведутся у нас и уходят в XML на площадку — тянуть их обратно значит затирать своё чужим. Плата: цена и статус, изменённые в кабинете, к нам не приедут, пока цены ведутся там |

Roadmap — в [docs/roadmap.md](docs/roadmap.md).

## В работе / следующий шаг

**Защита импорта от повторной заливки.** Сейчас повторный импорт того же листа
создаст дубли: номера выдаются новые, и повтор ничем не отсекается. Лечится
одним полем — из какого листа и строки приехал заказ — плюс пропуском уже
записанных со счётчиком в предпросмотре. Это следующий шаг.

### Дальше по заказам

1. Позиции заказов Kaspi (`/orders/{id}/entries`) — отдельный проход.
2. Карточка заказа: комментарии, позиции, ручная правка полей.
3. Проставление продавца админом у импортированных заказов (сейчас пусто,
   имя из «чей рабочий день» лежит в комментарии).
4. Ручной ввод офлайн-заказа продавцом — форма со справочниками и выбором товара.
5. **Кнопка «Добавить» в выпадашках справочников.** Значения `DictionaryItem`
   пополняются только через `POST /api/dictionaries`; в интерфейсе добавить
   новый статус доставки или способ оплаты негде. Нужен пункт «+ Добавить»
   в самом списке `Dropdown` — чтобы заводить значение там, где его не хватило,
   не уходя на отдельный экран. Полноценный экран управления справочниками
   (переименование, закрытие, порядок) — следом за кнопкой.
6. **Кнопка «Создать поставщика».** `Supplier` заводится только импортом
   из МойСклада. Нужен `POST /api/suppliers` и форма: название, адрес, телефон,
   Telegram ID. `externalId` у заведённого руками остаётся пустым — это UUID
   чужой системы, придумывать его нельзя.
7. Привязка офлайн-заказа к заказу Kaspi — поле есть, интерфейса выбора нет.
8. Cron на последние дни; кнопка, дотягивающая поля кабинета.

### Дальше по товарам

1. **Назначение склада товару руками.** Выбираешь склад из списка («Склад
   Астана»), ставишь остаток или срок предзаказа, сохраняешь. Складов у товара
   может быть несколько, у каждого свой срок. Сейчас это пишут только два
   импорта, руками не поправить.
   У товара, только что приехавшего из кабинета, складов не назначено вообще —
   форма должна начинаться с «добавить склад», а не с показа уже назначенных,
   иначе на новом товаре она откроется пустой и делать в ней будет нечего.
2. **Генерация XML для Kaspi.** Все поля уже есть в схеме: `kaspiStoreId`,
   `preOrderDays`, `quantity`, статус. Порядок работы — раздел 13
   в [kaspi-api-integration.md](docs/kaspi-api-integration.md). Открытый вопрос:
   чем управляется `available` — автоматически по наличию склада или отдельным
   переключателем.
3. Карточка товара: закупка, цены по каналам, ткань и оттенок.
4. Генератор комбинаций ткань × оттенок с артикулами пачкой.
5. Разовый импорт из МойСклада, после него МойСклад отключается.

### Отложено сознательно

- **Склады и поставщики — две отдельные модели.** Пока «откуда поехал товар»
  живёт списком `SHIPMENT_ORIGIN`, где вперемешку витрины и поставщики. Форма
  поставщика записана в [roadmap.md](docs/roadmap.md), этап 3.
- **Склад офлайн-точки** — до товароучёта.
- **Множественный выбор в фильтрах.** Сервер принимает список точек и значений
  справочников, интерфейс пока даёт выбрать одно: не решено, расширять
  `Dropdown` или заводить отдельный `MultiSelect`.

## Известные проблемы

**Повторный импорт создаёт дубли** — см. «следующий шаг».

**Запись импорта не проверена на живой базе** — прогонялся только разбор файла.
Первый импорт стоит делать на одной точке и потом смотреть глазами.

**Статистика не проверена на данных** — код написан, цифры глазами не сверялись.

**Отладочный вывод на странице заказов.** При каждой загрузке `/dashboard/orders`
идёт запрос в Kaspi (`?raw=1`) и печать сырья в консоль. Убрать вместе
с параметром, когда сверка статусов закончится.

**Стадия импортированных заказов угадывается только для однозначных статусов**
(«Доставлен Клиенту», «Отмена заказа», «Ошибочный ввод»). Остальные получают
«Новый» — подставлять правдоподобную стадию значит записать догадку.

**Две похожие подписи в таблице заказов:** «Номер» (наш `code`) и «Номер заказа»
(`externalNumber` из файла). Предложено переименовать первую в «Номер в системе»,
решения нет.

**Самовывоз и своя доставка считаются «деньгами в пути»**, пока заказ
не переведён в «Доставлен». Если самовывоз означает «клиент забрал и всё» —
правило надо менять.

**«Упаковка» и «Передача» не различаются** у заказов Kaspi: признака в Shop API
либо нет, либо наши строки устарели.

**Возвраты грубее, чем на складе.** В кабинете пять подсостояний, в Shop API два.

**Расхождение в количестве заказов Kaspi:** 4806 у нас против 4802 у пользователя.
Не разобрано. Проверять сравнением по дням.

**Название модели у ~700 товаров — тип изделия, а не модель.** Поле редактируемое,
решение пользователя — оставить.

**`prisma generate` на Windows не перезаписывает клиент при запущенном сервере.**
Миграция проходит, генерация молча нет. Останавливать `dev:server` перед миграцией
и проверять результат: `grep -rl "НовоеИмяМодели" server/src/generated/prisma`.

**Кука кабинета живёт в памяти процесса** и вставляется руками.

**Отчёты скриптов не в `.gitignore`.** `server/rename-products.txt` уедет в коммит.

**В компонентах пользователя** (`input/`, `button/`, `dashboard-nav-menu/`):
`cn(styles.X, ${className})` даёт класс со словом `undefined`; `className` стоит
после `{...props}` и теряется; `Input` не пробрасывает `id` и не ставит `aria-invalid`.

**Прочее:**
- Сохранение товаров идёт пачками по 100 из-за общего лимита тела в 1 МБ.
- `shared` отдаёт TypeScript-исходники; для продакшен-сборки нужен бандлер (`tsup`).
- Пароль `radeya_app` слабый — локально допустимо, для сервера нужен длинный случайный.
- `front/AGENTS.md` и `front/CLAUDE.md` может восстановить `next dev` — удалять.
- У `<dialog>` нельзя задавать `display` в обычном классе, только через `[open]`:
  авторские стили побеждают UA, и окно станет видимым всегда.
