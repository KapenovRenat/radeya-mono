# Текущее состояние

Ветка: **`feature/auth-dashboard`**. Дата среза: 21.09.2026.

## Как мы работаем

Действующая версия правил — в [AGENTS.md](AGENTS.md): **пользователь верстает,
я пишу всю логику** — сервер, `shared/`, и логику фронта по запросу. Вёрстку
по прямой просьбе тоже пишу (так сделаны таблицы товаров и заказов и общие
компоненты), но по умолчанию в разметку и SCSS не лезу.

## Сделано

### Этап 1 — доступы (готово)

Вход по логину, сессия в httpOnly-куке, состояние сессии в таблице.
`requireAuth`, `requireRole`. Первый админ заводится командой в терминале.
Раздел «Аккаунты» с журналом действий.

### Этап 2 — товары (готово в основном)

- **Каталог из Kaspi** грузится из кабинета и сохраняется в базу. Восемь моделей:
  артикул на `Variant`, цены в `Listing`, остатки в `VariantStock`.
- **Страница `/dashboard/products`**: дерево папок с поиском, порядком и меню
  действий; таблица с галками выделения, фото, ценой со скидкой, складами
  и закреплённым меню; перенос выбранных в папку модалкой с подтверждением.
- **DTO каталога полный** — все поля артикула, включая закупку. Эндпоинт закрыт
  ролью ADMIN; на витрину этот DTO отдавать нельзя.
- **Названия моделей** выводятся правилом `readModelName()`, переименование
  сохранённых — скриптом `rename-products`.

### Этап 3 — заказы (в работе)

- **Модель заведена целиком**: `Order`, `OrderEntry`, `OrderMarker`, `OrderStep`,
  миграция `orders`. Поля обоих источников — Shop API и кабинета — созданы сразу;
  кабинетные пока пустые, их заполнит отдельный проход.
- **Синхронизация работает**: `POST /api/orders/sync` — отрезки по 3 дня, курсор,
  две кнопки на странице (2 года / 3 месяца) с прогрессом и отменой.
- **Страница `/dashboard/orders`**: таблица из 8 колонок, поиск по номеру,
  выбор периода календарём.
- **Позиции заказов не тянутся.** `OrderEntry` пустая: Kaspi отдаёт состав
  отдельным запросом на каждый заказ, это отдельный проход.

### Общие компоненты

`Dropdown`, `Checkbox`, `DateRangePicker`, `Tables`, `TreeFolder`, `PriceTag`,
`Input`, `Button`, `Loader`. Всплывающие панели — через общий хук
`useAnchoredPanel` (портал, `position: fixed`, разворот вверх при нехватке места).

## Принятые решения (не пересматривать без причины)

| Решение | Почему |
|---|---|
| Сессии в таблице БД, не JWT | Уволил сотрудника — доступ закрывается сразу |
| Первый админ только из терминала | Публичная форма регистрации однажды окажется открытой в проде |
| Два статуса товара: `Variant.status` и `Listing.status` | Сняли у себя — снято везде. Но Kaspi может увести карточку в архив сам |
| Каналы продаж — значения enum, не колонки | Новый канал добавляется строкой |
| Каталог Kaspi — из JSON кабинета, не парсингом HTML | Вёрстка поедет при первом редизайне |
| Кука кабинета — в поле на странице и в памяти процесса | Это доступ в кабинет; на диске он уезжает в бэкап и однажды в git |
| Закупка отдаётся в дашборд | Эндпоинт под ADMIN, в админке она нужна. На витрину — никогда; при открытии каталога другим ролям срезать по роли |
| Деньги — строками с двумя знаками | `number` на цене теряет тиын и складывается с ошибкой |
| Заказы: сырые `kaspiStatus` и `kaspiState` рядом с нашим `status` | Наш статус производный; ошибёмся в правиле — пересчитаем из исходных, не дёргая Kaspi |
| Синхронизация заказов возобновляемая, с курсором | Два года это 244 отрезка по 3 дня: в один запрос не укладывается ни по времени, ни по терпению браузера |
| Поля кабинета при синхронизации по токену не обновляются | Иначе каждый прогон затирал бы их пустотой |
| Незнакомые значения Kaspi помечаются проблемой | Полного перечня статусов площадка не публикует; молча падать в «Новый» нельзя |
| Порядок папок — полный список уровня, а не «подними одну» | Идемпотентно и не съезжает при одновременной правке двумя админами |
| Границы суток для фильтра дат считает клиент | Сервер не знает пояс пользователя, а «за 21 сентября» в Алматы и в UTC — разные наборы |

Roadmap — в [docs/roadmap.md](docs/roadmap.md).

## В работе / следующий шаг

**Сверка статусов заказов с МойСкладом пользователя.** На этом остановились.

### Что уже выяснено

1. **«Предзаказ» вместо «На подписании» — исправлено.** Kaspi ставит
   `ACCEPTED_BY_MERCHANT` ещё до подписи клиента, и заказ попадал в ветку
   принятых, где срабатывал `preOrder`. Проверка `state = SIGN_REQUIRED`
   передвинута выше. Проверено на заказе `1082757256`.
2. **Имя покупателя — исправлено.** `customer.name` у Kaspi содержит только имя,
   фамилия лежит в `lastName` одной буквой. Показываем «А Аскарбек».
3. **Открыто: «Упаковка» против «Передачи».** Заказы `1082228132` (у пользователя
   «Передача») и `1082451968` («Упаковка») в нашей базе **совпадают по всем полям**:
   `assembled = f`, накладной нет, `courierTransmissionDate` пуст. Значит признака
   в Shop API либо нет вовсе, либо наши строки устарели.

### Следующий шаг — ровно один

Прогнать синхронизацию за 3 месяца и повторить запрос:

```
psql "postgresql://radeya_app:radeya@localhost:5432/radeya_mono" -x -P pager=off -c "SELECT code, status, assembled, \"waybillNumber\", \"updatedAt\" FROM \"Order\" WHERE code IN ('1082228132','1082451968','1082451969') ORDER BY code;"
```

- Появилась накладная у `1082228132` и нет у `1082451968` — признак найден,
  правило пишется по `waybillNumber`, лестница сходится.
- Обе пусты — признака в Shop API нет, «Упаковку» с «Передачей» по токену
  не разделить. Тогда решаем: оставить как есть или свести их в одну стадию
  до появления доступа к кабинету (там стадия видна в `steps[]` по шагу `CURRENT`).

Заодно станет виден `assembled` у `1082451969`: если `true`, то `assembled`
означает «передан», и наш `TRANSMISSION` надо переименовать в «Переданы на доставку».

**Важно при сверке:** в таблице у нас снимок последней синхронизации, а на складе
пользователя — живые данные. Сравнивать надо консоль браузера (она тянет Kaspi
напрямую) с его экраном, иначе расхождение объясняется просто свежестью.

## Известные проблемы

**Отладочный вывод на странице заказов.** При каждой загрузке `/dashboard/orders`
идёт запрос в Kaspi (`?raw=1`) и печать сырья в консоль браузера. Это для сверки
статусов — убрать вместе с параметром, когда сверка закончится.

**«Упаковка» и «Передача» не различаются** — см. выше.

**Возвраты грубее, чем на складе.** В кабинете пять подсостояний, в Shop API два:
`RETURN_REQUESTED` и `RETURNED`. «Споры» и «Закрытые заявки» по токену не отличить.
«Отменены при доставке» — обычный `CANCELLED`, отделять надо своим правилом.

**Расхождение в количестве заказов:** 4806 у нас против 4802 у пользователя.
Не разобрано. Проверять сравнением по дням, а не перебором номеров; сначала
убедиться, что периоды с обеих сторон одинаковые.

**Название модели у ~700 товаров — тип изделия, а не модель** («диван», «картина»).
У 761 товара бренд стоит первым словом `masterTitle`, и правило берёт слово после
него. Лечится словарём типов; решение пользователя — оставить, поле редактируемое.

**`prisma generate` на Windows не перезаписывает клиент при запущенном сервере.**
Миграция проходит, генерация молча нет — и запросы падают с
`Cannot read properties of undefined (reading 'findMany')`. Останавливать
`dev:server` перед миграцией.

**Кука кабинета живёт в памяти процесса** и вставляется руками. Перезапустили
сервер — вставлять заново.

**Отчёты скриптов не в `.gitignore`.** `server/rename-products.txt` уедет
в коммит, если не добавить строку.

**В компонентах пользователя** (`input/`, `button/`, `dashboard-nav-menu/`):
`cn(styles.X, ${className})` даёт класс со словом `undefined`; `className` стоит
после `{...props}` и теряется; `Input` не пробрасывает `id` и не ставит `aria-invalid`.

**Прочее:**
- Сохранение товаров идёт пачками по 100 из-за общего лимита тела в 1 МБ.
- `shared` отдаёт TypeScript-исходники; для продакшен-сборки нужен бандлер (`tsup`).
- Пароль `radeya_app` слабый — локально допустимо, для сервера нужен длинный случайный.
- `front/AGENTS.md` и `front/CLAUDE.md` может восстановить `next dev` — удалять.
