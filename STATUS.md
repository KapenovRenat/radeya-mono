# Текущее состояние

Ветка: **`feature/worker-order-supplier`**. Дата среза: 01.10.2026.

## Как мы работаем

Действующая версия правил — в [AGENTS.md](AGENTS.md): **пользователь верстает,
я пишу всю логику** — сервер, `shared/`, и логику фронта по запросу. Вёрстку
по прямой просьбе тоже пишу (таблицы товаров и заказов, общие компоненты,
страницы импортов и настроек, блок статистики), но по умолчанию в разметку
и SCSS не лезу.

- **Терминал пользователя — cmd**, не PowerShell: команды давать для cmd
  (`del`, `findstr`, `curl`), не `Remove-Item` и `Select-String`.
- **Ветку для commit-сообщения брать из `.git/HEAD`**, не из документов.
- **После каждой миграции — `prisma:generate` отдельной командой при остановленном
  сервере и воркере** (см. «Известные проблемы»).

## Сделано

### Этап 1 — доступы (готово)

Вход по логину, сессия в httpOnly-куке, состояние сессии в таблице. Первый админ
заводится командой в терминале. Раздел «Аккаунты» с журналом действий.

### Доступ по ролям (готово, 01.10.2026, ветка `feature/fix-roles-updates`)

- **`can(roles?)` у каждого маршрута**: `can()` — любой вошедший,
  `can([ADMIN, MANAGER])` — только эти роли. `router.use(can())` на модуль —
  страховка: забытый `can()` не делает маршрут публичным. `requireRole` удалён.
- Роли — `USER_ROLES` в `shared` (`ADMIN`, `MANAGER`, `SELLER`, `VIEWER`).
  Новая роль: `USER_ROLES` + `USER_ROLE_LABELS` + enum в `schema.prisma` + миграция.
  Должность («Дизайнер») — подпись, доступ решает роль.
- **Чтение открыто всем вошедшим:** заказы, окно заказа, комментарии, каталог,
  папки, склады, поставщики, статистика. Действия — по ролям. Полная таблица —
  «Права и роли» в [api-reference.md](docs/api-reference.md).
- **Закупка и себестоимость** — только `CATALOG_PURCHASE_ROLES` / `CATALOG_COST_ROLES`
  (сейчас ADMIN): сервер отдаёт `null`, фронт прячет столбцы, сортировка по закупке
  без доступа — 403.
- Фронт: `useCan()` — `can([ADMIN])` в JSX; `RoleGuard` без ролей — всем вошедшим.

### Воркеры (этапы 1 и 3 готовы, отправка проверена на живых заказах; 01.10.2026)

Всё — [docs/workers.md](docs/workers.md): решения пользователя (раздел 1),
устройство, файлы (раздел 4), отправка (раздел 5).

- **Процесс** `npm run dev:worker` (из корня), только при `WORKERS_ENABLED=true`.
  `server/src/modules/workers/`: `engine/` — общий движок, `jobs/orders/` —
  воркер заказов по шагам, `jobs/index.ts` — реестр.
- **Цикл воркера заказов:** заказы Kaspi за 1–3 мес → журнал изменений
  (`WorkerEvent`) → составы новых → даты прибытия из кабинета → отправка в Telegram.
- **Самовосстановление:** ошибка цикла не останавливает, 3 подряд — оповещение;
  падение процесса — «перезапуск после сбоя»; нет пульса — наблюдатель в API
  пишет «не отвечает».
- **Отправка — кому:** всё со склада Астаны (PP3) — наличие **и предзаказ** —
  в группу по виду доставки: «Отгрузки на Zammler» / «Своя доставка» / «Самовывоз»
  (`Warehouse.kaspiDeliveryChatId`, `ownDeliveryChatId`, `pickupChatId`); нужной нет —
  ждёт. Со складов без групп — поставщику (один ID на любой вид доставки).
  Поставщик не определён — разработчику (`devChatId`) с плашкой «ПОСТАВЩИК НЕ
  ОПРЕДЕЛЁН», окончательно: поставщику потом не дублируется.
- **Вид доставки:** `state = PICKUP` или `deliveryMode = DELIVERY_PICKUP` → самовывоз;
  `isKaspiDelivery` → Zammler; остальное → своя. `DELIVERY_LOCAL` бывает и у Kaspi
  Доставки — свою доставку по нему не определить.
- **Отправка — когда:** задержка 10/30/60 мин (галочка «Мгновенная отправка» —
  без неё, для теста), окно 8–17 по Астане и дни недели, точка отсечки — момент
  включения. Kaspi Доставка без «Планируемой даты прибытия» — ждёт. Отмена до
  отправки — не шлём; после — отмена/возврат тому же получателю. Анти-дубль —
  `OrderDispatch`.
- **Карточка-картинка** — Satori + resvg, шрифты Roboto в `server/assets/fonts/`
  (латиница и кириллица под разными именами). По виду доставки: Zammler и дата
  сдачи / адрес клиента и дата доставки / пункт выдачи и дата выдачи.
- **Настройки:** блок «Воркеры» (мгновенная отправка, настройки, состояние,
  причины неотправки, «Проверка отправки», таблица «История воркера» с получателем
  и Telegram ID), блок «Получатели в Telegram» (три группы Астаны, поставщики).

## Принятые решения (не пересматривать без причины)

| Решение | Почему |
|---|---|
| Сессии в таблице БД, не JWT | Уволил сотрудника — доступ закрывается сразу |
| Первый админ только из терминала | Публичная форма регистрации однажды окажется открытой в проде |
| Каталог Kaspi — из JSON кабинета, не парсингом HTML | Вёрстка поедет при первом редизайне |
| Закупка отдаётся в дашборд только ролям из `CATALOG_PURCHASE_ROLES` | На витрину — никогда; продавцу закупочные цены не нужны |
| Деньги — строками с двумя знаками | `number` на цене теряет тиын |
| Заказы: сырые `kaspiStatus` и `kaspiState` рядом с нашим `status` | Ошибёмся в правиле — пересчитаем из исходных, не дёргая Kaspi |
| Синхронизация заказов возобновляемая, с курсором | Два года это 244 отрезка по 3 дня |
| Поля кабинета синхронизация по токену не обновляет | Иначе каждый прогон затирал бы их пустотой |
| Незнакомые значения Kaspi помечаются проблемой | Полного перечня статусов площадка не публикует |
| Границы суток для фильтра дат считает клиент | Сервер не знает пояс пользователя |
| Площадки и офлайн-точки — один справочник `SalesPoint` | Иначе фильтр и статистика склеивались бы из двух мест |
| Дата заказа — `placedAt` | Период считается по одной дате для всех источников |
| Продавец — одно поле `sellerId` | Второе добавим, когда появится переброска продаж |
| Строка Excel = один заказ | Решение пользователя |
| Комментарии заказа — лента без правок и удалений | Подтираемый комментарий не отвечает на «кто решил» |
| Привязанный заказ и отменённые/возвраты не входят в выручку | Иначе двойной счёт и не-выручка |
| Номера офлайн-заказов с буквенным префиксом | Синхронизация Kaspi не затрёт офлайн-заказ |
| Импорт в два шага: предпросмотр, потом запись; спорное не угадывается | Иначе ошибка всплывёт через месяц в отчёте |
| Импорт каталога из Kaspi **только создаёт** (28.09.2026) | Остатки, предзаказ, закупка ведутся у нас и уходят в XML |
| Поставщик — `Supplier`, ключ сверки — UUID МойСклада; `externalId` руками не придумывается | По имени — 630 групп дублей |
| Артикул в выгрузке МойСклада — колонка «Код» | «Артикул» заполнен у 40 строк из 1799 |
| Закупка с валютой, к одной не приводится; сортировка по числу без валюты | Курса на дату закупки нет |
| История — в `AuditLog` в транзакции изменения; ключ поля, подпись из словаря | Изменение без записи хуже неудачной операции |
| Отчёт «Остатки» — снимок склада, пропавшее обнуляется; пусто → 0, минус как есть | Иначе проданный товар навсегда сохранил бы старую цифру |
| Себестоимость — одна на товар, в тенге | Решение пользователя |
| «Доступно» и «Дней на складе» не хранятся | Производное расходится со слагаемыми |
| `.xls` не читаем | `xlsx` в npm заброшен с уязвимостями |
| Реестр заказов — одна точка, по умолчанию Kaspi | У площадки и офлайн-точки разные таблицы |
| Состав заказа Kaspi — при первом открытии окна, у новых — воркером | Полный проход — 4800 запросов |
| Сортировка каталога — по одной колонке; фильтр «Склады» — «назначен» | Решение пользователя |
| Мультивыбор — пропом `Dropdown` | Один компонент выбора — одно поведение |
| Вся система по Астане (UTC+5) | Решение пользователя |
| **Доступ — `can([...])` у маршрута, роли в коде**, не таблица прав с галочками (01.10.2026) | Решение пользователя: просто и универсально. Галочки в настройках потребуют переделки |
| Чтение открыто всем вошедшим, действия — по ролям | Сотрудникам нужно видеть заказы и товары |
| Вход в кабинет Kaspi **по требованию**, не постоянный (30.09.2026) | Частые входы — блокировка учётной записи |
| Email и пароль Kaspi — в базе зашифрованными, ключ в `.env` | Бэкап базы без ключа доступа не даёт |
| GraphQL кабинета — запрос слово в слово как у кабинета | Урезанный запрос может быть отвергнут |
| Дата прибытия — только активным заказам, раз в час | Один запрос на заказ; частые запросы — блокировка |
| Воркер — отдельный процесс, все воркеры в одном (01.10.2026) | Падение воркера не роняет API; VPS 1 ГБ |
| Воркеры запускаются только при `WORKERS_ENABLED=true` | Копия базы с ноутбука не должна слать поставщикам |
| Следующий цикл — после конца текущего, потолок 10 мин | Решение пользователя: не начинать, пока не закончился |
| В журнал — только события, не «ничего нового» | 720 пустых строк в сутки |
| Маршрут: всё со склада Астаны (и предзаказ) → группа Астаны по виду доставки, остальное → поставщику (01.10.2026) | Решение пользователя: «это всё Астана» |
| Поставщик не определён → карточка разработчику с пометкой | Решение пользователя: заказ не должен теряться |
| Самовывоз — по `deliveryMode = DELIVERY_PICKUP` | `state = PICKUP` приходит только после принятия; проверено на живых заказах |
| Kaspi Доставка без даты сдачи — не отправлять, ждать | Решение пользователя |
| Две позиции — две карточки | Решение пользователя |
| Отправка — с точки отсечки (момент включения) | Иначе первый цикл высыпал бы весь период |
| Отмена одна на позицию; отмены первыми в цикле | «В пути» и «отменён» — одна отмена; отмена останавливает отгрузку |

Roadmap — в [docs/roadmap.md](docs/roadmap.md).

## В работе / следующий шаг

### Воркер — дотестировать на живых заказах

Карточки в группы Астаны и разработчику приходят (01.10.2026). Осталось:
1. Самовывоз после исправления (`DELIVERY_PICKUP`) — новый заказ должен уйти
   в «Астана — Самовывоз».
2. Предзаказ со склада Астаны — в группу по виду доставки. Заказ 1094124450
   ушёл **разработчику** — разобрано, см. задачу «Склад заказа не определён» ниже.
3. **Kaspi Доставка в наличии без «Планируемой даты прибытия»** (1094127411):
   кабинет её у наличия не даёт, есть только «Передать курьеру до». Решение
   пользователя — пока ждать. Если таких заказов будет много — предложено слать
   по «Передать курьеру до» со строкой на карточке вместо «Дата сдачи».
4. Отмена, возврат, окно отправки (ночь, неотмеченный день).
5. Снять галочку «Мгновенная отправка» после тестов.
6. Телефон клиента на карточке своей доставки — не выводится (личные данные
   уходят и поставщикам); добавить, если попросит пользователь.

### Воркер — склад заказа не определён в момент отправки (задача на 02.10.2026)

**Что случилось (01.10.2026, заказ 1094124450, пуф MC1024, PP3, Kaspi Доставка,
предзаказ):** при «Мгновенной отправке» воркер отправил заказ в 10:59 UTC, когда
он был ещё в статусе «Новый». Ушёл по ветке поставщика («[Астана] Досжан Пуфы»
без Telegram ID) → разработчику; отмена в 11:23 — туда же (по снимку получателя).
В 11:08 статус сменился на «Предзаказ»; сейчас у заказа `kaspiPickupPointId =
6871008_PP3` и склад PP3, то есть сейчас он ушёл бы в «Отгрузки на Zammler».
Значит, в 10:59 связи со складом PP3 у заказа не было: вероятно, у «Нового»
Kaspi ещё не прислал точку `6871008_PP3`. Доказать нельзя: `warehouseId`
перезаписывается каждой синхронизацией, прошлого значения нет.

**Предложено исправить (решить с пользователем):**
1. `resolveRecipient` (`recipients.ts`): у заказа Kaspi нет склада → не слать,
   а ждать («Склад заказа не определён, точка Kaspi: …» в журнал), как ждём дату
   сдачи. Для этого добавить `kaspiPickupPointId` в `dispatchOrderSelect`.
2. По желанию: не отправлять заказы в статусе «Новый» (до принятия).
3. Обновить `docs/workers.md` (правила маршрута).

**Идея пользователя — брать склад из каталога** (позиция → артикул → товар →
его склад в `VariantStock`). Моё мнение: как основной источник — нет. У товара
может быть несколько складов (Астана и склад поставщика), а с какого едет
именно этот заказ, решает Kaspi и пишет в заказе. Остатки в каталоге —
снимок импорта, могут устареть; товара может не быть в каталоге. Допустимо
разве что запасным путём, если товар назначен ровно одному складу. Решение — за
пользователем.
Довод пользователя: «в наличии в Астане — отгрузка из Астаны, кончилось —
предзаказ с завода (Петропавловск)». Против: сам 1094124450 — **предзаказ
из Астаны** (PP3, у Астаны свой предзаказ 7 дней), то есть предзаказ бывает
у обоих складов; остатки у нас — снимок импорта МойСклада, а Kaspi сейчас видит
наличие не из нашей базы (XML ещё не генерируем) — данные могут разойтись.
Ответ пользователя (01.10.2026): довод про предзаказ у обоих складов принят —
если предзаказ и в Астане, и на заводе, приоритет решает Kaspi, по каталогу
не определить. Довод про расхождение остатков не принят: наличие для Kaspi
будет идти из нашего XML, админка пока в разработке. **Вернуться к вопросу
02.10.2026.**

**Снять «Мгновенную отправку»** (задержка от 10 мин) скорее всего закрыло
бы этот случай: статус сменился через ~9 мин. Но когда именно Kaspi прислал
точку — неизвестно, гарантии нет; п.1 нужен всё равно.

### Складской учёт — решения пользователя (06.10.2026), план согласуется

**Модель остатков:** заказ с остатком → остаток −n, резерв +n (не «остаток 1 и
резерв 1»); остатка нет → `VariantStock` «предзаказ» (количество, новое поле;
не путать с `preOrderDays`) +n; заказ уехал → резерв −n; отмена до отгрузки →
остаток +n, резерв −n. **Доступно = Остаток + Ожидание.** Ожидание — из заказа
поставщику: статус «Ожидается» → +n, «Получен» → −n (через приёмку).
Импорт из МойСклада — один раз перед релизом, потом МойСклад не используется;
остаток при этом писать как «остаток МС − резерв МС» (в МС остаток включает резерв).

**Склады — один справочник `Warehouse`** (PP3, PP27…), второй модели нет.
Добавляются руками склады без Kaspi (шоурум «Астана Ncity» в ТЦ) —
`kaspiStoreId` станет необязательным. Остаток товара в шоуруме — строка
`VariantStock` этого склада.

**Этап A — документы склада, общий раздел `/dashboard/products/stock-documents`:**
один документ, тип дропдауном (оприходование / списание; позже приёмка — вместе
с заказом поставщику), фильтр по типу. Номер — 5 цифр, уникальный. Черновик
правит и удаляет менеджер; «Проведено» ставит ADMIN (константа ролей в коде) —
только тогда меняются остатки; проведённый не удаляется. Сумма = кол-во × цена.
Оприходование: цена из себестоимости, правится, при проведении пишется в
себестоимость товара. Списание: цена = себестоимость, без правки; в минус нельзя.
Выбор товара — картинка, название, артикул. Возвраты — оприходованием вручную.

**Этап B — резерв и предзаказ:** только новые заказы (с отсечки), Kaspi и офлайн;
офлайн — склад выбирает продавец. Нет склада от Kaspi — см. задачу выше.

**Этап C — заказ поставщику** (создан → утверждён → ожидается → получен) + приёмка.
